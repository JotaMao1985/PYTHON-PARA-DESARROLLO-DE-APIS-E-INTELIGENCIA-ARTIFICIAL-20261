Introducción: De Notebook a Producción

Imagina este escenario: terminaste tu modelo de series temporales en un Jupyter Notebook. Funciona. Los gráficos se ven bien, los residuos pasan las pruebas de normalidad y tu profesor está satisfecho. Ahora llega la pregunta inevitable: "¿Y cómo lo ponemos en producción para que el equipo de analítica lo consuma?"

Tu primer instinto es razonable: tomas el notebook, extraes la lógica en un main.py con FastAPI, hardcodeas la cadena de conexión a PostgreSQL, metes todo en un solo archivo de 400 líneas, y funciona. Hasta que tu compañero clona el repo y no puede correr la app porque tu contraseña de base de datos está en el código. O necesitas cambiar de la BD de desarrollo a la de producción, y eso implica editar código fuente. O quieres agregar un segundo endpoint que también consulta la BD, y copias y pegas la lógica de conexión. Tres meses después, el archivo tiene 1200 líneas y nadie entiende qué depende de qué.

Esto es lo que en ingeniería de software se llama código espagueti: todo está entrelazado, nada es reutilizable, y cualquier cambio rompe algo inesperado. En términos estadísticos, es como mezclar la recolección, limpieza, análisis y presentación de datos en un solo script sin secciones claras: eventualmente nadie puede auditar el proceso completo.

Objetivo de esta guía: Aprender tres patrones que resuelven estos problemas de raíz: (1) Variables de entorno para sacar la configuración sensible fuera del código, (2) Inyección de dependencias para que cada pieza declare explícitamente qué necesita, y (3) Integración modular para que main.py se lea casi como pseudocódigo.

¿Por qué un estadístico necesita estos patrones?

Como estadísticos, están acostumbrados a garantizar la reproducibilidad de sus análisis: semillas aleatorias fijas, datos versionados, supuestos documentados. Estos tres patrones son el equivalente en ingeniería de software a esa disciplina: garantizan que su aplicación es reproducible en cualquier entorno (desarrollo, staging, producción), mantenible por otros miembros del equipo, y auditable en cada uno de sus componentes.

Principio Estadístico Equivalente en Ingeniería Patrón en esta Guía
Reproducibilidad del análisis Configuración externa e idempotente Variables de entorno (.env + pydantic-settings)
Separación de concerns (EDA ≠ inferencia ≠ reporte) Principio de Responsabilidad Única Inyección de Dependencias (Depends)
Documentación del pipeline Árbol de dependencias explícito Arquitectura modular (archivos con responsabilidad única)

Módulo 1: De lo Duro a lo Flexible — Variables de Entorno

1.1 El Antipatrón: Credenciales en el Código

Observa este fragmento. Es exactamente lo que no debes hacer:
main.py — ❌ ANTIPATRÓN 
# main.py — ❌ ANTIPATRÓN
from sqlalchemy import create_engine

DATABASE_URL = "postgresql://admin:[email protected]:5432/encuestas_db"
API_KEY_REDCAP = "abc123xyz789"

engine = create_engine(DATABASE_URL)
Problema Consecuencia
Contraseña en texto planoSi se sube a GitHub, queda en el historial de Git para siempre
IP del servidor fijaCambiar de entorno requiere editar código fuente
API key mezclada con lógicaCualquier lector del código tiene acceso al sistema de captura de datos

1.2 La Solución: .env + Tipado con pydantic-settings

La idea es simple: las credenciales y parámetros viven en un archivo .env que nunca se sube al repositorio. Tu código lee ese archivo y valida que todo esté correcto antes de arrancar.

Paso 1.1: Instalar dependencias

Terminal 
pip install pydantic-settings python-dotenv

Paso 1.2: Crear el archivo .env

En la raíz de tu proyecto (al mismo nivel que main.py), crea un archivo llamado .env:

.env 
# .env — Este archivo NO se sube a Git
DB_HOST=localhost
DB_PORT=5432
DB_NAME=encuestas_db
DB_USER=admin
DB_PASSWORD=SuperSecreto123
DEBUG_MODE=true
SAMPLE_SIZE=1000
⚠️ Importante: Agrega .env a tu archivo .gitignore inmediatamente. Esto evita que se suba al repositorio por accidente. Tu .gitignore debe incluir al menos: .env, __pycache__/, y *.pyc.

Paso 1.3: Crear config.py con Validación de Tipos

Aquí es donde pydantic-settings brilla. En lugar de leer las variables como strings crudos, defines una clase que valida y convierte los tipos automáticamente:

config.py 
# config.py
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """
    Configuración de la aplicación.
    Cada atributo se mapea a una variable de entorno
    del mismo nombre (case-insensitive por defecto).
    """

    # --- Conexión a Base de Datos ---
    db_host: str
    db_port: int                    # Convierte "5432" (str) → 5432 (int)
    db_name: str
    db_user: str
    db_password: str

    # --- Parámetros de la aplicación ---
    debug_mode: bool = False        # Valor por defecto si no está en .env
    sample_size: int = 500          # Tamaño de muestra por defecto

    model_config = SettingsConfigDict(
        env_file=".env",            # Archivo de donde leer las variables
        env_file_encoding="utf-8",
    )

    @property
    def database_url(self) -> str:
        """Construye la URL de conexión a partir de las partes."""
        return (
            f"postgresql://{self.db_user}:{self.db_password}"
            f"@{self.db_host}:{self.db_port}/{self.db_name}"
        )
¿Qué hace Pydantic con los tipos?

db_port: int → Pydantic lee "5432" del .env y lo convierte a int. Si pones "abc", la app no arranca y te dice exactamente qué falló.

debug_mode: bool = False → Pydantic entiende que "true", "1", "yes" son True. Tiene un valor por defecto por si no defines la variable.

database_url es una propiedad derivada, no una variable de entorno. Se calcula a partir de las demás.

1.3 Ejercicio Práctico

Modifica config.py para agregar estas variables y verifica con un script de prueba:

  1. CONFIDENCE_LEVEL: float → con valor por defecto 0.95.
  2. MAX_ITERATIONS: int → sin valor por defecto (obligatoria en .env).
  3. APP_NAME: str → con valor por defecto "API Encuestas".

Verificación de Comprensión

Nivel Medio

Si defines db_port: int en tu clase Settings y en tu archivo .env escribes DB_PORT=abc, ¿qué sucede al instanciar Settings()?

Ver Respuesta y Retroalimentación▼
Respuesta Correcta: B

BaseSettings hereda todo el poder de validación de Pydantic. Si un campo está declarado como int y el valor provisto no es convertible a entero, Pydantic lanza un ValidationError al momento de la instanciación. Esto es lo que se llama fail fast: la app falla inmediatamente con un mensaje claro en lugar de fallar más tarde de forma impredecible.

Módulo 2: Inyección de Dependencias con Depends

2.1 ¿Qué es una "Dependencia"?

En el contexto más práctico posible: una dependencia es algo que tu función necesita para hacer su trabajo, pero que ella no debería crear por sí misma.

Piensa en esta analogía estadística: cuando haces un análisis, necesitas datos. Pero tu función de análisis no debería ser la que se conecta a la base de datos, descarga los datos, los limpia, y luego los analiza. Idealmente, tu función recibe los datos ya listos y se concentra en lo suyo.

2.2 Depends en FastAPI: La Mecánica

Depends es la forma que tiene FastAPI de decir: "Antes de ejecutar este endpoint, ejecuta esta otra función y pásale el resultado como parámetro."

Ejemplo mínimo de Depends 
from fastapi import FastAPI, Depends

app = FastAPI()


def get_sample_size() -> int:
    """Dependencia simple: retorna un valor de configuración."""
    return 1000


@app.get("/experimento")
def crear_experimento(n: int = Depends(get_sample_size)):
    """
    FastAPI ejecuta get_sample_size() automáticamente
    y pasa el resultado como 'n'.
    """
    return {"mensaje": f"Experimento creado con n={n}"}
¿Por qué no simplemente llamar get_sample_size() dentro del endpoint? Porque Depends te da tres ventajas: (1) Reutilización — usas la misma dependencia en 20 endpoints sin repetir código. (2) Testeo — en pruebas puedes reemplazar la dependencia por un mock sin tocar el endpoint. (3) Composición — las dependencias pueden depender de otras, formando un árbol que FastAPI resuelve automáticamente.

2.3 Dependencia con Ciclo de Vida: yield

Para recursos que necesitan limpieza (como una conexión a base de datos que debe cerrarse), usas yield en lugar de return:

Dependencia con yield 
from typing import Generator


def get_db_session() -> Generator:
    """
    Dependencia con ciclo de vida:
    - Antes del yield: se crea el recurso (abrir sesión).
    - yield: el endpoint usa el recurso.
    - Después del yield: se limpia (cerrar sesión).
    """
    print("→ Abriendo sesión de BD")
    session = {"fake": "session"}  # Simulación
    try:
        yield session
    finally:
        print("→ Cerrando sesión de BD")
        # Aquí: session.close() en una app real

2.4 Dependencia que Carga la Configuración

Ahora conectamos con el Módulo 1. Creamos una dependencia que instancie Settings:

dependencies.py 
# dependencies.py
from functools import lru_cache
from config import Settings


@lru_cache
def get_settings() -> Settings:
    """
    Carga la configuración desde .env.
    
    @lru_cache asegura que Settings() se instancie UNA sola vez
    y se reutilice en todas las peticiones. Evita leer
    el archivo .env en cada request.
    """
    return Settings()
¿Qué hace @lru_cache aquí?

@lru_cache es un decorador de la biblioteca estándar de Python. Memoriza el resultado de la función: la primera vez ejecuta Settings() (que lee el disco), las siguientes retorna el mismo objeto sin volver a leer el .env. Es como cachear el resultado de un cálculo estadístico costoso para no repetirlo innecesariamente.

2.5 Ejercicio Práctico

Crea un archivo dependencies.py con dos dependencias y un main.py que las use:

  • Dependencia 1: get_settings — carga la configuración con @lru_cache (ya la tienes arriba).
  • Dependencia 2: get_db — simula una sesión de BD usando un diccionario. Debe imprimir "Abriendo conexión" al inicio, hacer yield de {"connected": True}, e imprimir "Cerrando conexión" en el finally.

Crea un endpoint GET /health que use ambas dependencias. Levanta la app con uvicorn main:app --reload y observa en la terminal los mensajes de apertura y cierre de conexión.

Verificación de Comprensión

Nivel Medio

En una dependencia que usa yield, ¿qué pasa si el endpoint lanza una excepción antes de terminar?

Ver Respuesta y Retroalimentación▼
Respuesta Correcta: B

Este es precisamente el valor del patrón try/yield/finally. El bloque finally se ejecuta siempre, sin importar si el endpoint completó exitosamente o lanzó una excepción. Esto garantiza que recursos como conexiones de BD, archivos abiertos o locks siempre se liberen correctamente, evitando resource leaks.

Módulo 3: Integración Final — API Modular

3.1 Árbol de Dependencias

La verdadera potencia de Depends aparece cuando las dependencias dependen entre sí. FastAPI resuelve este árbol automáticamente de las hojas hacia la raíz:

3.2 Estructura Final del Proyecto

proyecto_encuestas/
├── .env                 ← Configuración sensible (NO en Git)
├── .gitignore
├── requirements.txt
├── config.py            ← Definición tipada de Settings
├── database.py          ← Motor y sesión de SQLAlchemy
├── dependencies.py      ← Funciones de dependencia
├── models.py            ← Modelos de SQLAlchemy (tablas)
├── schemas.py           ← Esquemas Pydantic (entrada/salida)
└── main.py              ← Solo endpoints, limpio y legible

3.3 Código Final: database.py

database.py 
# database.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase


class Base(DeclarativeBase):
    """Clase base para todos los modelos de SQLAlchemy."""
    pass


def build_engine(database_url: str):
    """Crea el motor de conexión a la BD."""
    return create_engine(database_url, echo=False)


def build_session_factory(database_url: str):
    """
    Crea una fábrica de sesiones.
    Una 'sesión' es el objeto a través del cual haces
    queries, inserts, updates, etc.
    """
    engine = build_engine(database_url)
    return sessionmaker(
        autocommit=False,
        autoflush=False,
        bind=engine,
    )

3.4 Código Final: models.py

models.py 
# models.py
from sqlalchemy import Column, Integer, String, Float, DateTime
from sqlalchemy.sql import func
from database import Base


class Encuesta(Base):
    """
    Modelo que representa una tabla de resultados de encuestas.
    Cada fila es una respuesta individual de un participante.
    """
    __tablename__ = "encuestas"

    id = Column(Integer, primary_key=True, index=True)
    participante_id = Column(String(50), nullable=False)
    pregunta = Column(String(200), nullable=False)
    respuesta_likert = Column(Integer, nullable=False)  # Escala 1-5
    tiempo_respuesta_seg = Column(Float)                # Segundos
    fecha_registro = Column(
        DateTime(timezone=True),
        server_default=func.now(),
    )

3.5 Código Final: schemas.py

schemas.py 
# schemas.py
from pydantic import BaseModel, Field
from datetime import datetime


class EncuestaCreate(BaseModel):
    """Esquema para recibir datos de una nueva respuesta."""
    participante_id: str = Field(
        ..., min_length=1, max_length=50,
        examples=["P-0042"],
    )
    pregunta: str = Field(
        ..., min_length=1, max_length=200,
        examples=["¿Qué tan satisfecho está con el servicio?"],
    )
    respuesta_likert: int = Field(..., ge=1, le=5)
    tiempo_respuesta_seg: float | None = Field(
        default=None, ge=0, examples=[12.5],
    )


class EncuestaRead(BaseModel):
    """Esquema para retornar datos de una respuesta."""
    id: int
    participante_id: str
    pregunta: str
    respuesta_likert: int
    tiempo_respuesta_seg: float | None
    fecha_registro: datetime

    model_config = {"from_attributes": True}


class ResumenEstadistico(BaseModel):
    """Esquema para retornar un resumen de las respuestas."""
    total_respuestas: int
    media_likert: float
    desviacion_estandar_likert: float

3.6 Código Final: dependencies.py Completo

dependencies.py — versión completa 
# dependencies.py — versión completa
from typing import Generator
from functools import lru_cache

from fastapi import Depends
from sqlalchemy.orm import Session

from config import Settings
from database import build_session_factory


@lru_cache
def get_settings() -> Settings:
    return Settings()


@lru_cache
def _get_session_factory(db_url: str):
    """Cachea la fábrica para no recrear el Engine en cada request."""
    return build_session_factory(db_url)


def get_db(
    settings: Settings = Depends(get_settings),
) -> Generator[Session, None, None]:
    """
    Dependencia que provee una sesión de base de datos.
    
    Nota cómo esta dependencia DEPENDE de get_settings.
    FastAPI resuelve el árbol automáticamente:
      get_settings() → settings → get_db(settings) → session
    """
    SessionFactory = _get_session_factory(settings.database_url)
    session = SessionFactory()
    try:
        yield session
    finally:
        session.close()

3.7 Código Final: main.py Limpio

Observa lo limpio que queda cuando toda la infraestructura está delegada. El archivo solo contiene endpoints y orquestación:

main.py — API limpia 
# main.py
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session
from sqlalchemy import func as sql_func

from config import Settings
from dependencies import get_db, get_settings
from models import Encuesta
from schemas import EncuestaCreate, EncuestaRead, ResumenEstadistico

app = FastAPI(
    title="API de Encuestas Estadísticas",
    version="1.0.0",
)


@app.get("/health")
def health_check(settings: Settings = Depends(get_settings)):
    return {"status": "ok", "debug": settings.debug_mode}


@app.post("/encuestas", response_model=EncuestaRead, status_code=201)
def registrar_respuesta(
    datos: EncuestaCreate,
    db: Session = Depends(get_db),
):
    """Registra una nueva respuesta de encuesta."""
    nueva = Encuesta(**datos.model_dump())
    db.add(nueva)
    db.commit()
    db.refresh(nueva)
    return nueva


@app.get("/encuestas", response_model=list[EncuestaRead])
def listar_respuestas(
    skip: int = 0,
    limit: int = 100,
    db: Session = Depends(get_db),
    settings: Settings = Depends(get_settings),
):
    """Lista las respuestas con paginación."""
    limit = min(limit, settings.sample_size)
    return db.query(Encuesta).offset(skip).limit(limit).all()


@app.get("/encuestas/resumen", response_model=ResumenEstadistico)
def resumen_estadistico(db: Session = Depends(get_db)):
    """Calcula estadísticas descriptivas de las respuestas."""
    resultado = db.query(
        sql_func.count(Encuesta.id).label("total"),
        sql_func.avg(Encuesta.respuesta_likert).label("media"),
        sql_func.stddev(Encuesta.respuesta_likert).label("stddev"),
    ).first()

    if resultado.total == 0:
        raise HTTPException(status_code=404, detail="Sin datos")

    return ResumenEstadistico(
        total_respuestas=resultado.total,
        media_likert=round(float(resultado.media), 4),
        desviacion_estandar_likert=round(float(resultado.stddev or 0), 4),
    )

Archivo Responsabilidad Única
