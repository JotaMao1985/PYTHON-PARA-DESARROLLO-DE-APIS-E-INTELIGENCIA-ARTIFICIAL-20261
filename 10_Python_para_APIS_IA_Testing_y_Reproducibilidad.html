«Cada modo de fallo previsto» es la parte que se suele saltar y la que la rúbrica mira: una API que sólo tiene pruebas del camino feliz no está probada. Entorno: Python 3.11.9 con pytest, httpx y TestClient.

1. Introducción

En las semanas previas se construyó una API estadística con FastAPI: se definieron modelos Pydantic con @field_validator, se inyectaron dependencias mediante Depends, se conectó SQLAlchemy a SQLite y se documentaron los endpoints en Swagger. El servicio funciona en el navegador y responde con códigos HTTP correctos. Sin embargo, una API que solo se prueba a mano es frágil: cualquier cambio puede invalidar un cálculo de regresión, modificar la forma de un intervalo de confianza o romper la serialización de un pronóstico de series temporales sin que el desarrollador lo note.

Esta unidad introduce el conjunto de prácticas que diferencia una API experimental de una API confiable para producción estadística:

  • la pirámide de testing, que organiza los esfuerzos de prueba según su costo y velocidad;
  • pytest, el framework de testing más usado en el ecosistema científico de Python;
  • el TestClient de FastAPI, que permite ejercitar endpoints sin levantar un servidor;
  • las fixtures, que aíslan los efectos secundarios y construyen datos de prueba reproducibles;
  • la reproducibilidad sin contenedores, lograda mediante fijación de versiones, semillas y archivos de configuración deterministas.
Objetivo de aprendizaje Al finalizar la unidad, el estudiante diseña, escribe y ejecuta una suite automatizada de pruebas para una API estadística, distingue los niveles de la pirámide, factoriza datos con fixtures y deja documentado un entorno cuya reconstrucción produzca los mismos resultados numéricos en otra máquina, sin recurrir a Docker.

Caso de estudio transversal

Para mantener un hilo conductor estadístico, los ejemplos giran alrededor de una API llamada encuestas-api que expone tres endpoints:

  • POST /muestras — registra una observación de encuesta (Pydantic valida edad, ingreso y estrato).
  • GET /resumen/media — devuelve la media muestral del ingreso con su intervalo de confianza al 95 %.
  • POST /modelos/regresion — ajusta una regresión lineal simple y devuelve coeficientes, R² y residuales.

Sobre esta base se construyen pruebas de los tres niveles de la pirámide.

2. Pirámide de testing

La pirámide de testing, popularizada por Mike Cohn, ordena los tipos de pruebas según cuántas se escriben de cada una. La base es ancha (muchas pruebas baratas y rápidas) y la cima es estrecha (pocas pruebas costosas y lentas). En una API estadística la pirámide luce así:

End-to-End (E2E) ~5 % · lentas · costosas · alta confianza
Integración ~15 % · velocidad media · ejercitan colaboradores reales
Unitarias ~80 % · milisegundos · aislamiento total

Figura 2.1 — Las pruebas unitarias dominan la suite por cantidad pero ocupan apenas milisegundos cada una; las E2E son escasas pero pueden tomar segundos por prueba.

2.1 Pruebas unitarias

Se centran en una sola unidad lógica, típicamente una función o un método, con todas sus dependencias reemplazadas. En el contexto estadístico una prueba unitaria valida la función pura que calcula la media y el error estándar:

# app/stats.py
from math import sqrt

def media_y_ee(datos: list[float]) -> tuple[float, float]:
    """Devuelve (media, error estándar). Requiere n >= 2."""
    n = len(datos)
    if n < 2:
        raise ValueError("Se requieren al menos 2 observaciones")
    media = sum(datos) / n
    var = sum((x - media) ** 2 for x in datos) / (n - 1)
    return media, sqrt(var / n)
# tests/test_stats.py
import pytest
from app.stats import media_y_ee

def test_media_y_ee_rechaza_una_sola_observacion():
    with pytest.raises(ValueError, match="al menos 2"):
        media_y_ee([5.0])

def test_media_y_ee_caso_canonico():
    media, ee = media_y_ee([2.0, 4.0, 4.0, 4.0, 5.0, 5.0, 7.0, 9.0])
    assert media == pytest.approx(5.0)
    assert ee == pytest.approx(0.7071067811865476, rel=1e-9)

2.2 Pruebas de integración

Verifican que dos o más componentes colaboran correctamente. Una prueba de integración típica en la API de encuestas combina el endpoint POST /muestras, la validación Pydantic y la persistencia con SQLAlchemy contra una base SQLite en memoria. El TestClient de FastAPI (sección 4) las mantiene en el orden de decenas de milisegundos al evitar levantar un servidor real.

2.3 Pruebas extremo a extremo (E2E)

Levantan el sistema completo, lo más parecido posible al entorno productivo, y lo ejercitan a través de la interfaz pública. Para una API estadística esto significa arrancar Uvicorn, conectarse a la base de datos real y enviar peticiones HTTP por la red local. Son lentas, frágiles ante cambios cosméticos y costosas de mantener; por eso se reservan para flujos críticos: por ejemplo, asegurar que un cliente externo puede subir un CSV de encuesta, ajustar una regresión y descargar los coeficientes.

Heurística de proporción Una API estadística mediana suele tener cientos de pruebas unitarias, decenas de pruebas de integración y unas pocas (3 a 10) pruebas E2E. Si la proporción se invierte, la suite tarda demasiado y los desarrolladores la ejecutan cada vez con menor frecuencia, perdiendo su valor.

2.4 Comparación rápida

Nivel Qué prueba Velocidad Ejemplo estadístico
Unitaria Una función pura, aislada. < 10 ms Cálculo del estadístico t para una muestra.
Integración Endpoint + validación + BD en memoria. 10–200 ms Insertar una observación y consultar la media.
E2E Sistema completo por HTTP real. 1–10 s Subir CSV, ajustar regresión y descargar JSON.

3. Framework pytest

pytest es el framework de testing dominante en Python. A diferencia del módulo estándar unittest, no exige clases ni nomenclatura ceremonial: basta con funciones cuyo nombre empieza por test_ dentro de archivos cuyo nombre también empieza por test_. Las aserciones se escriben con la palabra clave assert de Python, y pytest reescribe el bytecode para mostrar el valor real cuando una falla.

3.1 Estructura de proyecto recomendada

encuestas-api/
├── app/
│   ├── __init__.py
│   ├── main.py
│   ├── stats.py
│   ├── models.py
│   └── db.py
├── tests/
│   ├── __init__.py
│   ├── conftest.py            # fixtures compartidas
│   ├── test_stats.py
│   ├── test_endpoints.py
│   └── test_reproducibilidad.py
├── pyproject.toml
├── pytest.ini
└── requirements.txt

3.2 Configuración mínima

El archivo pytest.ini declara la configuración del proyecto. Se recomienda como mínimo:

# pytest.ini
[pytest]
minversion = 8.0
testpaths = tests
python_files = test_*.py
python_functions = test_*
addopts = -ra --strict-markers --strict-config -q
markers =
    slow: pruebas lentas (excluir con -m "not slow")
    integration: pruebas que tocan la base de datos
    statistics: pruebas que validan resultados numéricos

La opción --strict-markers obliga a declarar cada marcador, evitando typos silenciosos del tipo @pytest.mark.intgration. La opción -ra imprime un resumen de pruebas que no fueron passed.

3.3 Aserciones expresivas

pytest enriquece assert mostrando los operandos cuando una prueba falla. En el dominio estadístico, donde rara vez se compara con igualdad estricta, conviene usar los helpers pytest.approx y math.isclose:

import pytest
from app.stats import media_y_ee

def test_media_de_normales_centrada_en_cero():
    import random
    random.seed(42)
    datos = [random.gauss(0, 1) for _ in range(1000)]
    media, ee = media_y_ee(datos)
    # Tolerancia: 4 errores estándar evita una prueba inestable (flaky)
    # sin volverla trivialmente cierta.
    assert abs(media) < 4 * ee, f"Media {media} fuera de banda"

3.4 Parametrización

El decorador @pytest.mark.parametrize ejecuta una misma prueba con varios juegos de entradas. Cada combinación cuenta como una prueba independiente: si una falla, pytest indica exactamente cuál.

import pytest
from app.stats import media_y_ee

@pytest.mark.parametrize(
    "datos, media_esperada",
    [
        ([1.0, 2.0, 3.0],          2.0),
        ([10.0, 20.0],               15.0),
        ([-1.0, 0.0, 1.0],          0.0),
        ([100.0] * 5 + [200.0] * 5, 150.0),
    ],
    ids=["trio", "par", "simetrica", "bimodal"],
)
def test_media_de_casos_canonicos(datos, media_esperada):
    media, _ = media_y_ee(datos)
    assert media == pytest.approx(media_esperada)

Los identificadores explícitos en ids=[...] facilitan filtrar pruebas con pytest -k bimodal y producen reportes legibles.

Figura 3.1 — Cada fila corresponde a una invocación independiente de la misma función de prueba con un juego distinto de datos. El diamante magenta es el valor de la aserción media == media_esperada; los círculos púrpura son las observaciones del caso.

3.5 Marcadores

Los marcadores etiquetan pruebas para seleccionarlas o saltarlas. Los más útiles en una suite estadística son:

  • @pytest.mark.skip(reason=...) — omite la prueba siempre.
  • @pytest.mark.skipif(condición, reason=...) — omite condicionalmente.
  • @pytest.mark.xfail — se espera que falle (útil para bugs conocidos).
  • Marcadores propios declarados en pytest.ini, como @pytest.mark.slow. 
import pytest
import sys

@pytest.mark.slow
def test_simulacion_montecarlo_grande():
    # Se ejecuta solo cuando se invoca con -m slow
    ...

@pytest.mark.skipif(sys.platform == "win32", reason="Backend BLAS distinto")
def test_residuales_consistentes_con_R():
    ...

@pytest.mark.xfail(reason="Bug #142: precisión flotante en estrato vacío")
def test_resumen_estrato_vacio():
    ...

Para ejecutar selectivamente:

# Solo unitarias rápidas:
pytest -m "not slow"

# Solo integración:
pytest -m integration

# Una prueba específica por nombre:
pytest tests/test_stats.py::test_media_de_casos_canonicos[bimodal]
Sugerencia didáctica Conviene agrupar las pruebas que requieren red, base de datos o simulaciones largas bajo un marcador propio. Así la ejecución por defecto en el flujo de trabajo del estudiante es siempre rápida, y las pruebas pesadas se reservan para CI o para una invocación explícita con -m.

4. TestClient de FastAPI

Probar una API por HTTP real exige levantar Uvicorn, abrir un puerto, hacer peticiones con httpx o requests y limpiar el proceso al final. FastAPI ofrece una alternativa elegante: TestClient, una envoltura sobre httpx.Client que se comunica con la aplicación ASGI directamente, sin tocar la red. Las peticiones, las cabeceras y los códigos de estado son auténticos, pero la latencia y las dependencias de sistema son mínimas.

4.1 Configuración de la aplicación de ejemplo

# app/main.py
from fastapi import FastAPI, Depends, HTTPException
from pydantic import BaseModel, Field, field_validator
from .stats import media_y_ee

app = FastAPI(title="encuestas-api", version="1.0.0")

class Observacion(BaseModel):
    edad: int = Field(ge=18, le=120)
    ingreso: float = Field(gt=0)
    estrato: int = Field(ge=1, le=6)

    @field_validator("ingreso")
    @classmethod
    def ingreso_no_atipico(cls, v: float) -> float:
        if v > 1e9:
            raise ValueError("Ingreso fuera de rango plausible")
        return v

# Almacenamiento en memoria para el ejemplo;
# en producción se inyecta una sesión de SQLAlchemy.
_almacen: list[Observacion] = []

def obtener_almacen() -> list[Observacion]:
    return _almacen

@app.post("/muestras", status_code=201)
def crear_muestra(obs: Observacion, almacen=Depends(obtener_almacen)):
    almacen.append(obs)
    return {"id": len(almacen) - 1, "obs": obs}

@app.get("/resumen/media")
def resumen_media(almacen=Depends(obtener_almacen)):
    if len(almacen) < 2:
        raise HTTPException(status_code=409,
                            detail="Se requieren al menos 2 observaciones")
    media, ee = media_y_ee([o.ingreso for o in almacen])
    return {"n": len(almacen), "media": media, "error_estandar": ee,
            "ic95": [media - 1.96 * ee, media + 1.96 * ee]}

4.2 Pruebas con TestClient

# tests/test_endpoints.py
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_post_muestra_valida_devuelve_201():
    payload = {"edad": 35, "ingreso": 2_500_000, "estrato": 3}
    response = client.post("/muestras", json=payload)
    assert response.status_code == 201
    cuerpo = response.json()
    assert cuerpo["obs"]["edad"] == 35
    assert cuerpo["obs"]["ingreso"] == 2_500_000

def test_post_muestra_con_edad_invalida_devuelve_422():
    response = client.post("/muestras",
                           json={"edad": -1, "ingreso": 100, "estrato": 3})
    assert response.status_code == 422
    errores = response.json()["detail"]
    assert any(e["loc"] == ["body", "edad"] for e in errores)

def test_resumen_media_falla_con_pocas_observaciones():
    response = client.get("/resumen/media")
    assert response.status_code == 409
Cuidado con el estado compartido El _almacen del ejemplo es global, así que las pruebas se contaminan unas a otras según el orden de ejecución. Esto se resuelve sustituyendo la dependencia obtener_almacen por una versión limpia en cada prueba (sección 4.3) o encapsulando el estado en una fixture (sección 5).

4.3 Sustitución de dependencias con app.dependency_overrides

FastAPI permite reemplazar cualquier Depends por una función arbitraria en tiempo de prueba. Es la herramienta canónica para inyectar bases de datos en memoria, autenticación falsa o relojes deterministas:

from fastapi.testclient import TestClient
from app.main import app, obtener_almacen, Observacion

def test_resumen_media_con_almacen_inyectado():
    # El endpoint accede a o.ingreso (atributo), por lo que el almacén falso
    # debe contener instancias de Observacion, no diccionarios crudos.
    almacen_falso = [
        Observacion(edad=30, ingreso=1_000, estrato=2),
        Observacion(edad=40, ingreso=3_000, estrato=4),
    ]
    app.dependency_overrides[obtener_almacen] = lambda: almacen_falso

    try:
        client = TestClient(app)
        r = client.get("/resumen/media")
        assert r.status_code == 200
        assert r.json()["media"] == pytest.approx(2_000)
    finally:
        app.dependency_overrides.clear()

El bloque try/finally garantiza que las modificaciones no se filtren a otras pruebas. En la próxima sección este patrón se encapsula en una fixture, que lo hace automático y declarativo.

4.4 Pruebas asíncronas

El TestClient es síncrono incluso para endpoints declarados con async def: ejecuta el ciclo de eventos por debajo. Cuando se necesita código de prueba realmente asíncrono (por ejemplo, para llamar a varios endpoints en paralelo o para colaborar con corrutinas), se utiliza httpx.AsyncClient con el plugin pytest-asyncio: 

import asyncio, pytest, httpx
from app.main import app

@pytest.mark.asyncio
async def test_dos_post_concurrentes():
    async with httpx.AsyncClient(
        transport=httpx.ASGITransport(app=app), base_url="http://test"
    ) as ac:
        # asyncio.gather las dispara en paralelo; el orden de respuesta no se asume.
        r1, r2 = await asyncio.gather(
            ac.post("/muestras",
                    json={"edad": 30, "ingreso": 1000, "estrato": 2}),
            ac.post("/muestras",
                    json={"edad": 40, "ingreso": 3000, "estrato": 4}),
        )
    assert r1.status_code == 201 and r2.status_code == 201
Ejercicio 4.1 Se desea proteger el endpoint POST /muestras exigiendo una cabecera X-API-Token validada por una dependencia verificar_token. Se pide:
  1. Escribir la dependencia y aplicarla con Depends.
  2. Probar con TestClient que un POST sin la cabecera devuelve 401.
  3. Probar con TestClient que un POST con la cabecera correcta devuelve 201.
Sugerencia: utilícese app.dependency_overrides para inyectar un verificador permisivo en el caso 3.

5. Fixtures en pytest

Una fixture es una función decorada con @pytest.fixture que produce un valor o un recurso a disposición de las pruebas. pytest las inyecta por nombre: cuando una función de prueba declara un parámetro cuyo nombre coincide con una fixture disponible, pytest la ejecuta y le pasa el resultado. El sistema de fixtures cumple tres funciones: aislar las pruebas, evitar duplicación y modelar el ciclo de vida (setup/teardown) de los recursos.

5.1 Fixture mínima

# tests/conftest.py
import pytest

@pytest.fixture
def muestra_normal_pequena() -> list[float]:
    """Muestra fija para pruebas determinísticas."""
    return [2.0, 4.0, 4.0, 4.0, 5.0, 5.0, 7.0, 9.0]

# tests/test_stats.py
from app.stats import media_y_ee
import pytest

def test_media_constante_via_fixture(muestra_normal_pequena):
    media, _ = media_y_ee(muestra_normal_pequena)
    assert media == pytest.approx(5.0)

Al colocar la fixture en conftest.py, pytest la pone disponible para todas las pruebas del directorio sin necesidad de importarla.

5.2 Alcance (scope)

Cada fixture tiene un scope que controla cuántas veces se ejecuta:

Scope Frecuencia de ejecución Cuándo usarlo
function (por defecto) Una vez por cada prueba. Datos que pueden mutarse entre pruebas.
class Una vez por clase de pruebas. Suite agrupada que comparte estado.
module Una vez por archivo de pruebas. Cargar un dataset grande de solo lectura.
session Una vez para toda la corrida. Configuración costosa: motor de BD, modelo entrenado.
Regla de oro El alcance amplio (module, session) gana velocidad, pero solo es seguro si el recurso es inmutable. Una BD compartida entre pruebas con scope session exige transacciones que se reviertan al final de cada prueba; de lo contrario, las pruebas se contaminan y el orden empieza a importar.

5.3 Setup y teardown con yield

El patrón canónico para recursos con ciclo de vida (conexiones, archivos, procesos) es una fixture que entrega el recurso con yield y lo libera en las líneas posteriores:

import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from app.db import Base

@pytest.fixture(scope="function")
def db_sesion():
    # SETUP: motor SQLite en memoria, esquema creado.
    engine = create_engine("sqlite:///:memory:", future=True)
    Base.metadata.create_all(engine)
    Session = sessionmaker(bind=engine, future=True)
    sesion = Session()

    yield sesion

    # TEARDOWN: cerrar sesión y eliminar BD.
    sesion.close()
    Base.metadata.drop_all(engine)
    engine.dispose()

5.4 Composición de fixtures

Las fixtures pueden depender unas de otras. pytest resuelve el grafo de dependencias y las construye en orden. Esta es la forma idiomática de combinar una BD limpia, un cliente HTTP y datos sembrados:

import pytest
from fastapi.testclient import TestClient
from app.main import app, obtener_almacen

@pytest.fixture
def almacen_vacio() -> list:
    return []

@pytest.fixture
def cliente(almacen_vacio):
    app.dependency_overrides[obtener_almacen] = lambda: almacen_vacio
    with TestClient(app) as c:
        yield c
    app.dependency_overrides.clear()

def test_post_y_resumen_via_fixture(cliente):
    cliente.post("/muestras", json={"edad": 30, "ingreso": 1000, "estrato": 2})
    cliente.post("/muestras", json={"edad": 40, "ingreso": 3000, "estrato": 4})
    r = cliente.get("/resumen/media")
    assert r.status_code == 200
    assert r.json()["n"] == 2
    assert r.json()["media"] == 2000

5.5 Fábricas de datos parametrizables

Una fixture que devuelve una función permite generar datos a la medida dentro de cada prueba. Es el patrón factory-as-fixture:

import pytest
import random

@pytest.fixture
def fabrica_observaciones():
    """Devuelve una función que produce listas de observaciones reproducibles."""
    def _fabricar(n: int, semilla: int = 2026, ingreso_medio: float = 2_000_000):
        rng = random.Random(semilla)
        return [
            {
                "edad": rng.randint(18, 75),
                "ingreso": max(1.0, rng.gauss(ingreso_medio, ingreso_medio * 0.2)),
                "estrato": rng.randint(1, 6),
            }
            for _ in range(n)
        ]
    return _fabricar

def test_resumen_con_30_observaciones(cliente, fabrica_observaciones):
    for obs in fabrica_observaciones(30, semilla=1):
        cliente.post("/muestras", json=obs)
    r = cliente.get("/resumen/media")
    assert r.json()["n"] == 30
    assert r.json()["ic95"][0] < r.json()["media"] < r.json()["ic95"][1]

Como la fábrica recibe la semilla, las pruebas que la utilicen son completamente deterministas: cada vez que se ejecuten producirán los mismos datos sintéticos.

Figura 5.1 — Ingresos sintéticos generados por fabrica_observaciones(n=300, semilla=2026). El intervalo de confianza al 95 % rodea la media muestral; al fijar la semilla la figura se reproduce bit a bit en cualquier máquina.

5.6 Parametrización de fixtures

Una fixture puede declarar params= para que pytest la ejecute repetidamente con diferentes valores. Esto multiplica todas las pruebas que la consuman:

@pytest.fixture(params=[30, 100, 500], ids=["n30", "n100", "n500"])
def tamano_muestra(request) -> int:
    return request.param

def test_resumen_responde_para_varios_tamanos(cliente, fabrica_observaciones, tamano_muestra):
    for obs in fabrica_observaciones(tamano_muestra, semilla=7):
        cliente.post("/muestras", json=obs)
    cuerpo = cliente.get("/resumen/media").json()
    assert cuerpo["n"] == tamano_muestra
    assert cuerpo["ic95"][0] < cuerpo["media"] < cuerpo["ic95"][1]
    # Verificar que el IC se estrecha con n requiere comparar entre tamaños:
    # se delega al ejercicio 7.2 de la autoevaluación.
Diagnóstico de fixtures El comando pytest --fixtures lista todas las fixtures visibles desde el directorio actual con su docstring. Es una herramienta valiosa cuando el proyecto crece y hay riesgo de duplicar fixtures con nombres parecidos.

6. Reproducibilidad sin Docker

Reproducibilidad significa que dos personas, ejecutando el mismo código en dos máquinas distintas, obtienen los mismos resultados numéricos. En estadística esto es un requisito científico: una API que ajusta una regresión debe devolver los mismos coeficientes hoy y dentro de seis meses, en macOS y en Linux. Docker resuelve esta exigencia encapsulando el sistema operativo, pero introduce una capa adicional cuya curva de aprendizaje y costo no siempre se justifican en proyectos académicos. Esta sección presenta una alternativa basada únicamente en venv, fijación estricta de versiones, semillas explícitas y archivos de configuración deterministas.

6.1 Fijación estricta de dependencias

El archivo requirements.txt visto en semanas anteriores se generaliza con dos archivos:

  • requirements.in — declara únicamente las dependencias de alto nivel del proyecto (lo que el desarrollador realmente usa).
  • requirements.txt — contiene la versión exacta de cada dependencia y de cada dependencia transitiva, generada a partir del anterior.
# requirements.in
fastapi>=0.110,<0.120
uvicorn[standard]>=0.30,<0.32
pydantic>=2.7,<3.0
sqlalchemy>=2.0,<3.0
python-dotenv>=1.0,<2.0
numpy>=1.26,<2.0
pytest>=8.0,<9.0
httpx>=0.27,<0.29
pytest-asyncio>=0.23,<0.25

Para resolver versiones transitivas existen dos caminos. El más sencillo, sin herramientas adicionales:

# Crear y activar un entorno virtual limpio.
python3.11 -m venv .venv
source .venv/bin/activate         # macOS / Linux
# .venv\Scripts\activate         # Windows

# Instalar las dependencias declaradas.
pip install -r requirements.in

# Congelar el árbol completo con versiones exactas.
pip freeze --exclude-editable > requirements.txt

El más robusto utiliza pip-tools, que recalcula el lockfile cuando cambia el archivo de entrada y produce un fichero ordenado y comentado:

pip install pip-tools
pip-compile --generate-hashes --output-file=requirements.txt requirements.in
pip-sync requirements.txt
Hashes y verificación El flag --generate-hashes añade --hash=sha256:... a cada paquete. Cuando alguien clona el repositorio y ejecuta pip install -r requirements.txt, pip rechaza paquetes cuyo contenido no coincida bit a bit con el hash registrado. Esto cierra una clase entera de incidentes en los que un paquete se sobreescribe en PyPI.

El proyecto declara la versión exacta de Python en dos lugares:

6.3 Semillas y aleatoriedad determinista

Cualquier procedimiento estadístico que use números aleatorios debe sembrar explícitamente sus generadores. La semilla se fija antes de cualquier llamada que consuma aleatoriedad y se documenta en la configuración del proyecto.

# app/aleatorio.py
import os
import random
import numpy as np

def configurar_semillas(semilla: int | None = None) -> int:
    """Fija las semillas de random y numpy. Devuelve la semilla efectiva."""
    if semilla is None:
        semilla = int(os.environ.get("APP_SEED", "2026"))
    random.seed(semilla)
    np.random.seed(semilla)
    return semilla

# app/regresion.py
import numpy as np

def simular_regresion(n: int, beta0: float, beta1: float):
    rng = np.random.default_rng(seed=2026)  # API moderna preferible
    x = rng.uniform(0, 10, size=n)
    eps = rng.normal(0, 1, size=n)
    y = beta0 + beta1 * x + eps
    return x, y
Sembrar el RNG global no basta Las llamadas a np.random.seed sólo afectan al RNG global de NumPy. Las bibliotecas modernas (NumPy 1.17+, scikit-learn, PyTorch) recomiendan trabajar con objetos Generator propios (np.random.default_rng(seed)), porque son aislables y seguros frente a hilos. En la API se prefiere recibir el generador como parámetro en lugar de depender del estado global.

6.4 Configuración determinista vía .env

El archivo .env se versiona como plantilla (.env.example) y los valores reales quedan en .env, ignorado por git. Para reproducibilidad, los valores numéricos relevantes deben tener formatos exactos:

# .env.example
APP_SEED=2026
APP_NIVEL_CONFIANZA=0.95
APP_TOLERANCIA_NUMERICA=1e-9
APP_BD_URL=sqlite:///./encuestas.db
APP_LOG_LEVEL=INFO

El módulo de configuración carga estos valores con python-dotenv y los expone como objeto Pydantic, ya conocido por los estudiantes:

# app/config.py
from functools import lru_cache
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Configuracion(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="APP_")

    seed: int = Field(default=2026, ge=0)
    nivel_confianza: float = Field(default=0.95, gt=0.5, lt=1.0)
    tolerancia_numerica: float = Field(default=1e-9, gt=0)
    bd_url: str = "sqlite:///./encuestas.db"

@lru_cache
def obtener_config() -> Configuracion:
    return Configuracion()

6.5 Pruebas que validan reproducibilidad numérica

Una suite reproducible incluye pruebas explícitas que ejecutan el procedimiento dos veces y comparan los resultados con tolerancias acotadas. Estas pruebas son baratas y atrapan regresiones sutiles, como un cambio de versión de NumPy que altere el orden de evaluación de un sumatorio:

# tests/test_reproducibilidad.py
import numpy as np
from app.aleatorio import configurar_semillas
from app.regresion import simular_regresion

def test_regresion_simulada_es_reproducible():
    x1, y1 = simular_regresion(100, beta0=2.0, beta1=0.5)
    x2, y2 = simular_regresion(100, beta0=2.0, beta1=0.5)
    assert np.allclose(x1, x2, rtol=0, atol=0)
    assert np.allclose(y1, y2, rtol=0, atol=0)

def test_semilla_global_se_aplica():
    s1 = configurar_semillas(42)
    a = np.random.random(5)
    s2 = configurar_semillas(42)
    b = np.random.random(5)
    assert s1 == s2 == 42
    assert np.array_equal(a, b)

Figura 6.1 — Dos invocaciones independientes de simular_regresion(n=100, β₀=2, β₁=0.5) con la misma semilla producen arreglos que coinciden bit a bit. Si la prueba test_regresion_simulada_es_reproducible fallara, la causa más probable sería un cambio de versión de NumPy o un olvido de fijar la semilla.

¿Y el sistema operativo? Sin Docker, las diferencias entre macOS, Linux y Windows pueden manifestarse en el último bit decimal de operaciones flotantes y en backends BLAS distintos. Para una API estadística académica esto rara vez es relevante; las tolerancias del orden de 1e-9 a 1e-6 en pytest.approx y numpy.allclose absorben esa variación. Cuando se requiera reproducibilidad bit a bit, el siguiente paso natural sí es Docker o conda-lock.

8. Resumen y referencias

8.1 Resumen ejecutivo

  1. La pirámide de testing prescribe muchas pruebas baratas (unitarias), algunas intermedias (integración) y pocas costosas (E2E). Una API estadística saludable respeta esa proporción.
  2. pytest reemplaza la ceremonia de unittest por funciones simples, aserciones legibles y un sistema de fixtures expresivo. Sus marcadores y la parametrización permiten cubrir muchos casos sin duplicar código.
  3. TestClient de FastAPI ejecuta peticiones contra la aplicación ASGI sin levantar un servidor real. Sustituyendo dependencias con app.dependency_overrides se aíslan endpoints de la base de datos y de servicios externos.
  4. Las fixtures con yield modelan el ciclo de vida de los recursos. El scope determina cuántas veces se crean; las fábricas-fixture entregan datos sintéticos parametrizables y deterministas.
  5. Reproducibilidad sin Docker se logra fijando la versión de Python, congelando dependencias con hashes, sembrando explícitamente cada generador aleatorio, documentando la configuración numérica en .env y validando todo lo anterior con tests automatizados.

8.2 Comandos útiles

# Ejecutar toda la suite con resumen detallado:
