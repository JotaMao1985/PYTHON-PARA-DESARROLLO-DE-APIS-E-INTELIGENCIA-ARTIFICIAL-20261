Introducción: ¿De Qué Trata Esta Guía?

Hasta ahora tu aplicación FastAPI recibe datos, los valida con Pydantic, y devuelve respuestas. Pero hay una pieza que falta: ¿dónde se guardan esos datos cuando el servidor se apaga? Si reinicias la app, todo desaparece. Necesitas una base de datos, y necesitas una forma elegante de conectar tu código Python con ella. De eso trata esta guía.

Vamos a explicar cada concepto clave en términos simples antes de entrar en código:

¿Qué es SQL?

SQL (Structured Query Language) es el idioma que usan las bases de datos relacionales. Piensa en la base de datos como una colección de hojas de cálculo muy potentes (llamadas tablas), y SQL es el lenguaje con el que le dices qué hacer: "tráeme todos los usuarios que se registraron ayer", "guarda este pedido nuevo", "elimina los registros antiguos". Es un lenguaje universal — ya sea que uses PostgreSQL, MySQL o SQLite, las instrucciones básicas son las mismas.

¿Qué es un ORM y por qué existe?

Imagina que hablas español y necesitas comunicarte con alguien que solo habla japonés. Podrías aprender japonés (escribir SQL directamente), o podrías usar un traductor que convierte lo que dices al idioma del otro. Un ORM (Object-Relational Mapper) es exactamente ese traductor: te permite trabajar con objetos Python normales — clases, atributos, listas — y el ORM traduce todo eso a instrucciones SQL detrás de escena.

En lugar de escribir INSERT INTO usuarios (nombre, email) VALUES ('Ada', 'ada@mail.com'), simplemente escribes:

usuario = Usuario(nombre="Ada", email="ada@mail.com")
session.add(usuario)
session.commit()

El ORM genera el SQL por ti. Esto tiene ventajas enormes: tu IDE te avisa si escribes mal un nombre de columna, no necesitas memorizar la sintaxis SQL exacta de cada motor, y — lo más importante — te protege automáticamente contra ataques de SQL Injection (cuando alguien intenta "inyectar" código malicioso a través de los datos de entrada).

¿Qué es SQLAlchemy?

SQLAlchemy es la biblioteca de Python más popular para trabajar con bases de datos. Pero no es solo un ORM — es un sistema de dos capas:

La planta baja (Core) sabe cómo generar SQL y hablar con cualquier base de datos. El primer piso (ORM) te permite escribir código Python puro y deja que Core se encargue de la traducción. Puedes usar ambos pisos según lo que necesites.

¿Y SQLite? ¿Por qué empezar con él?

SQLite es el motor de base de datos relacional más sencillo para empezar: no necesitas instalar nada (ya viene con Python), no requiere un servidor corriendo, y guarda todo en un solo archivo (como app.db) que puedes explorar con SQLite Browser directamente desde tu escritorio. Es perfecto para aprender y desarrollar localmente. Cuando tu proyecto crezca, puedes cambiar a PostgreSQL simplemente cambiando una variable de entorno — sin tocar tu código.

¿Cómo se conecta todo con FastAPI y Pydantic?

La integración funciona como una cadena de tres eslabones que ya conoces por separado:

📥

Pydantic

Valida los datos que llegan del usuario antes de tocar la base de datos.

🔄

SQLAlchemy

Traduce los datos validados a operaciones SQL y los persiste en la BD.

💉

Depends(get_db)

Inyecta la conexión a BD en cada endpoint. Se abre al inicio, se cierra al final.

El usuario envía JSON → Pydantic lo valida → el endpoint recibe los datos limpios y una sesión de BD (gracias a Depends) → SQLAlchemy los guarda → Pydantic formatea la respuesta de vuelta como JSON.

Lo que viene en esta guía: Primero verás la comparación entre escribir SQL a mano y usar un ORM. Luego entenderás las dos capas de SQLAlchemy (Core vs ORM). Después aprenderás a definir modelos con la sintaxis moderna (SQLAlchemy 2.x) y a manejar migraciones con Alembic. Finalmente, integrarás todo en un proyecto FastAPI completo con SQLite. Al terminar, tendrás un proyecto funcional que podrás explorar con SQLite Browser y probar desde Swagger UI.

Módulo 1: ORM vs SQL en Crudo

1.1 ¿Qué hace un ORM?

Un ORM (Object-Relational Mapper) actúa como un traductor entre el mundo de los objetos Python y el mundo de las tablas SQL. En lugar de escribir INSERT INTO usuarios ..., creas un objeto Usuario(nombre="Ada") y el ORM genera el SQL por ti, incluyendo la parametrización segura de valores.

SQL en crudo te da control total sobre la consulta, pero viene con dos riesgos: SQL Injection si interpolas valores directamente, y fragilidad porque los strings de SQL no se validan en tiempo de desarrollo.

1.2 La Diferencia en la Práctica

demo_orm_vs_raw.py 
from sqlalchemy import create_engine, text, String, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, Session

engine = create_engine("sqlite://", echo=True)

class Base(DeclarativeBase):
    pass

class Usuario(Base):
    __tablename__ = "usuarios"
    id: Mapped[int] = mapped_column(primary_key=True)
    nombre: Mapped[str] = mapped_column(String(50))
    email: Mapped[str] = mapped_column(String(255), unique=True)

Base.metadata.create_all(engine)

# ═══ ENFOQUE 1: ORM — el "traductor" trabaja por ti ═══
with Session(engine) as session:
    nuevo = Usuario(nombre="Ada Lovelace", email="ada@example.com")
    session.add(nuevo)
    session.commit()

    stmt = select(Usuario).where(Usuario.nombre == "Ada Lovelace")
    usuario = session.scalars(stmt).first()
    print(f"ORM → {usuario.nombre}, {usuario.email}")

# ═══ ENFOQUE 2: Raw SQL con text() — SEGURO ═══
with engine.connect() as conn:
    conn.execute(
        text("INSERT INTO usuarios (nombre, email) VALUES (:nombre, :email)"),
        {"nombre": "Grace Hopper", "email": "grace@example.com"}
    )
    conn.commit()

# ═══ ❌ ANTI-PATRÓN: SQL con f-string — ¡NUNCA! ═══
# entrada = "'; DROP TABLE usuarios; --"
# query = f"SELECT * FROM usuarios WHERE nombre = '{entrada}'"
# ↑ Esto ejecutaría DROP TABLE. Usa SIEMPRE parámetros.
⚠️ Punto de Atención: SQL Injection. La regla es absoluta: nunca uses f-strings, .format() ni concatenación para construir SQL con datos del usuario. Tanto el ORM como text() con parámetros nombrados (:nombre) manejan esto automáticamente, escapando valores peligrosos.

1.3 ¿Cuándo Elegir Cada Uno?

Criterio ORM Raw SQL / Core
CRUD típico de una API web✅ IdealInnecesario
JOINs complejos o reportesPosible, pero verboso✅ Más natural
Inserción masiva (miles de filas)Más lento (~2x)✅ Más rápido
Protección SQL Injection✅ AutomáticaManual (requiere text())
Autocompletado en el IDE✅ Sí (con type hints)❌ No (son strings)

Recomendación práctica: empieza con ORM para toda la lógica de tu aplicación. Si detectas un cuello de botella con el profiler, baja a Core o raw SQL solo en ese punto.

Módulo 2: SQLAlchemy Core vs ORM — Dos Pisos, Un Edificio

SQLAlchemy no es "un ORM" — es una biblioteca de dos capas. Core (planta baja) es un toolkit de SQL que trabaja con objetos Table, Column y MetaData, ejecuta consultas a través de Engine/Connection, y devuelve objetos Row ligeros. ORM (primer piso) mapea clases Python sobre los Table de Core y agrega gestión de sesiones, relaciones y hooks del ciclo de vida.

En SQLAlchemy 2.x, ambas capas usan la misma función select() — la diferencia es qué le pasas: una clase ORM o un objeto Table.

demo_core_vs_orm.py 
from sqlalchemy import create_engine, select, Table, MetaData, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, Session

engine = create_engine("sqlite://")

class Base(DeclarativeBase):
    pass

class Producto(Base):
    __tablename__ = "productos"
    id: Mapped[int] = mapped_column(primary_key=True)
    nombre: Mapped[str] = mapped_column(String(100))
    precio: Mapped[float]

Base.metadata.create_all(engine)

# ═══ CORE: trabajas con Table y Connection, recibes Rows ═══
metadata = MetaData()
productos_table = Table("productos", metadata, autoload_with=engine)

with engine.connect() as conn:
    stmt = select(productos_table).where(productos_table.c.precio > 100)
    for fila in conn.execute(stmt):
        print(f"Core → {fila.nombre}: ${fila.precio}")

# ═══ ORM: trabajas con la clase y Session, recibes objetos ═══
with Session(engine) as session:
    stmt = select(Producto).where(Producto.precio > 100)
    for producto in session.scalars(stmt):
        print(f"ORM  → {producto.nombre}: ${producto.precio}")

# Observa: el select() es IDÉNTICO en estructura.
# Core recibe un Table, ORM recibe una clase mapeada.
⚠️ Punto de Atención: execute() vs scalars(). session.execute(stmt) devuelve objetos Row (tuplas). session.scalars(stmt) devuelve directamente las instancias del modelo ORM. Usa scalars() el 90% del tiempo cuando trabajas con el ORM.

2.2 ¿Cuándo Usar Cada Capa?

Caso de Uso Capa Recomendada
CRUD de una API web, relaciones entre objetosORM
ETL, inserciones masivas, reportes complejosCore
Aplicación real con ambas necesidadesHíbrido — ORM por defecto, Core para puntos críticos

Verificación de Comprensión

Nivel Medio

SQLAlchemy tiene una arquitectura de dos capas intencional. El ORM usa Core internamente para toda la generación de SQL. En SQLAlchemy 2.x, ambas capas comparten la misma función select(), lo que facilita el enfoque híbrido: ORM para lógica estándar, Core para operaciones de alto rendimiento.

Módulo 3: Modelado de BD y Migraciones con Alembic

3.1 Sintaxis Moderna: DeclarativeBase, Mapped y mapped_column

SQLAlchemy 2.0 introdujo un sistema donde tus type hints de Python definen las columnas de la base de datos. Mapped[int] genera INTEGER NOT NULL. Mapped[Optional[str]] genera un VARCHAR nullable. La antigua función declarative_base() y el uso directo de Column() se consideran legacy (heredados) y han sido reemplazados por este nuevo enfoque — aún funcionan, pero la documentación oficial recomienda la sintaxis moderna para proyectos nuevos.

app/models.py — Modelos con relaciones 
from typing import List, Optional
from datetime import datetime
from sqlalchemy import String, ForeignKey, DateTime, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    pass

class Autor(Base):
    __tablename__ = "autores"

    # Mapped[int] + primary_key → INTEGER NOT NULL PRIMARY KEY
    id: Mapped[int] = mapped_column(primary_key=True)
    nombre: Mapped[str] = mapped_column(String(100))
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    # Mapped[Optional[str]] → VARCHAR, nullable
    bio: Mapped[Optional[str]]
    creado_en: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )

    # Relación uno-a-muchos: un Autor tiene muchos Artículos
    articulos: Mapped[List["Articulo"]] = relationship(
        back_populates="autor", cascade="all, delete-orphan"
    )

class Articulo(Base):
    __tablename__ = "articulos"

    id: Mapped[int] = mapped_column(primary_key=True)
    titulo: Mapped[str] = mapped_column(String(200))
    contenido: Mapped[str]
    autor_id: Mapped[int] = mapped_column(ForeignKey("autores.id"))

    # Mapped["Autor"] (sin List) → relación escalar (un solo objeto)
    autor: Mapped["Autor"] = relationship(back_populates="articulos")

3.2 Referencia Rápida de Tipos

Anotación Python Columna SQL Generada
Mapped[int]INTEGER NOT NULL
Mapped[str]VARCHAR NOT NULL
Mapped[Optional[str]]VARCHAR, nullable
Mapped[bool]BOOLEAN NOT NULL
Mapped[datetime]DATETIME NOT NULL
⚠️ Punto de Atención: Lazy Loading y el problema N+1. Por defecto, las relaciones usan lazy loading: los artículos de un autor no se cargan hasta que accedes a autor.articulos. Si serializas 50 autores con sus artículos, se ejecutan 1 + 50 consultas. La solución: selectinload(Autor.articulos) reduce esto a exactamente 2 consultas.

3.3 Migraciones con Alembic

Alembic es como un "Git para tu esquema de BD": cada cambio genera un script con upgrade() y downgrade().

Terminal — Comandos de Alembic 
# Inicializar Alembic
pip install alembic
alembic init alembic

# Generar migración automática
alembic revision --autogenerate -m "crear tablas autores y articulos"

# Aplicar migraciones pendientes
alembic upgrade head

# Revertir la última
alembic downgrade -1

# CRÍTICO en alembic/env.py para SQLite:
# render_as_batch=True  ← Usa estrategia "copy and move"
⚠️ Punto de Atención: lo que autogenerate NO detecta. Alembic detecta creación/eliminación de tablas y columnas, pero NO detecta renombrados — los interpreta como borrar + crear (¡pierdes datos!). Si renombras algo, edita manualmente el script generado.

Módulo 4: SQLite para Desarrollo Local + Integración FastAPI

4.1 database.py — Engine, Sesiones y get_db

Aquí conectamos con lo que ya sabes de Depends y python-dotenv. El patrón get_db() usa yield para inyectar una sesión por request y garantizar su cierre en el finally.

app/database.py 
import os
from sqlalchemy import create_engine, event, Engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase

# URL configurable — SQLite en dev, PostgreSQL en prod
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./app.db")

# check_same_thread=False es necesario para SQLite con FastAPI.
# SQLite solo permite acceso desde el thread que creó la conexión,
# pero FastAPI despacha endpoints síncronos (def) a un threadpool.
# La seguridad se mantiene creando una sesión nueva por request (get_db).
connect_args = {}
if DATABASE_URL.startswith("sqlite"):
    connect_args["check_same_thread"] = False

engine = create_engine(DATABASE_URL, connect_args=connect_args)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

class Base(DeclarativeBase):
    pass

# ═══ CRÍTICO: Activar foreign keys en SQLite ═══
# Sin esto, puedes insertar registros huérfanos sin error
@event.listens_for(Engine, "connect")
def activar_fk_sqlite(dbapi_conn, connection_record):
    import sqlite3
    if isinstance(dbapi_conn, sqlite3.Connection):
        cursor = dbapi_conn.cursor()
        cursor.execute("PRAGMA foreign_keys=ON")
        cursor.close()

def get_db():
    """Inyecta una sesión por request. yield + finally = limpieza garantizada."""
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

4.3 Schemas Pydantic Separados de Modelos ORM

Esta separación es fundamental. Los modelos SQLAlchemy definen almacenamiento; los schemas Pydantic controlan qué cruza la frontera de la API. El puente entre ambos es ConfigDict(from_attributes=True) — el reemplazo de orm_mode en Pydantic v2.

app/schemas.py 
from pydantic import BaseModel, ConfigDict, field_validator
from datetime import datetime

class ArticuloCreate(BaseModel):
    titulo: str
    contenido: str

    @field_validator("titulo")
    @classmethod
    def titulo_no_vacio(cls, v: str) -> str:
        if len(v.strip()) < 3:
            raise ValueError("El título debe tener al menos 3 caracteres")
        return v.strip()

class ArticuloResponse(BaseModel):
    id: int
    titulo: str
    contenido: str
    publicado: bool
    autor_id: int
    # from_attributes=True reemplaza a orm_mode de Pydantic v1
    model_config = ConfigDict(from_attributes=True)

class AutorBase(BaseModel):
    nombre: str
    email: str

class AutorCreate(AutorBase):
    """Acepta nombre y email al crear. Sin id ni fecha."""
    pass

class AutorResponse(AutorBase):
    id: int
    creado_en: datetime
    articulos: list[ArticuloResponse] = []
    model_config = ConfigDict(from_attributes=True)

4.4 Endpoint con Depends(get_db)

app/routers/autores.py 
from typing import Annotated
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session, selectinload
from sqlalchemy import select
from app.database import get_db
from app import models, schemas

router = APIRouter(prefix="/autores", tags=["autores"])
DBSession = Annotated[Session, Depends(get_db)]

@router.post("/", response_model=schemas.AutorResponse, status_code=201)
def crear_autor(autor: schemas.AutorCreate, db: DBSession):
    """
    Flujo completo:
    1. FastAPI recibe JSON → 2. Pydantic valida →
    3. Depends inyecta sesión → 4. ORM persiste →
    5. response_model serializa con from_attributes=True
    """
    db_autor = models.Autor(nombre=autor.nombre, email=autor.email)
    db.add(db_autor)
    db.commit()
    db.refresh(db_autor)
    return db_autor

@router.get("/{autor_id}", response_model=schemas.AutorResponse)
def obtener_autor(autor_id: int, db: DBSession):
    stmt = (
        select(models.Autor)
        .options(selectinload(models.Autor.articulos))  # ← Evita N+1
        .where(models.Autor.id == autor_id)
    )
    db_autor = db.scalars(stmt).first()
    if db_autor is None:
        raise HTTPException(status_code=404, detail="Autor no encontrado")
    return db_autor

Requerimientos Funcionales

RF1. Modelos SQLAlchemy 2.x

Categoria: id, nombre (único), descripcion (opcional). Tarea: id, titulo, descripcion, completada (default False), prioridad (1-5), fecha_creacion (server_default), categoria_id (FK). Relación uno-a-muchos.

RF3. Endpoints (mínimo)

  • GET /categorias/ → listar con sus tareas (¡usa selectinload!).

Guía de Evaluación: Taller Práctico en Parejas

Modalidad: Trabajo en parejas · Plazo: 1 semana · Entrega: Repositorio Git o carpeta de proyecto con código funcional · Uso de IA: Permitido con documentación obligatoria del proceso · Escala: 0.0 a 5.0 (sistema colombiano)

Política sobre Uso de IA Generativa

Puedes usar cualquier herramienta de IA (ChatGPT, Claude, Copilot, Gemini, etc.) durante el desarrollo. Sin embargo, la evaluación está diseñada para medir tu comprensión real, no la capacidad de la IA. Concretamente:

✅ Permitido

Generar código, depurar errores, pedir explicaciones de conceptos, optimizar consultas, generar tests.

⚠️ Obligatorio

Documentar qué herramienta usaste, qué prompts diste, qué aceptaste/modificaste/rechazaste, y por qué.

❌ Evaluado aparte

La sustentación oral es individual. Debes explicar cualquier línea de tu código y hacer modificaciones en vivo.

Rúbrica de Evaluación — 6 Dimensiones

La nota final se calcula como la suma ponderada de las 6 dimensiones. Las dimensiones 1–4 y 6 son compartidas por la pareja; la dimensión 5 es individual, por lo que cada miembro puede obtener una nota final diferente.

Dimensión Peso ¿Qué evalúa?
1. Funcionalidad y correctitud25%¿Los endpoints CRUD funcionan? ¿Las relaciones operan correctamente?
2. Arquitectura y patrones20%Uso de DI, ORM 2.x, schemas separados, Alembic, estructura del proyecto
3. Calidad del código15%Naming, type hints, linting con Ruff, comentarios pertinentes
4. Testing y robustez15%Tests con pytest + TestClient, manejo de errores, cobertura
5. Sustentación oral ⚡ individual20%Explicar código, predecir comportamiento, modificar en vivo
6. Proceso y documentación5%README, historial Git, documentación de uso de IA
¿Por qué el 20% en sustentación oral? Si obtienes 5.0 en todo pero 0.0 en sustentación, tu nota máxima sería 4.0. Esto garantiza que entender el código es requisito para la excelencia, no solo generarlo.

¿Cómo instalar y usar Ruff? (herramienta gratuita)

Ruff reemplaza a Flake8, isort, Black y pyupgrade en una sola herramienta (open source, escrita en Rust, 10–100x más rápido). Instálalo con pip install ruff y agrega esto en tu pyproject.toml:

[tool.ruff]
line-length = 88
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "I", "W", "N", "UP", "B", "SIM"]
ignore = ["B008"]  # Necesario para Depends() de FastAPI

Ejecuta ruff check . para verificar y ruff format . para formatear automáticamente.

Glosario de Términos

Referencia rápida de los términos técnicos utilizados en este módulo. Los conceptos están agrupados por área temática para facilitar la consulta.

SQL y Bases de Datos Relacionales

SQL (Structured Query Language)

Lenguaje estándar para consultar y manipular bases de datos relacionales. Incluye sentencias como SELECT, INSERT, UPDATE, DELETE y CREATE TABLE.

Raw SQL (SQL en crudo)

Consultas SQL escritas directamente como cadenas de texto, en lugar de generarse a través de un ORM. En SQLAlchemy se escriben con text().

SQL Injection

Vulnerabilidad de seguridad donde un atacante inserta código SQL malicioso a través de datos de entrada no sanitizados. Se previene usando consultas parametrizadas en lugar de interpolación de strings.

DDL (Data Definition Language)

Subconjunto de SQL que define la estructura de la BD: CREATE TABLE, ALTER TABLE, DROP TABLE. Alembic genera DDL automáticamente.

Foreign Key (Clave foránea)

Restricción que vincula una columna con la clave primaria de otra tabla, garantizando integridad referencial. En SQLAlchemy se declara con ForeignKey("tabla.columna").

PRAGMA

Comando exclusivo de SQLite para configurar el comportamiento del motor. Ejemplo: PRAGMA foreign_keys=ON activa la validación de claves foráneas (desactivada por defecto).

Migración

Script que transforma el esquema de la BD de una versión a otra. Contiene funciones upgrade() (aplicar cambio) y downgrade() (revertir). Alembic las gestiona.

WAL (Write-Ahead Logging)

Modo de escritura de SQLite que mejora la concurrencia al permitir lecturas simultáneas con escrituras. No elimina el límite de un solo escritor.

SQLite

Motor de base de datos relacional embebido que almacena todo en un solo archivo. Incluido con Python (módulo sqlite3). Ideal para desarrollo y testing, no recomendado para producción con concurrencia.

Afinidad de tipos (Type Affinity)

Sistema de tipos flexible de SQLite donde las columnas tienen una "afinidad" sugerida (TEXT, NUMERIC, INTEGER, REAL, BLOB) pero no imponen restricciones estrictas de tipo, a diferencia de PostgreSQL o MySQL.

SQLAlchemy — Arquitectura y Componentes

ORM (Object-Relational Mapper)

Capa de abstracción que mapea clases Python a tablas SQL y objetos a filas. Genera SQL automáticamente y gestiona el ciclo de vida de los objetos en memoria.

SQLAlchemy Core

Capa inferior de SQLAlchemy: un toolkit de SQL que trabaja con objetos Table, Column y MetaData. Devuelve objetos Row ligeros sin mapeo a clases.

Engine

Punto de entrada a la base de datos. Gestiona el pool de conexiones y se crea con create_engine(url). Normalmente se crea una sola vez por aplicación.

Session

Objeto que gestiona las operaciones de BD: agrega, modifica y elimina registros dentro de una transacción. Se crea una por request y se cierra al finalizar.

DeclarativeBase

Clase base moderna (SQLAlchemy 2.x) de la que heredan todos los modelos ORM. Reemplaza a la antigua función declarative_base(), que se considera legacy pero sigue funcionando.

Mapped[T] / mapped_column()

Sistema de anotaciones de tipo de SQLAlchemy 2.x. Mapped[int] define el tipo Python y la columna SQL simultáneamente. mapped_column() permite personalización adicional (PK, FK, unique, etc.).

relationship()

Función que declara una relación entre dos modelos ORM. No crea columnas en la BD; define cómo navegar entre objetos relacionados. Se vincula bidireccionalmente con back_populates.

Unit of Work

Patrón de diseño implementado por la Session: acumula cambios pendientes en memoria y los ejecuta todos al hacer commit(), garantizando consistencia transaccional.

Identity Map

Caché interno de la Session que asegura que solo exista un objeto Python por clave primaria en una misma sesión. Evita inconsistencias al modificar el mismo registro desde varios puntos del código.

Patrones, Problemas y Soluciones

Problema N+1

Antipatrón donde una consulta por N registros genera N consultas adicionales para cargar relaciones. Ejemplo: 1 query por 50 autores + 50 queries por sus artículos = 51 queries en lugar de 2.

Lazy Loading

Comportamiento por defecto de las relaciones: los datos relacionados solo se cargan cuando se accede al atributo (ej: autor.articulos). Es la causa del problema N+1.

Eager Loading

Estrategia que carga relaciones anticipadamente en la misma consulta. selectinload() usa una consulta IN separada (ideal para colecciones); joinedload() usa JOIN (ideal para escalares).

Batch Mode (render_as_batch)

Estrategia de Alembic para SQLite: como SQLite no soporta la mayoría de operaciones ALTER TABLE, crea una tabla nueva, copia los datos, elimina la original y renombra.

Consulta parametrizada

Técnica donde los valores de la consulta se envían como parámetros separados al motor de BD (ej: :nombre), en lugar de interpolarse en el string SQL. Es la defensa principal contra SQL Injection.

Integración FastAPI + Pydantic

from_attributes (antes orm_mode)

Opción de Pydantic v2 que permite leer datos desde atributos de objetos (como instancias ORM) en lugar de solo diccionarios. Se configura con model_config = ConfigDict(from_attributes=True).

get_db()

Función generadora canónica que inyecta una sesión de BD por request. Usa yield para entregar la sesión y finally para garantizar su cierre, incluso ante excepciones.

Lifespan

Context manager de FastAPI que reemplaza a los eventos startup/shutdown deprecados. Ejecuta código de inicialización (antes del yield) y limpieza (después) del servidor.

Alembic

Herramienta oficial de migraciones de SQLAlchemy. Compara el estado de los modelos Python con el esquema real de la BD y genera scripts de migración con --autogenerate.
