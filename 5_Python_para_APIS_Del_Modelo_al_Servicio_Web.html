Introducción: ¿Por qué necesitas saber esto?

Imagina que has entrenado un modelo de regresión logística para predecir riesgo crediticio. El modelo funciona perfectamente en tu notebook de Jupyter: le pasas las variables de un solicitante y devuelve una probabilidad de impago. Ahora llega la pregunta real: ¿cómo lo usan los demás?

El equipo de desarrollo del banco necesita llamar a tu modelo desde su aplicación web. El equipo de fraude quiere consultarlo en tiempo real. Y la gerencia quiere un dashboard que muestre predicciones actualizadas. Ninguno de ellos va a abrir tu notebook. La respuesta es exponer tu modelo como una API: un servicio web al que cualquier sistema puede enviarle datos y recibir predicciones.

Pero esto abre nuevas preguntas fundamentales:

🏗️

¿Qué infraestructura necesitas para que tu modelo reciba peticiones HTTP?

📍

¿Cómo defines las rutas (/predict, /health, /stats) de forma clara?

⚡

¿Qué pasa si 500 usuarios consultan el modelo al mismo tiempo? ¿Cómo garantizas que no colapse?

Objetivo del módulo: Llevarte desde los fundamentos de cómo funciona un servidor web hasta la construcción de APIs asíncronas con FastAPI, siempre con ejemplos orientados a estadística y ciencia de datos. Al finalizar, tendrás la capacidad de exponer cualquier modelo estadístico como un servicio web robusto y escalable.

Módulo 1: El Servidor Web y WSGI

1.1 ¿Qué es un servidor web?

Piensa en un restaurante. Cuando un cliente (el navegador o una aplicación) hace un pedido (una petición HTTP), alguien tiene que recibirlo, llevarlo a la cocina y traer el plato de vuelta. Ese "alguien" es el servidor web.

En términos técnicos, un servidor web es un programa que: escucha conexiones entrantes en un puerto (típicamente el 80 o 443), recibe peticiones HTTP (GET, POST, PUT, DELETE…), las delega a tu aplicación Python, y devuelve la respuesta al cliente. Ejemplos de servidores web que encontrarás en producción: Nginx, Apache, Gunicorn, Uvicorn.

1.2 WSGI: El protocolo entre el servidor y tu aplicación

¿Cómo se comunican el servidor web y tu código Python? Necesitan un "idioma común". Ese idioma es WSGI (Web Server Gateway Interface), definido en la PEP 3333.

Analogía: Si el servidor web es el maître que recibe al cliente en el restaurante, WSGI es el protocolo de comunicación entre el maître y la cocina. Define exactamente cómo se pasa el pedido (la petición) y cómo se devuelve el plato (la respuesta).

Cuando usas Flask, en realidad estás trabajando sobre dos bibliotecas fundamentales: Werkzeug, que es el toolkit WSGI que se encarga de toda la comunicación HTTP (parsear peticiones, construir respuestas, manejar headers y cookies), y Jinja2, el motor de templates que permite renderizar páginas HTML dinámicas. Flask envuelve ambas y les agrega routing, configuración y una estructura de aplicación coherente. Para nuestro caso de uso (APIs JSON para modelos estadísticos), Werkzeug hace el trabajo pesado bajo el capó, mientras que Jinja2 queda en segundo plano ya que no renderizamos HTML sino que devolvemos datos estructurados.

¿Qué es Werkzeug exactamente?

Werkzeug (del alemán: "herramienta") es una biblioteca WSGI completa que implementa los detalles de bajo nivel del protocolo HTTP en Python. Cuando Flask recibe una petición, es Werkzeug quien parsea la URL, los headers, el body y los query parameters, construyendo un objeto Request limpio que tu función de vista puede usar. De manera similar, cuando devuelves un jsonify(), Werkzeug construye la respuesta HTTP con los headers correctos. El servidor de desarrollo de Flask (flask run) también es provisto por Werkzeug.

Jinja2, por su parte, es el motor de plantillas que permite generar HTML dinámico. Aunque no lo usaremos directamente en este módulo (nuestras APIs devuelven JSON, no páginas web), es importante saber que existe porque es la otra mitad de la arquitectura de Flask. Cuando ves aplicaciones Flask con render_template(), ahí es donde Jinja2 entra en acción.

* En FastAPI, la equivalencia sería: Starlette = Werkzeug (manejo HTTP), Pydantic = sistema de validación (sin equivalente directo en Flask puro).

Una aplicación WSGI, en su forma más pura, es simplemente una función callable:
Python 
# La aplicación WSGI más simple del mundo
def app(environ, start_response):
    """
    environ: diccionario con toda la info de la petición HTTP
    start_response: función para enviar los headers de respuesta
    """
    status = "200 OK"
    headers = [("Content-Type", "text/plain")]
    start_response(status, headers)
    return [b"Hola desde una app WSGI pura"]

Nadie escribe aplicaciones así en la práctica. Para eso existen los frameworks como Flask, que encapsulan esta complejidad.

1.3 De desarrollo a producción: Gunicorn y Waitress

Flask incluye un servidor de desarrollo (flask run), pero ese servidor no es apto para producción porque procesa una sola petición a la vez. Para producción necesitas un servidor WSGI real:
Terminal 
# Gunicorn (Linux/macOS) — el estándar de la industria
gunicorn --workers 4 --bind 0.0.0.0:8000 app:app

# Waitress (multiplataforma, incluye Windows)
waitress-serve --port=8000 app:app

El parámetro --workers 4 le dice a Gunicorn que lance 4 procesos independientes de tu aplicación. Cada worker puede atender una petición simultáneamente. Es como tener 4 cocinas paralelas en el restaurante.

Módulo 2: Routing Básico y Avanzado

2.1 ¿Qué es el routing?

El routing es el mecanismo que conecta una URL con una función de Python. Cuando alguien visita /predict, el framework necesita saber qué función ejecutar. Es el equivalente a un directorio telefónico: dado un "número" (la URL), te conecta con la "persona" (la función) correcta.

2.2 Routing en Flask

Flask usa el decorador @app.route() para definir rutas:

Flask — routing.py 
from flask import Flask, request, jsonify

app = Flask(__name__)

# Ruta estática simple
@app.route("/health")
def health_check():
    return jsonify({"status": "ok"})

# Variable de ruta: captura un valor dinámico de la URL
@app.route("/dataset/<string:dataset_name>/summary")
def dataset_summary(dataset_name: str):
    return jsonify({"dataset": dataset_name, "rows": 1500})

# Query parameters: valores opcionales después del '?'
# Ejemplo: GET /filter?min_age=25&max_age=60
@app.route("/filter")
def filter_data():
    min_age = request.args.get("min_age", default=0, type=int)
    max_age = request.args.get("max_age", default=120, type=int)
    return jsonify({"min_age": min_age, "max_age": max_age})

2.3 Routing en FastAPI

FastAPI aprovecha el type hinting de Python para definir parámetros de forma declarativa. Observa cómo el mismo routing se simplifica:

FastAPI — routing.py 
from fastapi import FastAPI, Query

app = FastAPI()

# Ruta estática — decorador específico por método HTTP
@app.get("/health")
async def health_check():
    return {"status": "ok"}

# Variable de ruta — el tipo se infiere del type hint
@app.get("/dataset/{dataset_name}/summary")
async def dataset_summary(dataset_name: str):
    return {"dataset": dataset_name, "rows": 1500}

# Query parameters — se definen como argumentos de la función
@app.get("/filter")
async def filter_data(
    min_age: int = Query(default=0, ge=0, description="Edad mínima"),
    max_age: int = Query(default=120, le=150, description="Edad máxima"),
):
    return {"min_age": min_age, "max_age": max_age}

Módulo 3: Flask vs Frameworks Modernos (FastAPI)

3.1 El endpoint /predict en Flask

Veamos cómo se implementa un endpoint de predicción con Flask, el framework veterano (2010). Observa la validación manual y la falta de documentación automática:

app_flask.py 
from flask import Flask, request, jsonify
import numpy as np
import pickle

app = Flask(__name__)

# Cargar modelo pre-entrenado
with open("modelo_credito.pkl", "rb") as f:
    modelo = pickle.load(f)

@app.route("/predict", methods=["POST"])
def predict():
    data = request.get_json()

    # ⚠️ Validación completamente manual
    required = ["income", "debt_ratio", "years_employed"]
    for field in required:
        if field not in data:
            return jsonify({"error": f"Falta el campo: {field}"}), 400

    features = np.array([[data["income"], data["debt_ratio"], data["years_employed"]]])
    probability = modelo.predict_proba(features)[0][1]

    return jsonify({
        "probability": round(float(probability), 4),
        "risk_level": "alto" if probability > 0.5 else "bajo"
    })

3.2 El mismo endpoint en FastAPI

Ahora veamos cómo el mismo endpoint se reimagina con FastAPI. Observa cómo Pydantic maneja la validación y la documentación se genera automáticamente:

app_fastapi.py 
from fastapi import FastAPI
from pydantic import BaseModel, Field
import numpy as np
import pickle

app = FastAPI(
    title="API de Riesgo Crediticio",
    description="Modelo de regresión logística para scoring crediticio",
    version="1.0.0",
)

with open("modelo_credito.pkl", "rb") as f:
    modelo = pickle.load(f)

# ✅ Validación automática vía Pydantic
class CreditRequest(BaseModel):
    income: float = Field(..., gt=0, description="Ingreso mensual en USD")
    debt_ratio: float = Field(..., ge=0, le=1, description="Ratio deuda/ingreso")
    years_employed: int = Field(..., ge=0, description="Años de empleo")

class CreditResponse(BaseModel):
    probability: float
    risk_level: str

@app.post("/predict", response_model=CreditResponse)
async def predict(data: CreditRequest):
    features = np.array([[data.income, data.debt_ratio, data.years_employed]])
    probability = float(modelo.predict_proba(features)[0][1])

    return CreditResponse(
        probability=round(probability, 4),
        risk_level="alto" if probability > 0.5 else "bajo",
    )

3.3 ¿Por qué migró el ecosistema?

No fue una moda. Hay razones técnicas concretas:

🚀 Productividad

FastAPI reduce el código boilerplate. La validación con Pydantic es más robusta en menos líneas.

⚡ Rendimiento

FastAPI con Uvicorn maneja 2x-3x más peticiones/segundo que Flask con Gunicorn para tareas I/O-bound.

📖 Documentación automática

Swagger UI y ReDoc se generan automáticamente. Elimina fricción entre equipos de data science y desarrollo.

🛡️ Type safety

Types hints + Pydantic permiten detectar errores antes de ejecutar el código, directamente en el editor.

¿Y Starlette? Starlette es el framework ASGI sobre el que FastAPI está construido. Es como la relación entre un motor y un coche: Starlette provee el routing, la gestión de peticiones y el soporte WebSocket; FastAPI agrega la capa de validación con Pydantic y la documentación automática. Rara vez usarías Starlette directamente, pero es importante saber que existe.

Módulo 4: Síncrono vs Asíncrono (Profundización)

4.1 I/O-bound vs CPU-bound

Antes de entender async/await, necesitas distinguir dos tipos de tareas:

CPU-bound 🧮

Tareas que mantienen al procesador ocupado calculando.

Ej: entrenar un random forest, multiplicar matrices grandes, bootstrap con 10,000 iteraciones.

I/O-bound ⏳

Tareas donde el procesador espera a que algo externo termine.

Ej: leer un CSV de disco, consultar una base de datos, llamar a otra API, enviar un email.

Punto clave: En una API de predicción, la mayor parte del tiempo se gasta en operaciones I/O, no en cómputo. Cargar datos, leer el modelo del disco, consultar la base de datos para obtener features del usuario… todo eso es espera.

4.2 Modelo síncrono: una fila con un solo cajero

En Flask (síncrono), cada petición bloquea al worker mientras se procesa. El Worker 1 no puede atender la Petición 2 hasta que termine con la 1, aunque el 97% del tiempo esté simplemente esperando a la base de datos:

Petición 1 ──[leer BD: 200ms]──[predecir: 5ms]──[responder]──▶ Petición 2 ──[leer BD: 200ms]──...

4.3 Modelo asíncrono: un cajero muy eficiente

Con async/await, un solo proceso puede manejar muchas peticiones concurrentemente. Mientras la Petición 1 espera la BD, el event loop atiende la 2 y la 3:

Petición 1 ──[leer BD ⏸️ ]─────────────────────[predecir]──[responder]──▶ Petición 2 ────────────────[leer BD ⏸️ ]───────[predecir]──[responder]──▶ Petición 3 ──────────────────────────[leer BD ⏸️ ][predecir][responder]──▶
Analogía: El chef y la olla

Imagina un chef que pone la pasta a hervir (operación I/O: esperar) y mientras hierve, prepara la salsa (otra tarea). No se queda mirando la olla. Eso es async: el event loop "cocina" múltiples platos aprovechando los tiempos de espera.

4.4 Ejemplo comparativo completo

Un endpoint que consulta dos fuentes de datos antes de hacer una predicción. Primero síncrono (Flask), luego asíncrono (FastAPI):

Flask — síncrono (0.3 + 0.2 = 0.5s) 
import time
from flask import Flask, jsonify

app = Flask(__name__)

def obtener_historial_credito(user_id: str) -> dict:
    time.sleep(0.3)  # Simula consulta a BD externa
    return {"score": 720, "defaults": 0}

def obtener_datos_empleo(user_id: str) -> dict:
    time.sleep(0.2)  # Simula consulta a otro servicio
    return {"years": 5, "income": 55000}

@app.route("/evaluate/<user_id>")
def evaluate(user_id: str):
    # ⚠️ Secuencial: 0.3 + 0.2 = 0.5 segundos mínimo
    credito = obtener_historial_credito(user_id)
    empleo = obtener_datos_empleo(user_id)
    risk_score = credito["score"] * 0.6 + empleo["years"] * 10
    return jsonify({"user": user_id, "risk_score": risk_score})
FastAPI — asíncrono (max(0.3, 0.2) = 0.3s) 
import asyncio
from fastapi import FastAPI

app = FastAPI()

async def obtener_historial_credito(user_id: str) -> dict:
    await asyncio.sleep(0.3)  # NO bloquea, cede control
    return {"score": 720, "defaults": 0}

async def obtener_datos_empleo(user_id: str) -> dict:
    await asyncio.sleep(0.2)  # NO bloquea, cede control
    return {"years": 5, "income": 55000}

@app.get("/evaluate/{user_id}")
async def evaluate(user_id: str):
    # ✅ Concurrente: ambas consultas en paralelo
    credito, empleo = await asyncio.gather(
        obtener_historial_credito(user_id),
        obtener_datos_empleo(user_id),
    )
    risk_score = credito["score"] * 0.6 + empleo["years"] * 10
    return {"user": user_id, "risk_score": risk_score}

4.5 Advertencia: async no es magia para todo

async/await brilla en tareas I/O-bound. Para tareas CPU-bound (como entrenar un modelo o calcular bootstrapping), async no ayuda porque el procesador está realmente ocupado. La estrategia correcta es delegar el cómputo a un proceso separado con run_in_executor + ProcessPoolExecutor.

Verificación de Comprensión

Nivel Medio

En el ejemplo comparativo, la versión Flask tarda 0.5s y la FastAPI 0.3s por petición individual. ¿Por qué la ventaja real del modelo asíncrono se amplifica bajo alta concurrencia (ej. 1,000 usuarios simultáneos)?

Ver Respuesta y Retroalimentación ▼
Respuesta Correcta: B

La clave es la concurrencia cooperativa. Con Flask y 4 workers de Gunicorn, la petición #5 debe esperar a que un worker se libere. Con FastAPI, un solo proceso con event loop puede "suspender" cientos de peticiones I/O-bound simultáneamente, atendiendo cada una cuando su operación I/O completa. Con 1,000 usuarios concurrentes, la versión asíncrona puede ser 10x-50x más eficiente en throughput.

Resumen y Mejores Prácticas

Conceptos Clave

Servidor Web y WSGI

Tu aplicación Flask no recibe peticiones directamente. Un servidor WSGI como Gunicorn gestiona los procesos. WSGI es síncrono por diseño; ASGI es su evolución asíncrona.

Routing

Flask usa @app.route() con extracción manual de parámetros. FastAPI usa decoradores por método HTTP y aprovecha type hints para inferir y validar parámetros automáticamente.

Flask vs FastAPI

Flask sigue siendo válido para proyectos simples o legacy. FastAPI es la elección preferida para APIs nuevas en ciencia de datos por su validación integrada, documentación automática y soporte nativo asíncrono.

Síncrono vs Asíncrono

El código síncrono bloquea el worker durante I/O. async/await permite concurrencia durante las esperas. Para CPU-bound, usa run_in_executor con ProcessPoolExecutor.

Do's and Don'ts

✅ Buenas Prácticas

  • Definir modelos Pydantic para todas las entradas y salidas
  • Separar la carga del modelo del endpoint (cargar al iniciar)
  • Incluir un endpoint /health para monitoreo
  • Usar async def para consultas a BD, lectura de archivos o llamadas a otros servicios
  • Versionar tu API (/v1/predict, /v2/predict)
  • Registrar las predicciones (logging) para auditoría

❌ Errores Comunes

  • Usar flask run en producción
  • Cargar el modelo .pkl dentro de la función del endpoint
  • Usar async def para tareas CPU-bound sin executor
  • Ignorar la validación de entrada (un NaN corrompe predicciones)
  • Devolver errores genéricos en vez de códigos HTTP apropiados
  • Exponer info sensible del modelo sin autenticación
