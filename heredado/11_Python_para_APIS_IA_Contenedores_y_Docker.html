1. Introducción y objetivos de aprendizaje

En las semanas previas se construyó una API estadística con FastAPI, se validaron sus entradas con Pydantic, se inyectaron dependencias mediante Depends, se persistieron observaciones con SQLAlchemy y se redactó una suite de pruebas con pytest. La pregunta natural que aparece a continuación es: ¿cómo se entrega ese servicio a otra máquina —el servidor del laboratorio, una máquina virtual en la nube, el computador de un compañero— sin que el ajuste de un modelo de regresión devuelva resultados distintos por culpa de una versión diferente de NumPy?

La respuesta moderna es la contenerización: el código, sus dependencias, el intérprete de Python y hasta la configuración del sistema operativo se empaquetan en una imagen —un artefacto inmutable— y esa imagen se ejecuta en un contenedor. El estándar de facto para construir imágenes y ejecutar contenedores se llama Docker. La lección 3 precisa la diferencia entre ambos términos.

Objetivo de aprendizaje Al finalizar esta unidad, el estudiante:
  • distingue contenedores de máquinas virtuales;
  • redacta un Dockerfile sintáctica y semánticamente correcto sobre la imagen base python:3.11.9-slim-bookworm;
  • controla qué archivos se envían al motor de Docker mediante el contexto de construcción y el archivo .dockerignore;
  • aplica multi-stage builds para reducir el tamaño y la superficie de ataque de la imagen final;
  • empaqueta una API FastAPI que sirve un modelo estadístico sencillo y comprueba que se comporta igual dentro y fuera del contenedor.

2. Del entorno virtual al contenedor

Antes de introducir los contenedores conviene revisar por qué no bastan los instrumentos vistos en semanas anteriores. La progresión natural es:

  1. Entorno virtual de Python (venv). Aísla las dependencias a nivel de paquete Python: garantiza que numpy==1.26.4 instalado para el proyecto no choque con la versión del sistema.
  2. Archivo requirements.txt. Documenta qué paquetes y qué versiones se necesitan. Permite reconstruir el entorno virtual con pip install -r requirements.txt.
  3. Fijación de las semillas aleatorias (y declaración de la versión del intérprete, por ejemplo en un archivo .python-version). Garantiza que dos ejecuciones del mismo análisis produzcan los mismos números en la misma máquina.

Estas herramientas resuelven la reproducibilidad dentro de una misma máquina, pero dejan abiertas tres preguntas críticas:

Pregunta ¿Lo resuelve venv + requirements.txt?
¿Qué versión del intérprete de Python se está usando? Solo en parte. Un archivo .python-version o una prueba pueden declarar y verificar la versión, pero venv usa el Python que ya tenga instalado cada máquina: no lo provee.
¿Qué bibliotecas del sistema operativo están disponibles (libstdc++, libopenblas, tzdata)? No. Dependen de la distribución y de los paquetes instalados en cada computador.
¿En qué orden y con qué configuración deben arrancar los procesos (Uvicorn, una base de datos, una caché)? No. Es responsabilidad del despliegue, no del entorno virtual.

Un contenedor responde las dos primeras preguntas: la imagen incluye el intérprete y las bibliotecas del sistema. La tercera —el orden y la configuración con que arrancan varios procesos— corresponde a un orquestador como Docker Compose, que esta unidad solo menciona.

El contenedor extiende la idea del entorno virtual al sistema operativo completo: en lugar de aislar solo paquetes Python, aísla también la versión del intérprete, las bibliotecas del sistema y los procesos. La analogía más útil para el lector estadístico es la siguiente:

Analogía conceptual Un venv es a los paquetes de Python lo que un contenedor es al sistema operativo. Si el archivo requirements.txt describe cómo reconstruir un entorno virtual, el Dockerfile describe cómo reconstruir una máquina completa, capa por capa.

El paralelismo es útil, aunque no exacto (un entorno virtual se puede modificar; una imagen, no), y conviene tenerlo presente durante el resto de la unidad:

Concepto en el entorno virtual Concepto análogo en Docker
python -m venv .venv (crear el entorno) docker build (crear la imagen)
source .venv/bin/activate (activar) docker run (lanzar un contenedor)
requirements.txt (declaración de dependencias) Dockerfile (declaración de la imagen)
Un entorno virtual existente (carpeta .venv/) Una imagen construida (artefacto inmutable, identificado por un hash)
Una sesión de terminal con el entorno activado Un contenedor en ejecución (instancia mutable de una imagen)
Idea central Una imagen es una plantilla inmutable. Un contenedor es una instancia en ejecución de esa plantilla. La relación es la misma que existe entre una clase y una instancia en Python, o entre una distribución y una muestra extraída de ella.

3. Contenedores vs Máquinas Virtuales

Tanto las máquinas virtuales (VMs) como los contenedores buscan el mismo objetivo: ejecutar varias aplicaciones aisladas en un mismo computador físico. La diferencia está en dónde se traza la línea de aislamiento.

4.2 Mecanismo técnico del aislamiento

El kernel de Linux ofrece dos primitivas que Docker explota directamente:

  • Namespaces. Aíslan la vista que un proceso tiene del sistema: PID (procesos), MNT (puntos de montaje), NET (interfaces de red), UTS (nombre de host), IPC (memoria compartida) y USER (mapeo de identificadores de usuario). Cada contenedor obtiene su propia vista y no puede observar los procesos de otro contenedor o del anfitrión.
  • Control groups (cgroups). Limitan los recursos que un grupo de procesos puede consumir: CPU, memoria, E/S de disco y número de procesos. Docker no aplica límites por defecto: hay que pedirlos (--memory, --cpus). Sin ellos, un único contenedor podría agotar la memoria del servidor.
Implicación para macOS y Windows Los namespaces y los cgroups son construcciones del kernel de Linux. En macOS y Windows, Docker Desktop ejecuta una pequeña máquina virtual Linux por debajo, y los contenedores corren dentro de esa VM. El estudiante percibe la misma interfaz, pero conviene saber que en esos sistemas hay un nivel adicional de indirección. Además, un Mac con procesador Apple (arm64) construye imágenes arm64, mientras que la mayoría de los servidores en la nube son amd64: una imagen sirve para una arquitectura. Si se construye en un Mac con procesador Apple una imagen que se va a ejecutar en un servidor x86, se indica con docker build --platform linux/amd64 ….

4.4 ¿Cuándo elegir una u otra?

La elección depende del objetivo:

  • Si se necesita ejecutar Windows dentro de Linux o aislar máquinas de organizaciones distintas en una misma nube, una VM es lo apropiado.
  • Si se necesita empaquetar y desplegar una API estadística junto a sus dependencias en cualquier máquina del laboratorio, o si se quiere reproducir exactamente el experimento de un compañero, un contenedor es la opción natural.
Convivencia, no exclusión En la práctica, los servidores en la nube ejecutan máquinas virtuales que, a su vez, hospedan decenas de contenedores. Las dos tecnologías coexisten en capas distintas de la pila de despliegue.

4. ¿Por qué Docker ahora?

La contenerización como concepto no es nueva: el aislamiento basado en namespaces aparece en Linux a comienzos de los 2000 y FreeBSD jails es aún más antiguo. Lo que Docker introduce, a partir de 2013, es una experiencia de desarrollo ergonómica: un formato de imagen estandarizado, un registro público (Docker Hub) y una sintaxis declarativa (Dockerfile) que cualquier desarrollador puede leer en pocos minutos.

5.1 Cinco ventajas para el ciclo de desarrollo de una API estadística

  1. Reproducibilidad fuerte. La frase "funciona en mi máquina" deja de ser una excusa: la imagen es la máquina. Una imagen construida en 2026 y conservada (en un registro, o con docker save) puede volver a ejecutarse en 2030 con exactamente el mismo software. Reconstruirla desde el Dockerfile es otra cosa: exige que sigan disponibles la imagen base y los paquetes de PyPI, y en otra CPU o arquitectura las últimas cifras decimales de un cálculo en coma flotante pueden diferir.
  2. Paridad entre desarrollo, pruebas y producción. La misma imagen que se ejecuta en un equipo de desarrollo opera sin cambios en el servidor de integración continua y en el servidor de producción. Las diferencias de configuración entre entornos —una causa frecuente de fallos al desplegar— se reducen mucho.
  3. Despliegue como composición de piezas. Los orquestadores modernos (Docker Compose, Kubernetes) toman varias imágenes —una API, una base de datos PostgreSQL, una caché Redis— y las orquestan como un sistema coherente.
  4. Aislamiento de experimentos. Es habitual en estadística comparar bibliotecas: scikit-learn 1.4 contra 1.5, statsmodels contra PyMC. Cada experimento puede vivir en una imagen distinta sin contaminar el sistema operativo del investigador.
  5. Empaquetamiento de modelos entrenados. Un modelo de regresión, un GLM o una red neuronal pueden incluirse como un archivo dentro de la imagen y servirse a través de FastAPI, todo en una sola unidad versionada.

5.2 Encaje en el ciclo de desarrollo moderno

Un flujo típico para una API estadística contenerizada sigue estos pasos:

  1. Se escribe el código de la API junto con un Dockerfile.
  2. Cada git push dispara una integración continua (un servidor que ejecuta las pruebas de forma automática en cada cambio) que ejecuta la suite de pytest sobre el código y, si pasa, ejecuta docker build.
  3. Si las pruebas pasan, la imagen se etiqueta con el hash del commit y se publica a un registro privado.
  4. El servidor de producción descarga la imagen y la ejecuta: es, byte a byte, la imagen que se construyó en el flujo.
Conexión con la Semana 10 El capítulo previo defendió la reproducibilidad sin Docker como una higiene mínima: fijar versiones, semillas y configuración. Docker no reemplaza esa higiene; la amplifica. Una imagen construida sobre dependencias flotantes seguirá siendo no determinista. Toda buena práctica de la semana 10 sigue vigente; lo que Docker añade es lo que aquella no podía fijar —el sistema operativo y sus bibliotecas, por ejemplo BLAS— y la unidad de empaquetamiento.

5.3 ¿Qué Docker no resuelve?

  • No corrige errores de modelado: una regresión mal especificada empaquetada en una imagen sigue mal especificada.
  • No reemplaza una suite de pruebas: el contenedor garantiza el entorno, pero la lógica se sigue verificando con pytest.
  • No reemplaza la documentación: el Dockerfile describe cómo se construye la imagen; el README sigue siendo necesario para describir qué hace la API.
  • No congela lo que no se fijó: las dependencias transitivas sin fijar, las etiquetas mutables y un apt-get sin versiones producen imágenes distintas en cada construcción.

¿Por qué ahora? Porque ya existe algo que empaquetar: una API con validación, persistencia y pruebas (semanas 4 a 10), y la semana 12 la despliega en internet.

5. Estructura de un Dockerfile

Un Dockerfile es un archivo de texto plano, sin extensión, que contiene una secuencia ordenada de instrucciones. Las instrucciones que cambian el contenido de la imagen (FROM, COPY, RUN) producen cada una una capa; las demás solo registran metadatos (se precisa en 6.3). La metáfora útil es la de un manual de cocina: cada paso recibe el resultado del anterior y agrega algo encima.

6.1 Anatomía mínima

# Dockerfile — versión didáctica mínima
FROM python:3.11.9-slim-bookworm

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Cada palabra mayúscula es una instrucción reconocida por el motor de Docker. A continuación se describen las más importantes.

6.2 Instrucciones esenciales

Instrucción Propósito Ejemplo
FROM Declara la imagen base de la que se parte. Es la primera instrucción (solo ARG puede precederla). FROM python:3.11.9-slim-bookworm
WORKDIR Establece el directorio de trabajo dentro de la imagen. Si no existe, se crea. WORKDIR /app
COPY Copia archivos desde el contexto de construcción (lección 8) a la imagen. COPY requirements.txt .
RUN Ejecuta una orden en una capa nueva durante la construcción. RUN pip install -r requirements.txt
ENV Define una variable de entorno que persiste en imagen y contenedor. ENV PYTHONUNBUFFERED=1
ARG Define una variable disponible solo durante la construcción. ARG APP_VERSION=0.1.0
EXPOSE Documenta los puertos que la aplicación escucha. Es informativo: no publica puertos por sí solo. EXPOSE 8000
USER Cambia el usuario que ejecutará las instrucciones siguientes y el proceso del contenedor. USER appuser
CMD Define el comando por defecto del contenedor. Suele escribirse en forma exec (lista JSON). CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]
ENTRYPOINT Fija el ejecutable del contenedor. Combinado con CMD permite pasar argumentos por línea de comandos. ENTRYPOINT ["uvicorn"]
HEALTHCHECK Define un sondeo que Docker repite cada cierto tiempo para marcar el contenedor como healthy o unhealthy. No lo reinicia por sí solo. HEALTHCHECK CMD python -c "..."
Del contenedor al navegador: EXPOSE, -p y --host EXPOSE 8000 solo documenta el puerto: no lo abre. Para llegar a la API desde el anfitrión hay que publicarlo al lanzar el contenedor, con docker run -p 8000:8000 (formato ANFITRIÓN:CONTENEDOR). Y dentro del contenedor, Uvicorn debe escuchar en todas las interfaces: por defecto lo hace solo en 127.0.0.1, es decir, únicamente para sí mismo, y el tráfico que entra por -p no llega hasta ahí. De ahí el --host 0.0.0.0 del CMD.

6.3 La imagen como una pila de capas

Las instrucciones FROM, COPY, RUN y ADD (y WORKDIR, cuando crea el directorio) añaden una capa nueva e inmutable con contenido; ENV, USER, EXPOSE y CMD solo anotan metadatos. La imagen final es la superposición de las capas, y al ejecutarla Docker añade encima una capa delgada de lectura y escritura propia del contenedor. Una imagen construida con el Dockerfile anterior tiene una estructura conceptual como esta:

CAPA 1 Imagen base python:3.11.9-slim-bookworm
CAPA 2 WORKDIR /app
CAPA 3 COPY requirements.txt .
CAPA 4 RUN pip install --no-cache-dir -r requirements.txt
CAPA 5 COPY app/ ./app/
METADATOS EXPOSE 8000 · CMD [...] (no añaden contenido)
CONTENEDOR Capa de lectura y escritura: nace al ejecutar y se descarta con docker rm

Figura 6.1 — Las capas de la imagen son de solo lectura y se comparten entre imágenes; el contenedor añade encima la suya, que es donde escribe.

Conexión con requirements.txt Cada línea de requirements.txt describe un paquete Python; cada instrucción del Dockerfile describe una transformación del sistema de archivos. Ambas son listas declarativas y ordenadas que producen un entorno determinado a partir de un punto de partida conocido. La diferencia es de alcance: requirements.txt opera sobre el árbol de paquetes Python; el Dockerfile opera sobre la pila completa.

6.4 Caché de capas: una optimización crítica

Docker calcula un hash de las entradas de cada instrucción: el contenido de los archivos copiados, los argumentos de RUN y el estado de la capa anterior. Si el hash coincide con uno ya almacenado, reutiliza la capa en lugar de reconstruirla.

De ahí surge una regla de oro: se ordenan las instrucciones por estabilidad decreciente. Las instrucciones que cambian rara vez van arriba; las que cambian con frecuencia van abajo. Por eso el patrón copiar primero requirements.txt, instalar dependencias y luego copiar el código es estándar:

  • Las dependencias cambian semanas o meses; el código cambia varias veces al día.
  • Si el código cambia pero requirements.txt no, las capas 3 y 4 se toman de la caché y la reconstrucción tarda segundos en lugar de minutos.
# Fragmento de un Dockerfile (sin FROM ni WORKDIR)

# Anti-patrón: una sola instrucción COPY rompe la caché en cada cambio
COPY . .
RUN pip install --no-cache-dir -r requirements.txt

# Patrón correcto: dependencias primero, código después
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app/ ./app/

6.5 Forma exec vs forma shell

Las instrucciones CMD, ENTRYPOINT y RUN aceptan dos sintaxis:

  • Forma exec (lista JSON): CMD ["uvicorn", "app.main:app"]. El proceso se ejecuta sin shell intermedio. Es la forma recomendada porque permite que el proceso reciba directamente las señales del sistema operativo (SIGTERM, SIGINT) y termine limpiamente.
  • Forma shell: CMD uvicorn app.main:app. El motor envuelve la orden en /bin/sh -c. La señal SIGTERM llega al shell y no al proceso de Python, lo que puede impedir un cierre limpio.
Cierre limpio Una API estadística que no responde a SIGTERM deja peticiones a medias y conexiones de base de datos abiertas. Al detener un contenedor, Docker envía SIGTERM y, si el proceso no termina en 10 segundos, lo mata con SIGKILL: con la forma exec, docker stop de una API Uvicorn tardó menos de un segundo; con la forma shell, los 10 segundos completos. Se recomienda usar la forma exec en producción.
Cuando el puerto lo decide la plataforma La forma exec no expande variables de entorno: "--port", "$PORT" pasaría a Uvicorn la cadena literal $PORT. Plataformas como Render o Railway (semana 12) asignan el puerto en esa variable, así que allí el CMD se escribe con un shell que la lea y con exec, para que Uvicorn siga siendo el proceso principal y reciba SIGTERM: 
CMD ["sh", "-c", "exec uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]
El mismo patrón sirve para ejecutar una orden antes de arrancar, por ejemplo las migraciones de Alembic: sh -c "alembic upgrade head && exec uvicorn …".

7.2 ¿Por qué esta variante y no otra?

El repositorio python ofrece varias variantes. Su elección obedece a un compromiso entre tamaño, compatibilidad y seguridad:

Variante Tamaño aproximado Cuándo se elige
python:3.11.9 (Debian completa) ≈ 1 GB Útil cuando se requieren muchas bibliotecas del sistema; ineficiente en producción.

python:3.11.9-alpine ≈ 50 MB La más pequeña, pero usa musl en lugar de glibc: algunas bibliotecas científicas (scikit-learn, PyTorch) no publican wheels —paquetes ya compilados que pip instala sin compilar— para musl y obligan a compilar, alargando los tiempos de construcción, y las diferencias de libc pueden causar fallos sutiles.

Recomendación Para una API estadística que dependa del ecosistema científico de Python (NumPy, SciPy, pandas, scikit-learn, statsmodels), slim-bookworm es el equilibrio práctico. Las wheels oficiales de PyPI son compatibles y el tamaño final es razonable.

7.3 ¿Qué incluye y qué no incluye?

La variante slim incluye:

  • El intérprete CPython 3.11.9 con su biblioteca estándar.
  • pip, setuptools y un pequeño conjunto de utilidades de Debian (apt-get, dpkg).
  • Un puñado de librerías compartidas necesarias para arrancar Python.

Y deja fuera, entre otras cosas:

  • Compiladores (gcc, g++, build-essential).
  • Cabeceras de desarrollo (python3-dev, libssl-dev).
  • Herramientas comunes como git, curl, wget o vim.
Cuando una dependencia exige compilar Si una biblioteca científica no provee wheel para Linux (x86_64 o arm64) y requiere compilación (caso poco frecuente con NumPy, SciPy o scikit-learn, pero posible con paquetes menos comunes), conviene instalar build-essential en una etapa temporal (builder) y descartarla en la imagen final. Este patrón se desarrolla en la lección 9.

7.4 Fijación explícita de la versión

Existe la tentación de escribir FROM python:3.11-slim. Esto produce una imagen reproducible hoy, pero no mañana: la etiqueta flotante 3.11 apunta al último parche disponible. Una reconstrucción meses después puede traer 3.11.10 o 3.11.12 y, con ello, cambios sutiles en el intérprete.

Para una API estadística, donde la reproducibilidad numérica importa, se prefiere la versión completa:

# Ejemplos alternativos: en un Dockerfile real se escribe UNA sola línea FROM.

# No recomendado: la versión flota.
FROM python:3.11-slim

# Recomendado: versión exacta.
FROM python:3.11.9-slim-bookworm

# Reproducibilidad máxima: hash criptográfico de la imagen (el de abajo es ilustrativo).
# El hash se obtiene con: docker pull python:3.11.9-slim-bookworm
# y luego: docker inspect python:3.11.9-slim-bookworm --format='{{index .RepoDigests 0}}'
# (el resultado tiene la forma python@sha256:…; se pega tras la etiqueta, como abajo)
FROM python:3.11.9-slim-bookworm@sha256:abc123...def

Fijar el hash digest (@sha256:...) es la forma más estricta de reproducibilidad: garantiza que el contenido de la imagen base es bit a bit el mismo, incluso si la etiqueta cambia.

Fijar no es congelar: una imagen fijada no recibe los parches de seguridad de Debian ni de CPython que aparecen después. El curso la fija para que todos trabajen con la misma base y sus resultados sean comparables; en un proyecto que se mantiene, la versión se sube de forma deliberada cada cierto tiempo, con las pruebas en verde y tras escanear la imagen (apartado 12.2).

7. Contexto de construcción

Al ejecutar docker build . el cliente de Docker (la orden docker) no construye la imagen por sí mismo: empaqueta el directorio actual y lo envía al daemon, el proceso del motor de Docker que efectivamente la construye (normalmente en la misma máquina). Ese paquete recibe el nombre de contexto de construcción.

8.1 Definición precisa

El contexto es el árbol de archivos enraizado en el directorio que se pasa como último argumento a docker build. La instrucción COPY solo puede leer archivos que estén dentro de ese árbol; no puede escapar hacia rutas absolutas del anfitrión ni navegar fuera con ...

cd regresion-api
docker build -t regresion-api:0.1.0 .

La salida de BuildKit, abreviada, se parece a esta:

[+] Building 12.4s (10/10) FINISHED

 => [internal] load build definition from Dockerfile             0.0s
 => [1/5] FROM docker.io/library/python:3.11.9-slim-bookworm     2.1s
 => [2/5] WORKDIR /app                                            0.0s
 => [3/5] COPY requirements.txt .                                 0.0s

La línea transferring context indica que se enviaron 482 KB al daemon. En proyectos descuidados ese número puede crecer hasta varios gigabytes.

8.2 El archivo .dockerignore

El mecanismo principal para controlar qué se envía al daemon es el archivo .dockerignore, situado en la raíz del contexto. Su sintaxis se parece a la de .gitignore, con una diferencia que importa: los patrones parten de la raíz del contexto, así que __pycache__ a secas solo excluye la carpeta de la raíz; para excluir a cualquier profundidad se escribe **/__pycache__. 8.3 ¿Por qué importa tanto este archivo?

  1. Velocidad. Cada byte sobrante se transfiere y se sube por la red a registros remotos.
  2. Seguridad. Sin .dockerignore, un archivo .env con credenciales puede acabar dentro de la imagen y publicarse al registro. La regla práctica es: todo lo que no debería copiarse, debe ignorarse explícitamente.
  3. Caché. Cuando la instrucción COPY . . incluye archivos volátiles (logs, cachés de tests), su hash cambia constantemente y la caché se invalida en cada construcción, alargando los tiempos.
Riesgo de fuga de credenciales Un .env con la contraseña de la base de datos copiado a una imagen queda registrado en una capa permanente. Aunque luego se elimine con un RUN rm, la capa anterior sigue conservando el archivo. La única protección efectiva es no copiarlo nunca: para eso sirven .dockerignore y, cuando un secreto hace falta durante la construcción, RUN --mount=type=secret (nunca ARG ni ENV, que quedan registrados en la imagen). En ejecución, las credenciales se inyectan como variables de entorno (semana 8).

8.4 Verificación práctica

Para inspeccionar exactamente qué archivos llegarían al daemon antes de construir la imagen, puede prepararse un contexto de prueba:

docker build --no-cache --progress=plain --output type=cacheonly -f - . <<'EOF'
FROM python:3.11.9-slim-bookworm
COPY . /ctx
RUN find /ctx -type f | sort
EOF

Esta orden construye una imagen desechable (con --output type=cacheonly no deja ninguna) que solo copia el contexto y, en el registro de la construcción, lista cada archivo que llegó a ella: el contexto real, con el .dockerignore aplicado tal como lo aplica Docker. (tar --exclude-from no sirve para esto: compara los patrones a cualquier profundidad y no entiende ** ni !, así que puede mostrar como excluidos archivos que Docker sí enviaría.) Es una herramienta valiosa para auditar contextos sospechosamente grandes.

8. Multi-stage builds

Una primera versión de un Dockerfile suele mezclar dos preocupaciones distintas: construir el software (compilar, instalar herramientas de desarrollo, ejecutar pruebas) y ejecutarlo (servir peticiones HTTP). El resultado contiene compiladores, cabeceras y artefactos intermedios que en producción son superfluos y, peor aún, agrandan la superficie de ataque.

Los multi-stage builds, disponibles desde Docker 17.05, resuelven el problema dividiendo el Dockerfile en etapas. Cada etapa empieza con una nueva instrucción FROM y puede copiar selectivamente artefactos de las anteriores con COPY --from=....

9.1 Esquema general

# Etapa 1: builder — todo lo que solo hace falta durante la construcción
FROM python:3.11.9-slim-bookworm AS builder
# ... instalar compiladores, descargar dependencias, compilar wheels ...

# Etapa 2: runtime — la imagen final que se entrega a producción
FROM python:3.11.9-slim-bookworm AS runtime
COPY --from=builder /opt/venv /opt/venv
# ... copiar el código y arrancar la aplicación ...

La imagen final, identificada por la etapa con la última instrucción FROM (o por una etapa nombrada con --target), contiene la imagen base de esa etapa más lo que se copió explícitamente. Las herramientas de la etapa builder no aparecen en el resultado.

9.2 Ventajas concretas

  1. Reducción de tamaño. Un Dockerfile mono-etapa que necesita compilar y conserva el compilador puede pesar unos 750 MB; el mismo proyecto en multi-stage queda en unos 450 MB (−40 %). Si ninguna dependencia necesita compilar, un mono-etapa sin compiladores pesa lo mismo: el multi-stage no adelgaza más, permite compilar sin cargar con el compilador.
  2. Separación de dependencias. Las dependencias de construcción (compiladores, cabeceras) viven solo en el builder; las de ejecución (la API y sus paquetes Python) viven en runtime.
  3. Superficie de ataque más pequeña. Sin compiladores ni cabeceras de desarrollo en producción (y, con un USER sin privilegios, sin poder instalar nada con apt), un atacante que logre ejecutar código tiene menos herramientas para escalar privilegios.
  4. Reutilización de etapas. Una misma etapa builder puede alimentar varias imágenes finales (API, worker, job batch) sin duplicar la instalación de dependencias.
  5. Construcción paralela. Etapas independientes pueden construirse en paralelo cuando se utiliza el motor BuildKit.

9.3 Patrón recomendado para Python

El patrón más común instala las dependencias en un entorno virtual dentro del builder y copia ese entorno virtual completo a la etapa de runtime. Así se evita reinstalar paquetes en la imagen final.

# Dockerfile: patrón multietapa recomendado para Python

# ============================================================
# Etapa 1 — builder
# ============================================================
FROM python:3.11.9-slim-bookworm AS builder

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

# build-essential solo se necesita para compilar wheels que no
# lleguen precompiladas; se descarta junto con esta etapa.
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*

# Entorno virtual aislado en /opt/venv. Se puede copiar a la etapa runtime
# porque ambas etapas usan la misma imagen base y la misma ruta.
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

WORKDIR /build
COPY requirements.txt .
RUN pip install -r requirements.txt

# ============================================================
# Etapa 2 — runtime
# ============================================================
FROM python:3.11.9-slim-bookworm AS runtime

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"

# Usuario no privilegiado para ejecutar la aplicación.
RUN groupadd --system --gid 1001 appgroup \
 && useradd --uid 1001 --gid appgroup --create-home appuser

WORKDIR /app

# Solo se trae el entorno virtual: ni compiladores ni cachés de apt.
COPY --from=builder /opt/venv /opt/venv

# Código de la aplicación: propiedad de root y de solo lectura para appuser.
COPY app/ ./app/

USER appuser

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

10.2 Modelo entrenado fuera de línea

Para mantener el ejemplo autocontenido, el modelo se reduce a una regresión lineal univariada con coeficientes precalculados. En un proyecto real este archivo lo produciría un script de entrenamiento separado (idealmente versionado). El archivo, app/modelo.json, guarda los coeficientes de y = 2.3·x + 1.7 y el dominio de entrenamiento; un JSON no admite comentarios, así que esa explicación va aquí y no dentro del archivo:

{
    "version": "0.1.0",
    "intercepto": 1.7,
    "pendiente": 2.3,
    "x_min": -10.0,
    "x_max": 10.0
}

10.3 Carga del modelo (app/modelo.py)

# app/modelo.py
from __future__ import annotations

import json
from dataclasses import dataclass
from functools import lru_cache
from pathlib import Path

RUTA_MODELO = Path(__file__).parent / "modelo.json"


@dataclass(frozen=True)
class ModeloRegresion:
    """Regresión lineal simple con coeficientes inmutables."""
    version: str
    intercepto: float
    pendiente: float
    x_min: float
    x_max: float

    def predecir(self, x: float) -> float:
        return self.intercepto + self.pendiente * x


@lru_cache(maxsize=1)
def cargar_modelo() -> ModeloRegresion:
    """Carga el modelo desde disco una sola vez por proceso."""
    with RUTA_MODELO.open("r", encoding="utf-8") as f:
        datos = json.load(f)
    return ModeloRegresion(**datos)

La función cargar_modelo, decorada con @lru_cache, se integra con el patrón de inyección de dependencias visto en la semana 8: actúa como un proveedor reutilizable (provider), costoso la primera vez y barato después.

10.4 Esquemas Pydantic (app/schemas.py)

# app/schemas.py
from pydantic import BaseModel, Field, field_validator


class EntradaPrediccion(BaseModel):
    x: float = Field(..., description="Variable explicativa")

    @field_validator("x")
    @classmethod
    def validar_rango(cls, valor: float) -> float:
        if not -1000.0 <= valor <= 1000.0:
            raise ValueError("x debe pertenecer a [-1000, 1000]")
        return valor


class SalidaPrediccion(BaseModel):
    y_hat: float = Field(..., description="Predicción del modelo")
    extrapolado: bool = Field(
        ...,
        description="True si x cae fuera del rango observado en entrenamiento",
    )
    version_modelo: str = Field(
        ...,
        description="Versión semántica del modelo servido",
    )

La validación con @field_validator y la respuesta automática HTTP 422 frente a cargas útiles inválidas son herencia directa de las semanas 4, 6 y 7 (Pydantic y FastAPI). La pieza nueva es que el contenedor las preserva exactamente igual al desplegarse; el apartado 10.11 lo comprueba.

Dos rangos, dos propósitos Conviene distinguir los dos rangos que aparecen sobre x:
  • El rango de validación de Pydantic ([-1000, 1000]) protege a la API de entradas absurdas o mal formadas; al violarlo, la API devuelve 422 Unprocessable Entity.
  • El rango del modelo ([x_min, x_max] = [-10, 10]) describe el dominio en el que se entrenó la regresión. Una x = 50 es perfectamente válida como tipo numérico, pero implica una extrapolación; la API responde 200 con extrapolado: true para que el cliente quede advertido.
Confundir ambos rangos es un error frecuente: la primera es responsabilidad de FastAPI/Pydantic; la segunda, del estadístico que entrenó el modelo.

10.5 Aplicación FastAPI (app/main.py)

# app/main.py
from fastapi import FastAPI, Depends

from app.modelo import ModeloRegresion, cargar_modelo
from app.schemas import EntradaPrediccion, SalidaPrediccion

app = FastAPI(
    title="regresion-api",
    version="0.1.0",
    description="API mínima que sirve un modelo de regresión lineal simple.",
)


@app.get("/health", status_code=200)
def health() -> dict[str, str]:
    """Sondeo de vida: responde 200 mientras el proceso atienda peticiones."""
    return {"status": "ok"}


@app.post("/predicciones", response_model=SalidaPrediccion)
def predecir(
    entrada: EntradaPrediccion,
    modelo: ModeloRegresion = Depends(cargar_modelo),
) -> SalidaPrediccion:
    y_hat = modelo.predecir(entrada.x)
    return SalidaPrediccion(
        y_hat=y_hat,
        extrapolado=not (modelo.x_min <= entrada.x <= modelo.x_max),
        version_modelo=modelo.version,
    )

COPY --from=builder /opt/venv /opt/venv

# Código de la aplicación: propiedad de root y de solo lectura para appuser.
COPY app/ ./app/

USER appuser

EXPOSE 8000

# Sondeo de salud: Docker consulta /health y marca el contenedor como healthy o unhealthy.
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=3)"

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
Lo nuevo en este Dockerfile
  • Usuario no privilegiado. groupadd y useradd crean un grupo y un usuario sin privilegios con uid y gid 1001, y USER hace que el proceso corra como él. El código se copia sin --chown: queda como propiedad de root y de solo lectura para appuser, de modo que quien comprometa el proceso no puede modificar la aplicación.
  • Variables de Python y de pip. PYTHONUNBUFFERED=1 envía los mensajes de la aplicación a docker logs sin esperar; PYTHONDONTWRITEBYTECODE=1 impide que Python escriba archivos .pyc al ejecutar la aplicación (los cerca de 2000 que pip compila al instalar sí quedan en el entorno virtual); PIP_NO_CACHE_DIR=1 impide que pip guarde las wheels descargadas.
  • HEALTHCHECK. Cada 30 s hace una petición a /health; Docker marca el contenedor como healthy o unhealthy (se ve en docker ps). No lo reinicia: eso lo hace un orquestador, o la plataforma con sus propios sondeos.
  • Entorno virtual copiado entre etapas. Funciona porque las dos etapas usan la misma imagen base y la misma ruta (/opt/venv): un entorno virtual guarda la ruta del intérprete con el que se creó y no es reubicable.

10.11 Comprobar que la API se comporta igual

La práctica de la semana pide comprobar que la API se comporta igual dentro del contenedor. La forma más simple es lanzar las mismas peticiones contra la versión local y contra la del contenedor, y comparar. Con el entorno virtual del proyecto activo, se arranca la API local en otro puerto, para no chocar con el contenedor, que usa el 8000:

uvicorn app.main:app --port 8001

Desde otra terminal se repiten tres peticiones —una dentro del rango del modelo, una extrapolada y una inválida— contra los dos puertos, y diff compara las salidas:

peticiones() {
  for x in 2.0 50.0 5000.0; do
    curl -s -w ' [HTTP %{http_code}]\n' -X POST "http://localhost:$1/predicciones" \
      -H 'Content-Type: application/json' -d "{\"x\": $x}"
  done
}
diff <(peticiones 8001) <(peticiones 8000) && echo "Respuestas idénticas"

Si diff no encuentra diferencias, imprime Respuestas idénticas: la API responde 200 con extrapolado: false, 200 con extrapolado: true y 422 exactamente igual en las dos versiones. Si solo uno de los dos está levantado, curl no obtiene respuesta del otro ([HTTP 000]) y diff lo muestra; antes conviene comprobar que ambos responden en /health, porque con los dos apagados la comparación saldría «idéntica». Los <( … ) requieren bash o zsh.

Tarea autónoma Contenerizar el proyecto propio y verificar la equivalencia con el entorno local: repetir esta comparación con sus propios endpoints (uno que responda bien, uno que falle por validación y uno que dependa de la configuración o de la base de datos). Los ajustes que suele exigir el proyecto propio están en el apartado siguiente.

10.12 De este ejemplo a tu proyecto

El proyecto propio casi nunca se parece al ejemplo. Estos son los ajustes más frecuentes.

1. Estructura. Si el proyecto es plano (main.py en la raíz, sin carpeta app/), el COPY y el CMD cambian con él: COPY main.py . y "main:app" en lugar de "app.main:app". Hay que copiar también todo lo que el código lee al arrancar: modelos entrenados (.joblib, .pkl), la carpeta de migraciones, plantillas.

2. Variables de entorno. La imagen no lleva .env (lo excluye el .dockerignore): la configuración llega al lanzar el contenedor, con --env-file o con -e. Si la configuración se lee con pydantic-settings (semana 8), se toma del entorno real cuando no hay archivo .env, y el código no cambia. En --env-file las comillas se conservan como parte del valor: se escribe CLAVE=valor, sin comillas (Docker Compose, en cambio, interpreta las comillas y las quita).

docker run --rm -p 8000:8000 --env-file .env regresion-api:0.1.0

3. Una base SQLite. SQLite guarda la base en un archivo, y eso plantea tres asuntos:

  • El usuario appuser no puede crear archivos en /app (lo creó WORKDIR como root). La base necesita un directorio propio: en la etapa runtime, antes de USER, se añade la línea siguiente, y la URL de la base apunta allí (por ejemplo sqlite:////data/app.db: cuatro barras, porque la ruta es absoluta). 
    RUN mkdir /data && chown appuser:appgroup /data
  • Lo que se escribe dentro de un contenedor vive en su capa de escritura y desaparece con docker rm. Para que los datos sobrevivan, se monta un volumen en ese directorio: 
    docker run -d --name api -p 8000:8000 -v datos:/data regresion-api:0.1.0
docker restart api    # el contenedor es el mismo: los datos también
docker rm -f api      # se elimina el contenedor, pero no el volumen «datos»
docker run -d --name api -p 8000:8000 -v datos:/data regresion-api:0.1.0   # los datos reaparecen
  • El .dockerignore excluye **/*.db: la base de desarrollo no debe viajar en la imagen.

4. Arranque y puerto. Si el proyecto usa Alembic, las migraciones se aplican antes de arrancar; si la plataforma asigna el puerto en $PORT, el CMD debe leerlo. Ambos casos se resuelven con el CMD con sh -c y exec del apartado 6.5. Y si el puerto cambia, el HEALTHCHECK debe sondear ese mismo puerto: de lo contrario el contenedor responde pero Docker lo marca unhealthy; basta con que el sondeo lea la misma variable (os.environ.get('PORT', '8000')).

5. Un solo comando. Un archivo docker-compose.yml describe ese mismo lanzamiento —imagen, puertos, volumen— y se levanta con docker compose up; con env_file: .env se le pasan las variables.

services:
  api:
    build: .
    ports:
      - "8000:8000"
    volumes:
      - datos:/data

volumes:
  datos:

Imagen base python:3.11.9-slim-bookworm Coincide con el intérprete del curso, es ligera y compatible con las wheels del ecosistema científico.

Preguntas conceptuales

Ejercicio 11.1 — Diferencia clave Explíquese, en no más de 60 palabras, por qué dos contenedores que se ejecutan en el mismo computador comparten el kernel del sistema Linux que los ejecuta, mientras que dos máquinas virtuales no comparten el suyo.
Solución comentada 11.1 Cada máquina virtual incluye un sistema operativo huésped completo —con su propio kernel— sobre un hipervisor: dos VMs cargan dos kernels. Un contenedor solo aísla el espacio de usuario mediante namespaces y cgroups del kernel del anfitrión; todos los contenedores de una máquina comparten ese único kernel y, por eso, arrancan en milisegundos y consumen mucha menos memoria.
Ejercicio 11.2 — Lectura de etiquetas Indíquese qué significa cada componente de la etiqueta python:3.11.9-slim-bookworm, por qué la elección de 3.11.9 es preferible a 3.11 en una API estadística y qué fuente de variación elimina esa elección y cuál no.
Solución comentada 11.2 python es el repositorio oficial; 3.11.9 es la versión exacta del intérprete; slim indica una variante reducida de Debian; bookworm es el nombre en clave de Debian 12. Fijar 3.11.9 evita que la etiqueta flotante 3.11 apunte automáticamente a un parche posterior del intérprete. No garantiza por sí solo resultados numéricos idénticos: para eso hay que fijar también NumPy y SciPy con ==, la base por digest y las semillas, y aun así BLAS puede variar con la CPU y el número de hilos.
Ejercicio 11.3 — Caché de capas El siguiente fragmento se reconstruye lentamente cada vez que cambia un archivo de la carpeta app/. Identifíquese el problema y propóngase una corrección: 
FROM python:3.11.9-slim-bookworm
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
Solución comentada 11.3 El problema es que COPY . . incluye el código fuente; cualquier cambio en app/ invalida esa capa y todas las posteriores, y obliga a reinstalar todas las dependencias. La corrección consiste en separar la copia de requirements.txt de la del código: 
FROM python:3.11.9-slim-bookworm
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app/ ./app/
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
Mientras requirements.txt no cambie, la capa de instalación se reutiliza y la reconstrucción tarda segundos en lugar de minutos.
Ejercicio 11.4 — Contexto de construcción Indíquense tres archivos o carpetas que nunca deberían incluirse en una imagen de producción, descríbase qué problema concreto causa cada uno si llega a colarse y nómbrese el archivo que evita que lleguen al contexto de construcción.
Solución comentada 11.4 Tres ejemplos típicos:
  • .env: contiene credenciales (claves de API, contraseñas de bases de datos). Si llega a la imagen, queda registrado en una capa permanente y puede filtrarse cuando la imagen se publica al registro.
  • .git/: incluye toda la historia del proyecto y sus posibles ramas, archivos eliminados que aún viven en commits, y datos de identidad de los autores. Aumenta el tamaño y la superficie de información expuesta.
  • data/raw/: archivos crudos de varios gigabytes vuelven la imagen muy pesada, ralentizan los despliegues y pueden contener información personal sin anonimizar.
Otras respuestas válidas: .venv/, __pycache__/, tests/, claves privadas (*.pem), bases de datos locales (*.db). El archivo que lo evita es .dockerignore. Sigue siendo necesario aunque el Dockerfile use COPY selectivo: el contexto completo viaja al daemon, y un COPY . . futuro —o el de otro compañero— lo copiaría todo.
Ejercicio 11.5 — Multi-stage en propias palabras Resúmase, en no más de 60 palabras, qué problema resuelve un multi-stage build y qué elemento del builder del Dockerfile de 10.9 no llega a la imagen final.
Solución comentada 11.5 Un multi-stage build separa las dependencias necesarias para construir el software de las necesarias para ejecutarlo. Solo la última etapa forma la imagen entregada; todas las anteriores se descartan. En el ejemplo del curso, lo que no llega a la imagen final es todo el builder: en particular build-essential (el compilador y sus cabeceras), que reduce el tamaño y la superficie de ataque. Borrar /var/lib/apt/lists/ o instalar con --no-cache-dir es otra técnica, ortogonal: ahorra espacio dentro de una misma etapa.
Ejercicio 11.6 — Usuario no privilegiado Suponiendo que el Dockerfile ya creó el usuario appuser, justifíquese por qué se recomienda la instrucción USER appuser en una imagen de producción, incluso aunque las pruebas funcionen igual con USER root.
Solución comentada 11.6 Si una vulnerabilidad permite a un atacante ejecutar código arbitrario dentro del contenedor y el proceso corre como root, ese código actúa como root: puede modificar todos los archivos del contenedor, instalar paquetes, escribir o borrar en los volúmenes del anfitrión que se hayan montado en él y, en escenarios con fugas de aislamiento, escalar privilegios al sistema anfitrión. Un usuario no privilegiado convierte ese mismo escenario en un compromiso mucho más limitado: el atacante hereda los permisos restringidos de appuser, lo que contiene el daño y facilita la respuesta a incidentes.

Redacción de Dockerfiles

Ejercicio 11.7 — Mini-API en un contenedor Redáctese un Dockerfile mono-etapa, basado en python:3.11.9-slim-bookworm, que empaquete la mini-API FastAPI siguiente, con un único endpoint GET /version que devuelve {"version": "0.1.0"}: 
from fastapi import FastAPI

app = FastAPI()


@app.get("/version")
def version() -> dict[str, str]:
    return {"version": "0.1.0"}
Con este requirements.txt (y un app/__init__.py vacío): 
fastapi==0.111.0
uvicorn[standard]==0.30.1
Cúmplanse estos requisitos:
  1. El proceso debe correr como un usuario no privilegiado.
  2. La caché debe permitir que un cambio en el código no reinstale las dependencias.
  3. La API debe responder en http://localhost:8000/version desde el anfitrión.
Compruébese: construir la imagen, lanzarla con docker run --rm -p 8000:8000, consultar /version con curl y ejecutar docker run --rm <imagen> id -u, que debe imprimir 1001.
Solución comentada 11.7 
# Dockerfile mono-etapa, didáctico
FROM python:3.11.9-slim-bookworm

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# Usuario no privilegiado.
RUN groupadd --system --gid 1001 appgroup \
 && useradd --uid 1001 --gid appgroup --create-home appuser

WORKDIR /app

# Dependencias primero para preservar la caché.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Código después; cambios aquí no reinstalan paquetes.
COPY app/ ./app/

USER appuser
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
El orden requirements.txt → pip install → código garantiza que la capa de dependencias se reutilice mientras el archivo de dependencias no cambie. La instrucción USER appuser aplica el principio de menor privilegio. EXPOSE solo documenta el puerto: lo que hace accesible la API desde el anfitrión es publicarlo con -p 8000:8000 y que Uvicorn escuche en 0.0.0.0. Durante la construcción, pip avisa de que se ejecuta como root; es inocuo, porque la imagen se construye como root y solo el proceso final corre como appuser.
Ejercicio 11.8 — Versión multi-stage Reescríbase el Dockerfile del ejercicio anterior empleando dos etapas (builder y runtime). El builder debe instalar las dependencias en un entorno virtual y, para que el ahorro sea visible, build-essential (como en el ejemplo integrador); la etapa final debe contener únicamente el entorno virtual y el código. Compárense los tamaños de las imágenes de 11.7 y 11.8 (suma de docker history).
Solución comentada 11.8 
# --- builder ---
FROM python:3.11.9-slim-bookworm AS builder
ENV PIP_NO_CACHE_DIR=1
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /build
COPY requirements.txt .
RUN pip install -r requirements.txt

# --- runtime ---
FROM python:3.11.9-slim-bookworm AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"
RUN groupadd --system --gid 1001 appgroup \
 && useradd --uid 1001 --gid appgroup --create-home appuser
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY app/ ./app/
USER appuser
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
Con build-essential en el builder, la imagen final no lo lleva: el multi-stage se ahorra el compilador y sus cabeceras, que pesan cientos de megabytes. Sin él, las dos imágenes pesan casi lo mismo (la de dos etapas incluso unos 25 MB más, porque el entorno virtual trae su propio pip y setuptools): el multi-stage solo compensa cuando el builder contiene algo que el runtime no necesita. Error frecuente: la ruta del entorno virtual debe ser la misma en las dos etapas, y ambas deben usar la misma imagen base. El patrón es el del ejemplo integrador y resulta transferible a otras APIs estadísticas.

11. Conclusión, buenas prácticas de seguridad y recursos

12.1 Resumen

  1. Un contenedor extiende la idea del entorno virtual al sistema operativo completo: aísla paquetes, intérprete, bibliotecas del sistema y procesos.
  2. Las máquinas virtuales virtualizan el hardware y cargan un kernel completo; los contenedores comparten el kernel del anfitrión y son órdenes de magnitud más livianos.
  3. El Dockerfile describe, instrucción a instrucción, cómo se reconstruye la imagen. Las instrucciones que añaden contenido producen capas inmutables que Docker reutiliza desde la caché mientras sus entradas no cambian.
  4. La imagen base python:3.11.9-slim-bookworm ofrece un balance razonable entre tamaño, compatibilidad con el ecosistema científico de Python y vigencia de soporte.
  5. El contexto de construcción es lo que el cliente envía al daemon. Un .dockerignore bien diseñado mantiene el contexto pequeño, rápido y sin secretos.
  6. Los multi-stage builds separan construcción de ejecución: la imagen final no contiene compiladores ni cachés, lo que reduce el tamaño y la superficie de ataque.

12.2 Buenas prácticas de seguridad

Cuatro prácticas mínimas, todas vistas en esta unidad:

  • No ejecutar como root. Crear un usuario sin privilegios con useradd y aplicar USER antes del CMD final.
  • No copiar secretos a la imagen. Usar .dockerignore para excluir .env, claves privadas y certificados; inyectar las credenciales como variables de entorno en tiempo de ejecución (docker run --env-file) y, si un secreto hace falta al construir, RUN --mount=type=secret —nunca ARG ni ENV—.
  • Fijar versiones. Tanto la imagen base (3.11.9-slim-bookworm) como las dependencias en requirements.txt con ==; idealmente, fijar el digest @sha256:... de la imagen base.
  • Reducir la superficie de ataque. Multi-stage para descartar compiladores; una sola responsabilidad por imagen; sin curl ni git en producción. Mantener además el contexto pequeño y limpio.

Para ampliar, cuando el proyecto lo pida:

  • Escanear vulnerabilidades. Herramientas como docker scout, trivy o grype inspeccionan las capas y reportan CVE (vulnerabilidades publicadas, con identificador).
  • Actualizar de forma deliberada. Fijar no es congelar: una base fijada no recibe parches. Reconstruir y republicar con versiones nuevas de Debian o de CPython, con las pruebas en verde y tras escanear la imagen.
  • Privilegios mínimos en tiempo de ejecución. Lanzar con docker run --read-only o --cap-drop=ALL cuando la aplicación lo permita.

12.3 Compatibilidad con prácticas previas

Lo aprendido en esta unidad no contradice ninguna de las recomendaciones anteriores del curso, sino que las reafirma:

  • La validación con Pydantic y la respuesta HTTP 422 (semanas 4 y 6) operan dentro del contenedor exactamente igual que fuera; el aislamiento no altera la semántica de FastAPI.
  • La pirámide de testing sigue rigiendo: las pruebas unitarias se ejecutan antes de construir la imagen, y la imagen final no lleva pytest.
  • La inyección de dependencias con Depends coexiste con el contenedor: la configuración se inyecta como variables de entorno al lanzar el contenedor (docker run -e o --env-file) y la aplicación las lee igual que en local (semana 8).
  • La fijación de versiones, semillas y configuración numérica es el primer paso para una imagen verdaderamente reproducible.
