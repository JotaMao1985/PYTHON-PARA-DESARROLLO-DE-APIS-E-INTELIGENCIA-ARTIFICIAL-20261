2. Concepto de PaaS

El modelo de servicios en la nube clasifica las plataformas según qué partes del stack tecnológico administra el proveedor y qué partes administra el equipo de desarrollo. Las tres categorías canónicas son IaaS (Infraestructura como Servicio), PaaS (Plataforma como Servicio) y SaaS (Software como Servicio).

El esquema deja claro el trade-off central: cuanto más alto se sube en la pila, menos control existe sobre la infraestructura, pero también menos esfuerzo se invierte en operación. Como referencia, suele añadirse un cuarto modelo, On-premise (servidores propios en sala de cómputo), donde el equipo administra absolutamente todas las capas. La Figura 2.1 sitúa los cuatro modelos en un plano de control contra carga operativa, donde se evidencia que PaaS es el punto óptimo para una API estadística académica: el equipo conserva control sobre el código, los datos y la lógica estadística, mientras delega parches del kernel, balanceadores y certificados TLS al proveedor.

El círculo rosado y más grande representa PaaS, dentro del recuadro punteado que delimita el sweet spot académico; la flecha sugiere el desplazamiento natural desde IaaS hacia PaaS cuando se prioriza la simplicidad operativa sobre el control fino del entorno.

2.2 ¿Qué hace exactamente un PaaS?

Un PaaS recibe el código fuente o una imagen Docker y se encarga de:

  1. Construir la aplicación: ejecutar docker build o invocar buildpacks que detectan el lenguaje (Python, Node, Go, …) e instalan dependencias.
  2. Aprovisionar recursos: contenedores, balanceadores, almacenamiento, certificados TLS, dominios.
  3. Ejecutar el contenedor con la cantidad de CPU y memoria solicitada, reiniciándolo si falla.
  4. Exponer el servicio en un dominio público con HTTPS.
  5. Recolectar logs, métricas y, en algunos casos, trazas distribuidas.
  6. Inyectar variables de entorno y secretos al contenedor en el arranque (detalle en §3).

Lo que no hace un PaaS, y se sigue gestionando del lado del estudiante, es: escribir las migraciones, definir validadores Pydantic, decidir esquemas de la base de datos, mantener el código de regresión y diseñar la API.

2.4 ¿Cuándo NO usar PaaS?

  • Cuando la carga es masiva y predecible: una infraestructura propia (IaaS o Kubernetes administrado) suele ser más económica a partir de cierto volumen.
  • Cuando hay restricciones regulatorias estrictas sobre la región física donde residen los datos, y el PaaS no las garantiza.
  • Cuando se requiere customización profunda del sistema operativo, drivers especializados (GPU sin soporte oficial, hardware FPGA, etc.) o configuraciones de red que el proveedor no expone.

Para una API estadística que sirve modelos de regresión, intervalos de confianza o pronósticos de baja a media intensidad, ninguno de los tres puntos suele aplicar.

3. Variables de entorno: desarrollo vs. producción

Las variables de entorno son el mecanismo estándar para inyectar configuración a un proceso sin tocar el código fuente. La metodología de los Twelve-Factor Apps, referencia de la industria, postula su tercer principio: la configuración debe almacenarse en el entorno, no en archivos versionados ni en constantes.

3.1 Qué cambia entre desarrollo y producción

El estudiante ya conoce python-dotenv y los archivos .env para desarrollo. La diferencia con producción es conceptual y operativa:

Aspecto Desarrollo (local) Producción (PaaS)
Origen de las variables Archivo .env leído por python-dotenv. Inyección directa por el proveedor; .env no se sube.
Base de datos SQLite local: sqlite:///./encuestas.db. PostgreSQL gestionado: postgresql+psycopg://….
Recarga automática uvicorn --reload. Deshabilitada; reinicio sólo en redeploy.
Nivel de log DEBUG o INFO. INFO o WARNING.
Documentación interactiva Swagger UI y Redoc abiertos. Pueden ocultarse o protegerse.
Secretos En .env ignorado por git. En el panel del proveedor o gestor de secretos.
Puerto Fijo (por ejemplo, 8000). Asignado por el proveedor vía variable PORT.

La Figura 3.1 visualiza la misma comparación en un eje cualitativo de "endurecimiento": cada línea conecta el valor en desarrollo con el valor en producción para una misma dimensión, y el desplazamiento horizontal sintetiza cuánto cambia la configuración al cruzar la frontera local → PaaS.

Figura 3.1 — En desarrollo (azul navy), todas las dimensiones se resuelven con herramientas locales sencillas: .env, SQLite, --reload, log abierto. En producción (rosa USTA), cada dimensión sube en complejidad y endurecimiento: panel del PaaS, PostgreSQL gestionado, secretos centralizados, puerto inyectado, documentación restringida. La diferencia más pronunciada está en el manejo de secretos.

3.2 Configuración tipada con Pydantic Settings

Una buena práctica, ya esbozada en la Semana IV, consiste en exponer toda la configuración a través de un objeto Pydantic. Eso unifica la lectura de variables y deja todo el sistema de tipos como fuente de verdad:

# app/config.py
from functools import lru_cache
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Configuracion(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_prefix="APP_",
        extra="ignore",
    )

    # Generales
    entorno: str = Field(default="development")        # development | production
    debug: bool = Field(default=True)
    log_level: str = Field(default="INFO")

    # Persistencia
    bd_url: str = Field(default="sqlite:///./encuestas.db")

    # Numéricos del dominio estadístico
    seed: int = Field(default=2026, ge=0)
    nivel_confianza: float = Field(default=0.95, gt=0.5, lt=1.0)

@lru_cache
def obtener_config() -> Configuracion:
    return Configuracion()

El estudiante reconocerá el patrón: obtener_config se inyecta con Depends en cualquier endpoint y la cache asegura que la lectura ocurre una sola vez por proceso.

3.3 Archivos .env y .env.example

El archivo .env queda en la raíz del proyecto y se ignora en git. En su lugar se versiona una plantilla .env.example con los nombres de las variables y valores ficticios. La estructura típica es:

# .env.example  (versionado, sin valores reales)
APP_ENTORNO=development
APP_DEBUG=true
APP_LOG_LEVEL=INFO
APP_BD_URL=sqlite:///./encuestas.db
APP_SEED=2026
APP_NIVEL_CONFIANZA=0.95

El .gitignore debe contener al menos:

# .gitignore
.env
.env.*.local
__pycache__/
*.pyc
.venv/
encuestas.db
Errores frecuentes Subir .env al repositorio expone credenciales. Aun después de eliminarlo, los secretos quedan en el historial de git: lo correcto es rotarlos en el proveedor antes de continuar. Por la misma razón nunca se incluyen secretos en el Dockerfile con ENV; se inyectan en tiempo de ejecución.

3.4 Variables en Railway y Render

Ambos proveedores ofrecen un panel donde se definen las variables y se inyectan al contenedor antes del arranque. Para la API estadística, una configuración productiva típica luce así:

# Variables configuradas en el panel del PaaS (no en el repositorio)
APP_ENTORNO=production
APP_DEBUG=false
APP_LOG_LEVEL=INFO
APP_BD_URL=postgresql+psycopg://usuario:secreto@host:5432/encuestas
APP_SEED=2026
APP_NIVEL_CONFIANZA=0.95
# PORT lo inyecta automáticamente el proveedor; no debe definirse a mano

Cuando se aprovisiona una base de datos PostgreSQL gestionada (un add-on en Railway o un servicio de base en Render), el proveedor expone una variable como DATABASE_URL que puede referenciarse desde la configuración:

# Railway permite escribir referencias entre variables:
APP_BD_URL=${{Postgres.DATABASE_URL}}

3.5 El puerto en producción: $PORT

Una diferencia operativa importante: el PaaS decide en qué puerto el contenedor debe escuchar y comunica esa decisión por la variable PORT. El comando de arranque debe usar esa variable, no un número fijo. Para Uvicorn:

# Comando de arranque dentro del Dockerfile
CMD ["sh", "-c", "uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]

La sintaxis ${PORT:-8000} es la expansión POSIX habitual: si PORT no está definida, se usa 8000. Esto mantiene compatibilidad con docker run -p 8000:8000 en local y con la inyección del proveedor en producción.

Bind a 0.0.0.0, no a 127.0.0.1 En desarrollo se trabaja con 127.0.0.1 porque sólo el propio equipo se conecta. En un contenedor de producción, el tráfico llega desde fuera del contenedor: Uvicorn debe escuchar en 0.0.0.0 para aceptarlo. Si no, el proveedor reportará el servicio como caído.

4. CI/CD básico con GitHub

4.1 ¿Qué es CI/CD?

El acrónimo combina dos prácticas relacionadas:

  • CI (Continuous Integration / Integración Continua): en cada cambio que se sube al repositorio, un servidor automatizado instala dependencias, ejecuta las pruebas y reporta el resultado. El objetivo es detectar regresiones antes de que lleguen a la rama principal.
  • CD (Continuous Delivery / Continuous Deployment): cuando los cambios fusionan en la rama principal, se construye el artefacto (imagen Docker) y se publica en producción de forma automática. Delivery deja el artefacto listo y un humano lo aprueba; Deployment publica directamente.

4.2 El pipeline completo

El reparto concreto de responsabilidades entre GitHub Actions (la pieza CI) y el PaaS (la pieza CD) se detalla en §4.5; aquí basta con visualizar el orden temporal del flujo, desde que el estudiante hace git push hasta que la nueva versión queda publicada.

01git push El estudiante sube cambios a GitHub.
›
02CI: pytest Actions instala deps y ejecuta la suite.
›
03Merge a main Si pasa, se acepta el PR.
›
04CD: build + deploy Railway/Render reconstruye y publica.

En la práctica del curso, GitHub Actions se ocupa del paso de CI (ejecutar pytest y, opcionalmente, construir la imagen) y el PaaS se ocupa del paso de CD (reconstruir y publicar al detectar un push en main).

La Figura 4.1 cuantifica el costo en tiempo de cada fase, distinguiendo la primera ejecución de las posteriores (cuando la caché de pip y la caché de capas de Docker están calientes). Conocer estos órdenes de magnitud ayuda a interpretar la duración de un workflow y a identificar cuellos de botella reales.

Figura 4.1 — La caché de pip activada por actions/setup-python@v5 y la caché de capas de Docker reducen drásticamente el tiempo del pipeline. El cuello de botella estable suele ser pytest, que no se acelera por caché. Valores aproximados, dependientes del tamaño del proyecto y la región del runner.

4.3 Anatomía de un workflow de GitHub Actions

Los workflows son archivos YAML alojados en .github/workflows/. Cada uno declara:

  • Disparadores (on): qué evento lo dispara (push, pull_request, schedule, …).
  • Trabajos (jobs): unidades que se ejecutan en una máquina virtual runner.
  • Pasos (steps): comandos o acciones reutilizables, una tras otra dentro del trabajo.

Para la API encuestas-api, un workflow mínimo que ejecuta pytest en cada push y cada pull request hacia main tiene esta forma:

# .github/workflows/ci.yml
name: CI - tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - name: Clonar repositorio
        uses: actions/checkout@v4

      - name: Configurar Python 3.11.9
        uses: actions/setup-python@v5
        with:
          python-version: "3.11.9"
          cache: "pip"

      - name: Instalar dependencias
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Ejecutar suite con pytest
        env:
          APP_ENTORNO: test
          APP_DEBUG: "false"
          APP_LOG_LEVEL: WARNING
          APP_BD_URL: sqlite:///./test.db
        run: pytest -ra --maxfail=1

Lectura del workflow paso a paso

  1. actions/checkout@v4 clona el repositorio dentro del runner.
  2. actions/setup-python@v5 instala exactamente Python 3.11.9, la misma versión usada en desarrollo y dentro del Dockerfile.
  3. El paso Instalar dependencias aprovecha la caché de pip: en ejecuciones siguientes, sólo descarga lo nuevo.
  4. Las variables de entorno se inyectan en el bloque env de la última etapa para que la suite encuentre la configuración esperada.
  5. pytest -ra --maxfail=1 reporta todos los resultados y se detiene en el primer fallo, lo cual deja el log más legible.

4.4 Proteger la rama principal

Por sí sola, la presencia de un workflow no impide que un cambio defectuoso entre en main. Para que CI sea efectivo, en la configuración del repositorio se define una regla de protección de rama que exige:

  • Todos los cambios entran a main sólo a través de pull request.
  • El check tests debe estar en estado verde antes de fusionar.
  • Opcionalmente, se requiere al menos una revisión humana del PR.

Con esta protección activada, un compañero o el propio estudiante no puede fusionar un cambio que rompa una prueba; el botón de merge aparece deshabilitado.

4.5 Conexión del PaaS con GitHub: la pieza CD

El despliegue automático se configura una sola vez:

  1. En Railway o Render se selecciona Deploy from GitHub repo y se autoriza el acceso al repositorio.
  2. Se elige la rama de seguimiento (típicamente main).
  3. Se configuran las variables de entorno productivas en el panel.
  4. El proveedor instala un webhook en GitHub: cada push al branch seguido dispara automáticamente un build y un deploy.

El estudiante observará que, al fusionar un PR aprobado, en cuestión de uno o dos minutos Railway/Render compila el Dockerfile y publica la nueva versión. Si los tests del PR pasaron, hay una probabilidad muy alta de que el despliegue también lo haga.

Patrón didáctico recomendado Para un curso de pregrado, CI con GitHub Actions + CD nativo del PaaS cubre el 95 % de los casos sin complicaciones. Los workflows de Actions con pasos de docker login + docker push a un registro propio son posibles, pero suelen ser una fuente de fallos por permisos y se reservan para etapas más avanzadas.

4.6 Workflow extendido: lint y cobertura

Cuando la suite crece, conviene añadir verificaciones complementarias en el mismo workflow:

      - name: Lint con ruff
        run: |
          pip install ruff==0.5.0
          ruff check app tests

      - name: Cobertura mínima del 85 %
        run: |
          pip install pytest-cov==5.0.0
          pytest --cov=app --cov-report=term-missing --cov-fail-under=85

El parámetro --cov-fail-under=85 hace fallar el workflow si la cobertura cae por debajo del umbral, materializando una política objetiva sobre el repositorio.

5. Logs de producción

5.1 ¿Por qué print no es suficiente en producción?

Durante el desarrollo es habitual usar print para inspeccionar el flujo del programa. En producción, sin embargo, esa práctica acarrea problemas:

  • No hay forma de filtrar por severidad (no se distingue una advertencia inofensiva de un error crítico).
  • No incluyen marca de tiempo, módulo origen ni identificador de proceso.
  • No se pueden silenciar selectivamente sin tocar el código.
  • No tienen contexto consistente entre módulos: en un servicio con muchos endpoints es imposible saber con certeza qué archivo o función emitió cada mensaje.

El módulo logging de la biblioteca estándar resuelve los cuatro puntos.

5.2 Niveles de severidad

Nivel Valor numérico Cuándo emitirlo
DEBUG10 Detalle interno útil sólo al depurar (valor de un coeficiente intermedio).
INFO20 Eventos normales (petición recibida, modelo ajustado correctamente).
WARNING30 Situación inusual pero recuperable (matriz de diseño cercana a singular).
ERROR40 Una operación falló pero el servicio sigue arriba (excepción no controlada en un endpoint).
CRITICAL50 Falla que pone en riesgo el servicio completo (BD inalcanzable).

La Figura 5.1 ilustra la distribución típica de eventos por severidad en una API estadística saludable. La forma esperada es altamente asimétrica: INFO domina por volumen, mientras que ERROR y CRITICAL son raros pero precisamente por eso merecen alertas inmediatas. Una distribución muy distinta (por ejemplo, 20 % de ERROR) sería un síntoma claro de un problema en producción.

Figura 5.1 — En una API estadística sana, INFO concentra cerca del 95 % de los eventos. La escala logarítmica permite ver simultáneamente niveles que difieren en órdenes de magnitud: ERROR y CRITICAL son menos del 1 %, pero su cantidad absoluta y tendencia diaria son métricas clave de observabilidad.

5.3 Configuración mínima para FastAPI

El siguiente módulo configura el logging al inicio del proceso. La política es:

  • El nivel se lee de APP_LOG_LEVEL.
  • El destino es la salida estándar (sys.stdout); el PaaS la captura.
  • El formato incluye timestamp ISO, nivel, módulo y mensaje.
# app/logs.py
import logging
import sys
from app.config import obtener_config

def configurar_logging() -> None:
    config = obtener_config()
    nivel = getattr(logging, config.log_level.upper(), logging.INFO)

    formato = "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s"
    fecha = "%Y-%m-%dT%H:%M:%S%z"

    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(logging.Formatter(formato, datefmt=fecha))

    root = logging.getLogger()
    root.setLevel(nivel)
    root.handlers = [handler]
    # Acalla el ruido de Uvicorn por debajo de WARNING en producción
    logging.getLogger("uvicorn.access").setLevel(
        logging.WARNING if config.entorno == "production" else logging.INFO
    )

Y en el módulo principal de la aplicación se invoca antes de instanciar FastAPI:

# app/main.py
from fastapi import FastAPI
from app.logs import configurar_logging

configurar_logging()
app = FastAPI(title="encuestas-api", version="0.5.0")

5.4 Emisión de logs desde un endpoint

El logger se obtiene por nombre de módulo (__name__) y se emiten mensajes con el nivel correspondiente. Es importante no concatenar strings: se usa el lazy formatting de %, que solo formatea si el log se emite:

# app/api/regresion.py
import logging
from fastapi import APIRouter, HTTPException
from app.schemas import RegresionInput  # modelo Pydantic con campos x, y

logger = logging.getLogger(__name__)
router = APIRouter()

@router.post("/modelos/regresion")
def ajustar(payload: RegresionInput):
    logger.info("Ajuste solicitado: n=%d", len(payload.x))

    try:
        resultado = ajuste_ols(payload.x, payload.y)
    except ValueError as e:
        logger.warning("Datos inadecuados: %s", e)
        raise HTTPException(status_code=422, detail=str(e))
    except Exception:
        logger.exception("Fallo inesperado en ajuste")
        raise HTTPException(status_code=500, detail="Error interno")

    logger.info("Ajuste OK: R2=%.4f", resultado.r2)
    return resultado

El método logger.exception registra el mensaje y, automáticamente, la traza completa de la excepción en curso. Es la forma correcta de capturar fallas inesperadas sin perder información para el diagnóstico posterior.

Nunca se registran datos sensibles Los logs son leídos por administradores, copiados a sistemas de búsqueda y, eventualmente, archivados. No deben contener: credenciales, tokens, números de identificación personales, ni los datos crudos de las observaciones cuando el conjunto sea confidencial. Sí se registran tamaños, identificadores anónimos y resúmenes estadísticos.

5.5 Cómo se ven los logs en producción

Una traza típica de la API en Railway o Render durante una petición exitosa luce así (los colores corresponden al nivel):

5.6 Logs estructurados (opcional)

Cuando los logs van a ser procesados por un sistema externo (Datadog, Grafana Loki, Elastic Stack), se prefiere el formato JSON, donde cada línea es un objeto independiente. Esto permite filtrar por campos sin recurrir a expresiones regulares:

# Log estructurado, una línea por evento
{"ts": "2026-04-30T14:22:42Z", "level": "INFO", "logger": "app.api.regresion",
 "event": "ajuste_ok", "n": 128, "r2": 0.8731, "duracion_ms": 42}

Bibliotecas como structlog o python-json-logger simplifican esa salida. Para el alcance de este curso es suficiente con el formateador de texto descrito en 5.3.

5.7 Lectura de logs en Railway y Render

Ambos paneles ofrecen una vista en vivo de la salida estándar y estándar de error del contenedor. Las funciones típicas son:

  • Filtrar por nivel (WARNING o superior).
  • Buscar por subcadena (por ejemplo, R2=).
  • Descargar el log de las últimas 24-72 horas para análisis fuera de línea.
  • Ver el log histórico de una build: útil para depurar fallos de construcción del Dockerfile.
Doce factores y los logs El undécimo principio de los Twelve-Factor Apps dice: logs as event streams. La aplicación no debe preocuparse por archivos de log, rotación ni destino: simplemente escribe a stdout. La plataforma se encarga del resto. Esto es exactamente lo que hacen Railway y Render.

6. Railway / Render: detección automática de Dockerfile

6.1 ¿Cómo deciden estos PaaS qué construir?

Cuando se conecta un repositorio a Railway o Render, el proveedor inspecciona los archivos de la raíz para decidir el método de construcción:

¿Existe Dockerfile en la raíz? │ ├── Sí ──► Construir con `docker build .` ◄──── ruta usada en este curso │ └── No ──► Detectar lenguaje (Python, Node, ...) ├── requirements.txt → buildpack Python ├── package.json → buildpack Node └── go.mod → buildpack Go

Cuando hay un Dockerfile, los buildpacks (Nixpacks en Railway, sistema propio en Render) se ignoran. Esto da control total sobre la imagen y deja al proveedor sólo el rol de construir, ejecutar y exponer.

6.2 Requisitos del Dockerfile para Railway / Render

El Dockerfile multi-stage de la semana anterior ya cumple casi todo lo necesario. Sólo requiere dos confirmaciones:

  1. El comando CMD debe usar la variable $PORT.
  2. El proceso debe escuchar en 0.0.0.0.

Una versión productiva completa, compatible con ambos proveedores, es:

# ============================ Etapa de construcción
FROM python:3.11.9-slim-bookworm AS builder

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

WORKDIR /build

COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt

# ============================ Etapa final
FROM python:3.11.9-slim-bookworm

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# Usuario sin privilegios
RUN useradd --create-home --uid 1000 api
USER api

WORKDIR /app

COPY --from=builder /install /usr/local
COPY --chown=api:api app ./app

# El proveedor inyecta PORT; en local cae a 8000
EXPOSE 8000
CMD ["sh", "-c", "uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]
Por qué PYTHONUNBUFFERED=1 Sin esta variable, Python amortigua su salida estándar y los logs aparecen en bloques grandes y con retraso en el panel del proveedor. Con PYTHONUNBUFFERED=1, cada logger.info(...) se ve casi en tiempo real.

6.3 Flujo de despliegue en Railway

El procedimiento típico, ya en posesión del Dockerfile anterior, es:

  1. Crear cuenta en railway.app y autorizar el acceso al repositorio GitHub.
  2. Pulsar New Project ▸ Deploy from GitHub repo y seleccionar el repositorio de la API.
  3. Railway detecta el Dockerfile y construye la primera versión sin intervención adicional.
  4. En Variables se introducen APP_ENTORNO=production, APP_DEBUG=false, APP_LOG_LEVEL=INFO, APP_BD_URL, etc. La variable PORT se inyecta automáticamente y no debe definirse a mano.
  5. En Settings ▸ Networking se genera un dominio público (encuestas-api.up.railway.app). Opcionalmente se asigna uno propio.
  6. Cualquier push futuro a la rama elegida dispara un nuevo build + deploy.

6.4 Flujo de despliegue en Render

El procedimiento es análogo, con dos diferencias prácticas:

  1. Render distingue entre Web Service (servicio HTTP) y otros tipos (background worker, cron job, base de datos). Para la API se elige Web Service.
  2. El plan gratuito suspende el servicio tras 15 minutos sin tráfico; la primera petición tras la suspensión tarda algunos segundos en arrancar el contenedor. Para evitarlo, se cambia al plan pagado o se mantiene un health check periódico desde un servicio externo.

6.6 Health check para alta disponibilidad

Ambos proveedores aceptan un endpoint que el balanceador consulta para decidir si el contenedor está sano. En FastAPI se añade fácilmente:

# app/api/salud.py
from fastapi import APIRouter

router = APIRouter()

@router.get("/healthz")
def salud():
    return {"status": "ok"}

En Railway no es obligatorio definirlo (la simple aceptación de conexiones TCP basta). En Render se configura en Settings ▸ Health Check Path = /healthz. El nombre /healthz es una convención de Kubernetes adoptada por la comunidad: la z al final reduce la probabilidad de colisión con un endpoint de negocio.

6.7 Verificación final

Tras el despliegue, una verificación completa contempla:

  1. Documentación viva: abrir https://<dominio>/docs y comprobar que Swagger UI carga los tres endpoints.
  2. Health check: curl https://<dominio>/healthz debe devolver {"status":"ok"} en menos de 200 ms.
  3. Logs: en el panel del PaaS debe verse al menos un evento INFO de inicialización al arrancar.
  4. Variables: consultar el endpoint GET /resumen/media y comprobar que la conexión a la BD productiva funciona.
Una API estadística nunca está "terminada" El despliegue en producción no cierra el ciclo, lo abre. A partir de ese momento, los logs y los reportes de los usuarios alimentan el siguiente sprint de mejoras, que entrará nuevamente al pipeline CI/CD descrito en la sección 4.

Ejercicio 7.2 — Configuración tipada Extiéndase la clase Configuracion de la sección 3.2 con un campo cors_origins de tipo list[str] que se lea de la variable APP_CORS_ORIGINS separada por comas. from pydantic import field_validator

class Configuracion(BaseSettings):
    cors_origins: list[str] = Field(default_factory=list)

    @field_validator("cors_origins", mode="before")
    @classmethod
    def parsear_csv(cls, v):
        if isinstance(v, str):
            return [s.strip() for s in v.split(",") if s.strip()]
        return v

# tests/test_config.py

Ejercicio 7.4 — Diagnóstico por logs Léase el siguiente fragmento de log productivo y dígase: (i) qué endpoint se invocó, (ii) cuál fue la causa probable del error 500, (iii) qué cambio mitigaría una repetición del incidente. 
2026-04-30T14:23:09+0000 | INFO    | app.api.regresion | Ajuste solicitado: n=3
2026-04-30T14:23:09+0000 | ERROR   | app.api.regresion | Fallo inesperado en ajuste

Solución 7.4
  1. (i) Se invocó POST /modelos/regresion, según el módulo app.api.regresion que emite el log.
  2. (ii) La matriz XTX resultó singular: con n=3 el rango efectivo de la matriz de diseño suele ser deficiente — más coeficientes que observaciones útiles, varianza nula en la covariable o colinealidad perfecta entre columnas. Ejercicio 7.5 — Variables de entorno Identifíquense los problemas en el siguiente Dockerfile en el contexto de un despliegue en Railway, y propónganse correcciones: 
FROM python:3.11.9-slim-bookworm
ENV APP_BD_URL=postgresql://prod_user:s3cret@db:5432/encuestas
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
CMD uvicorn app.main:app --host 127.0.0.1 --port 8000
Solución 7.5
  • Secreto incrustado en la imagen: la línea ENV APP_BD_URL=... deja la contraseña dentro del filesystem de la imagen, accesible para cualquiera que la ejecute. Debe eliminarse y configurarse en el panel del PaaS como variable de entorno.
  • --host 127.0.0.1: el contenedor sólo aceptará tráfico desde sí mismo y el balanceador no podrá alcanzarlo. Debe ser 0.0.0.0.
  • Puerto fijo: Railway inyecta PORT. La forma correcta es --port ${PORT:-8000} con CMD ["sh", "-c", "..."].
  • COPY . /app sin orden: impide cachear la capa de instalación de dependencias. Es preferible copiar primero requirements.txt, instalar y luego copiar el resto.
  • Sin usuario no privilegiado: el proceso corre como root. Conviene crear un usuario dedicado y usar USER api.
Ejercicio 7.6 — Health check Diséñese un endpoint GET /readyz que verifique, además de la disponibilidad del proceso, que la base de datos responde. Discútase qué código de estado se devuelve cuando la BD no responde y por qué importa la distinción con /healthz.
Solución 7.6 
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy import text
from app.db import obtener_sesion

router = APIRouter()

@router.get("/readyz")
def listo(sesion = Depends(obtener_sesion)):
    try:
        sesion.execute(text("SELECT 1"))
    except Exception:
        raise HTTPException(status_code=503, detail="BD no disponible")
    return {"status": "ready"}

Distinción clave: /healthz (liveness) responde mientras el proceso esté vivo y permite al PaaS decidir si reiniciar el contenedor; /readyz (readiness) responde sólo si el servicio está en condiciones de atender tráfico, lo cual incluye dependencias externas. Devolver 503 en /readyz permite al balanceador retirar la instancia del pool sin matarla, esperando a que la BD vuelva.

8. Resumen y referencias

8.1 Resumen ejecutivo

  1. El modelo IaaS / PaaS / SaaS describe qué administra el proveedor y qué administra el equipo. Para una API estadística académica, PaaS es el punto de equilibrio entre control y simplicidad operativa.
  2. Las variables de entorno son la frontera entre código y configuración. En desarrollo viven en .env (cargado por python-dotenv) y en producción se inyectan desde el panel del proveedor. Pydantic Settings unifica la lectura con tipos verificables.
  3. CI/CD básico se construye con dos piezas: GitHub Actions ejecutando pytest en cada push y el PaaS (Railway o Render) reconstruyendo y desplegando al fusionar en main. La protección de rama materializa la política de calidad.
  4. Los logs en producción se emiten con el módulo logging, escriben a stdout y los recoge el proveedor. Los niveles DEBUG/INFO/WARNING/ERROR/CRITICAL permiten filtrar y diagnosticar; los datos sensibles nunca se registran.
  5. Railway y Render detectan automáticamente el Dockerfile en la raíz del repositorio. Basta con que el CMD use ${PORT:-8000} y escuche en 0.0.0.0 para que la imagen multi-stage de la semana anterior funcione sin modificaciones.
