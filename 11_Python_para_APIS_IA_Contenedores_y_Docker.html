1. Introducción y objetivos de aprendizaje

En las semanas previas se construyó una API estadística con FastAPI, se validaron sus entradas con Pydantic, se inyectaron dependencias mediante Depends, se persistieron observaciones con SQLAlchemy y se redactó una suite de pruebas con pytest. La pregunta natural que aparece a continuación es: ¿cómo se entrega ese servicio a otra máquina —el servidor del laboratorio, una máquina virtual en la nube, el computador de un compañero— sin que el ajuste de un modelo de regresión devuelva resultados distintos por culpa de una versión diferente de NumPy?

La respuesta moderna es la contenerización. Un contenedor empaqueta el código, sus dependencias, el intérprete de Python y hasta la configuración del sistema operativo en un único artefacto inmutable. El estándar de facto para construir y ejecutar contenedores se llama Docker.

Objetivo de aprendizaje Al finalizar esta unidad, el estudiante distingue contenedores de máquinas virtuales, redacta un Dockerfile sintáctica y semánticamente correcto sobre la imagen base python:3.11.9-slim-bookworm, controla qué archivos se envían al motor de Docker mediante el contexto de construcción, aplica multi-stage builds para reducir el tamaño y la superficie de ataque de la imagen final, y empaqueta una API FastAPI que sirva un modelo estadístico sencillo.

1.1 ¿Qué se construye en esta semana?

El hilo conductor consiste en empaquetar una API FastAPI llamada regresion-api que expone un único endpoint: POST /predicciones, el cual recibe un valor de la variable explicativa x y devuelve la predicción ŷ de un modelo de regresión lineal previamente entrenado. La unidad culmina con una imagen Docker construida en dos etapas, ejecutándose como un usuario no privilegiado y de tamaño reducido.

1.2 Prerrequisitos

  • Python 3.11.9, entornos virtuales (venv) y requirements.txt (Semana I–II).
  • FastAPI, Pydantic, ASGI, Depends, python-dotenv (Semana III).
  • Pruebas con pytest y reproducibilidad sin Docker (Semana IV).
  • Línea de comandos básica (cd, ls, ejecución de scripts) y un editor de texto.
Instalación previa Para reproducir los ejemplos se recomienda instalar Docker Desktop (Windows, macOS) o Docker Engine (distribuciones de Linux). La verificación se hace ejecutando en una terminal: 
$ docker --version

La segunda orden descarga una imagen mínima y la ejecuta. Si imprime el mensaje Hello from Docker!, el entorno está listo.

2. Del entorno virtual al contenedor

Antes de introducir los contenedores conviene revisar por qué no bastan los instrumentos vistos en semanas anteriores. La progresión natural es:

  1. Entorno virtual de Python (venv). Aísla las dependencias a nivel de paquete Python: garantiza que numpy==1.26.4 instalado para el proyecto no choque con la versión del sistema.
  2. Archivo requirements.txt. Documenta qué paquetes y qué versiones se necesitan. Permite reconstruir el entorno virtual con pip install -r requirements.txt.
  3. Fijación del intérprete y de las semillas aleatorias. Garantiza que dos ejecuciones del mismo análisis produzcan los mismos números en la misma máquina.

Estas tres herramientas resuelven la reproducibilidad dentro de una misma máquina, pero dejan abiertas tres preguntas críticas:

Pregunta ¿Lo resuelve venv + requirements.txt?
¿Qué versión del intérprete de Python se está usando? No. venv hereda el Python del sistema; cada máquina puede tener uno distinto.
¿Qué bibliotecas del sistema operativo están disponibles (libstdc++, libopenblas, tzdata)? No. Dependen de la distribución y de los paquetes instalados en cada computador.
¿En qué orden y con qué configuración deben arrancar los procesos (Uvicorn, una base de datos, una caché)? No. Es responsabilidad del despliegue, no del entorno virtual.

El contenedor extiende la idea del entorno virtual al sistema operativo completo: en lugar de aislar sólo paquetes Python, aísla también la versión del intérprete, las bibliotecas del sistema y los procesos. La analogía más útil para el lector estadístico es la siguiente:

Analogía conceptual Un venv es a los paquetes de Python lo que un contenedor es al sistema operativo. Si el archivo requirements.txt describe cómo reconstruir un entorno virtual, el Dockerfile describe cómo reconstruir una máquina completa, capa por capa.

El paralelismo es estricto y conviene tenerlo presente durante el resto de la unidad:

Concepto en el entorno virtual Concepto análogo en Docker
python -m venv .venv (crear el entorno) docker build (crear la imagen)
source .venv/bin/activate (activar) docker run (lanzar un contenedor)
requirements.txt (declaración de dependencias) Dockerfile (declaración de la imagen)
Un entorno virtual existente (carpeta .venv/) Una imagen construida (artefacto inmutable, identificado por un hash)
Una sesión de terminal con el entorno activado Un contenedor en ejecución (instancia mutable de una imagen)
Idea central Una imagen es una plantilla inmutable. Un contenedor es una instancia en ejecución de esa plantilla. La relación es la misma que existe entre una clase y una instancia en Python, o entre un molde estadístico y una realización muestral.

3. Contenedores vs Máquinas Virtuales

Tanto las máquinas virtuales (VMs) como los contenedores buscan el mismo objetivo: ejecutar varias aplicaciones aisladas en un mismo computador físico. La diferencia está en dónde se traza la línea de aislamiento.

3.1 Pila de cada tecnología

SO huésped 1 (kernel completo)
App 1 + dependencias
SO huésped 2 (kernel completo)

Contenedores
Hardware físico

Figura 3.1 — La VM virtualiza el hardware y carga un sistema operativo completo por instancia; el contenedor virtualiza el espacio de usuario y comparte el kernel del anfitrión.

3.2 Mecanismo técnico del aislamiento

El kernel de Linux ofrece dos primitivas que Docker explota directamente:

  • Namespaces. Aíslan la vista que un proceso tiene del sistema: PID (procesos), MNT (puntos de montaje), NET (interfaces de red), UTS (nombre de host), IPC (memoria compartida) y USER (mapeo de identificadores de usuario). Cada contenedor obtiene su propia vista y no puede observar los procesos de otro contenedor o del anfitrión.
  • Control groups (cgroups). Limitan los recursos que un grupo de procesos puede consumir: CPU, memoria, ancho de banda de disco y de red. Sin ellos, un único contenedor podría agotar la memoria del servidor.
Implicación para macOS y Windows Los namespaces y los cgroups son construcciones del kernel de Linux. En macOS y Windows, Docker Desktop ejecuta una pequeña máquina virtual Linux por debajo, y los contenedores corren dentro de esa VM. El estudiante percibe la misma interfaz, pero conviene saber que en esos sistemas hay un nivel adicional de indirección.

3.3 Comparativa cuantitativa

Dimensión Máquina virtual Contenedor
Tiempo de arranque Decenas de segundos a minutos (arranca un kernel). Milisegundos a segundos (sólo se inician procesos).
Tamaño en disco Gigabytes por VM (incluye el SO huésped). Decenas a cientos de megabytes por imagen.
Sobrecarga de memoria Cada VM reserva su RAM dedicada. Sólo la memoria de los procesos del contenedor.
Aislamiento Muy fuerte: kernel separado. Fuerte pero menor: kernel compartido. Vulnerabilidades del kernel pueden afectar a todos los contenedores.
Portabilidad Atada al hipervisor. Universal: cualquier máquina con un motor compatible ejecuta la imagen.
Caso de uso típico Aislar SOs distintos, separar tenants, sandboxes de seguridad. Empaquetar y desplegar aplicaciones; arquitecturas de microservicios.

Figura 3.2 — Valores típicos en escala logarítmica. Las diferencias entre VMs y contenedores no son cuantitativas sino de orden de magnitud: ~50× más rápido en arranque, ~20× menos disco y ~16× menos memoria para un escenario equivalente de servir una API.

3.4 ¿Cuándo elegir una u otra?

La elección depende del objetivo:

  • Si se necesita ejecutar Windows dentro de Linux o aislar máquinas de organizaciones distintas en una misma nube, una VM es lo apropiado.
  • Si se necesita empaquetar y desplegar una API estadística junto a sus dependencias en cualquier máquina del laboratorio, o si se quiere reproducir exactamente el experimento de un compañero, un contenedor es la opción natural.
Convivencia, no exclusión En la práctica, los servidores en la nube ejecutan máquinas virtuales que, a su vez, hospedan decenas de contenedores. Las dos tecnologías coexisten en capas distintas de la pila de despliegue.

4. ¿Por qué Docker ahora?

La contenerización como concepto no es nueva: el aislamiento basado en namespaces aparece en Linux a comienzos de los 2000 y FreeBSD jails es aún más antiguo. Lo que Docker introduce, a partir de 2013, es una experiencia de desarrollo ergonómica: un formato de imagen estandarizado, un registro público (Docker Hub) y una sintaxis declarativa (Dockerfile) que cualquier desarrollador puede leer en pocos minutos.

4.1 Cinco ventajas para el ciclo de desarrollo de una API estadística

  1. Reproducibilidad fuerte. La frase "funciona en mi máquina" deja de ser una excusa: la imagen es la máquina. Un análisis empaquetado en una imagen Docker en 2026 puede reejecutarse en 2030 y producir los mismos números, suponiendo que la imagen base permanezca accesible.
  2. Paridad entre desarrollo, pruebas y producción. La misma imagen que se ejecuta en un equipo de desarrollo opera sin cambios en el servidor de integración continua y en el servidor de producción. Las diferencias de configuración entre entornos —una de las primeras causas de incidentes— desaparecen casi por completo.
  3. Despliegue como composición de piezas. Los orquestadores modernos (Docker Compose, Kubernetes) toman varias imágenes —una API, una base de datos PostgreSQL, una caché Redis— y las orquestan como un sistema coherente.
  4. Aislamiento de experimentos. Es habitual en estadística comparar bibliotecas: scikit-learn 1.4 contra 1.5, statsmodels contra PyMC. Cada experimento puede vivir en una imagen distinta sin contaminar el sistema operativo del investigador.
  5. Empaquetamiento de modelos entrenados. Un modelo de regresión, un GLM o una red neuronal pueden incluirse como un archivo dentro de la imagen y servirse a través de FastAPI, todo en una sola unidad versionada.

4.2 Encaje en el ciclo de desarrollo moderno

Un flujo típico para una API estadística contenerizada sigue estos pasos:

  1. Se escribe el código de la API junto con un Dockerfile.
  2. Cada git push dispara una integración continua que ejecuta docker build y luego corre la suite de pytest dentro de un contenedor construido a partir de la imagen.
  3. Si las pruebas pasan, la imagen se etiqueta con el hash del commit y se publica a un registro privado.
  4. El servidor de producción descarga la imagen y la ejecuta. Lo que se prueba es idéntico, byte a byte, a lo que se despliega.
Conexión con la Semana X El capítulo previo defendió la reproducibilidad sin Docker como una higiene mínima: fijar versiones, semillas y configuración. Docker no reemplaza esa higiene; la amplifica. Una imagen construida sobre dependencias flotantes seguirá siendo no determinista. Toda buena práctica de la Semana X sigue vigente; lo que cambia es la unidad de empaquetamiento.

4.3 ¿Qué Docker no resuelve?

  • No corrige errores de modelado: una regresión mal especificada empaquetada en una imagen sigue mal especificada.
  • No reemplaza una suite de pruebas: el contenedor garantiza el entorno, pero la lógica se sigue verificando con pytest.
  • No reemplaza la documentación: el Dockerfile describe cómo se construye la imagen; el README sigue siendo necesario para describir qué hace la API.

5. Estructura de un Dockerfile

Un Dockerfile es un archivo de texto plano, sin extensión, que contiene una secuencia ordenada de instrucciones. Cada instrucción produce una capa de la imagen final. La metáfora útil es la de un manual de cocina: cada paso recibe el resultado del anterior y agrega algo encima.

5.1 Anatomía mínima

# Dockerfile — versión didáctica mínima
FROM python:3.11.9-slim-bookworm

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Cada palabra mayúscula es una instrucción reconocida por el motor de Docker. A continuación se describen las más importantes.

5.2 Instrucciones esenciales

Instrucción Propósito Ejemplo
FROM Declara la imagen base de la que se parte. Debe ser la primera instrucción no comentada. FROM python:3.11.9-slim-bookworm
WORKDIR Establece el directorio de trabajo dentro de la imagen. Si no existe, se crea. WORKDIR /app
COPY Copia archivos desde el contexto de construcción (sección 7) a la imagen. COPY requirements.txt .
RUN Ejecuta una orden en una capa nueva durante la construcción. RUN pip install -r requirements.txt
ENV Define una variable de entorno que persiste en imagen y contenedor. ENV PYTHONUNBUFFERED=1
ARG Define una variable disponible solo durante la construcción. ARG APP_VERSION=0.1.0
EXPOSE Documenta los puertos que la aplicación escucha. Es informativo: no publica puertos por sí solo. EXPOSE 8000
USER Cambia el usuario que ejecutará las instrucciones siguientes y el proceso del contenedor. USER appuser
CMD Define el comando por defecto del contenedor. Suele escribirse en forma exec (lista JSON). CMD ["uvicorn", "app.main:app"]
ENTRYPOINT Fija el ejecutable del contenedor. Combinado con CMD permite pasar argumentos por línea de comandos. ENTRYPOINT ["uvicorn"]

5.3 La imagen como una pila de capas

Cada instrucción FROM, COPY, RUN, ENV, WORKDIR y USER añade una capa nueva e inmutable. La imagen final es la superposición de todas ellas. Una imagen construida con el Dockerfile anterior tiene una estructura conceptual como esta:

CAPA 1 Imagen base python:3.11.9-slim-bookworm
CAPA 2 WORKDIR /app
CAPA 3 COPY requirements.txt .
CAPA 4 RUN pip install -r requirements.txt
CAPA 5 COPY app/ ./app/
CAPA 6 EXPOSE 8000 (metadatos)
CAPA 7 CMD [...] (metadatos)
Conexión con requirements.txt Cada línea de requirements.txt describe un paquete Python; cada instrucción del Dockerfile describe una transformación del sistema de archivos. Ambas son listas declarativas y ordenadas que producen un entorno determinado a partir de un punto de partida conocido. La diferencia es de alcance: requirements.txt opera sobre el árbol de paquetes Python; el Dockerfile opera sobre la pila completa.

5.4 Caché de capas: una optimización crítica

Docker calcula un hash de las entradas de cada instrucción: el contenido de los archivos copiados, los argumentos de RUN y el estado de la capa anterior. Si el hash coincide con uno ya almacenado, reutiliza la capa en lugar de reconstruirla.

De ahí surge una regla de oro: se ordenan las instrucciones por estabilidad decreciente. Las instrucciones que cambian rara vez van arriba; las que cambian con frecuencia van abajo. Por eso el patrón copiar primero requirements.txt, instalar dependencias y luego copiar el código es estándar:

  • Las dependencias cambian semanas o meses; el código cambia varias veces al día.
  • Si el código cambia pero requirements.txt no, las capas 3 y 4 se toman del caché y la reconstrucción tarda segundos en lugar de minutos.
# Anti-patrón: una sola instrucción COPY rompe la caché en cada cambio
COPY . .
RUN pip install -r requirements.txt

# Patrón correcto: dependencias primero, código después
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app/ ./app/

5.5 Forma exec vs forma shell

Las instrucciones CMD, ENTRYPOINT y RUN aceptan dos sintaxis:

  • Forma exec (lista JSON): CMD ["uvicorn", "app.main:app"]. El proceso se ejecuta sin shell intermedio. Es la forma recomendada porque permite que el proceso reciba directamente las señales del sistema operativo (SIGTERM, SIGINT) y termine limpiamente.
  • Forma shell: CMD uvicorn app.main:app. El motor envuelve la orden en /bin/sh -c. La señal SIGTERM llega al shell y no al proceso de Python, lo que puede impedir un cierre limpio.
Cierre limpio Una API estadística que no responde a SIGTERM deja peticiones a medias y conexiones de base de datos abiertas. Se recomienda usar siempre la forma exec en producción.

6. Imagen base: python:3.11.9-slim-bookworm

La elección de la imagen base condiciona el tamaño, la seguridad y la rapidez de construcción del contenedor. La imagen empleada en este curso es python:3.11.9-slim-bookworm. Conviene desmenuzar su nombre.

6.1 Lectura de la etiqueta

Componente Significado
python Repositorio oficial de imágenes con el intérprete CPython preinstalado, publicado y mantenido por la Python Software Foundation y la Docker Library.
3.11.9 Versión del intérprete: la misma utilizada en las semanas anteriores del curso. Fija las tres componentes (mayor, menor y de parche) para evitar saltos automáticos.
slim Variante recortada: incluye lo mínimo para ejecutar Python y pip; omite documentación, locales extensos y herramientas auxiliares de Debian.
bookworm Nombre en clave de la distribución base: Debian 12, publicada en junio de 2023 y soportada como stable hasta aproximadamente 2028.

6.2 ¿Por qué esta variante y no otra?

El repositorio python ofrece varias variantes. Su elección obedece a un compromiso entre tamaño, compatibilidad y seguridad:

Variante Tamaño aproximado Cuándo se elige
python:3.11.9 (Debian completa) ≈ 1 GB Útil cuando se requieren muchas bibliotecas del sistema; ineficiente en producción.
python:3.11.9-slim-bookworm ≈ 130–150 MB Punto de partida estándar para APIs Python en producción. Elección de este curso.
python:3.11.9-alpine ≈ 50 MB La más pequeña, pero usa musl en lugar de glibc: muchas wheels precompiladas (NumPy, pandas, scikit-learn) no son compatibles y deben recompilarse, alargando los tiempos de construcción.

Figura 6.1 — La variante slim-bookworm ocupa una fracción de la imagen completa sin renunciar a la compatibilidad binaria con glibc que exigen las wheels oficiales del ecosistema científico de Python.

Recomendación Para una API estadística que dependa del ecosistema científico de Python (NumPy, SciPy, pandas, scikit-learn, statsmodels), slim-bookworm es el equilibrio práctico. Las wheels oficiales de PyPI son compatibles y el tamaño final es razonable.

6.3 ¿Qué incluye y qué no incluye?

La variante slim incluye:

  • El intérprete CPython 3.11.9 con su biblioteca estándar.
  • pip, setuptools y un pequeño conjunto de utilidades de Debian (apt-get, dpkg).
  • Un puñado de librerías compartidas necesarias para arrancar Python.

Y deja fuera, entre otras cosas:

  • Compiladores (gcc, g++, build-essential).
  • Cabeceras de desarrollo (python3-dev, libssl-dev).
  • Herramientas comunes como git, curl, wget o vim.
Cuando una dependencia exige compilar Si una biblioteca científica no provee wheel para Linux x86_64 y requiere compilación (caso poco frecuente con NumPy, SciPy o scikit-learn, pero posible con paquetes menos comunes), conviene instalar build-essential en una etapa temporal (builder) y descartarla en la imagen final. Este patrón se desarrolla en la sección 8.

6.4 Pinning explícito de la versión

Existe la tentación de escribir FROM python:3.11-slim. Esto produce una imagen reproducible hoy, pero no mañana: la etiqueta flotante 3.11 apunta al último parche disponible. Una reconstrucción meses después puede traer 3.11.10 o 3.11.12 y, con ello, cambios sutiles en el intérprete.

Para una API estadística, donde la reproducibilidad numérica importa, se prefiere siempre la versión completa:

# No recomendado: la versión flota.
FROM python:3.11-slim

# Recomendado: versión exacta.
FROM python:3.11.9-slim-bookworm

# Reproducibilidad máxima: hash criptográfico de la imagen.
# El hash se obtiene con: docker pull python:3.11.9-slim-bookworm
# y luego: docker inspect python:3.11.9-slim-bookworm --format='{{index .RepoDigests 0}}'
FROM python:3.11.9-slim-bookworm@sha256:abc123...def

Fijar el hash digest (@sha256:...) es la forma más estricta de reproducibilidad: garantiza que el contenido de la imagen base es bit a bit el mismo, incluso si la etiqueta cambia.

7. Contexto de construcción

Al ejecutar docker build . el cliente de Docker no compila la imagen en la máquina local: empaqueta el directorio actual y lo envía a un proceso llamado daemon de Docker, que es quien efectivamente construye la imagen. Ese paquete recibe el nombre de contexto de construcción.

7.1 Definición precisa

El contexto es el árbol de archivos enraizado en el directorio que se pasa como último argumento a docker build. La instrucción COPY sólo puede leer archivos que estén dentro de ese árbol; no puede escapar hacia rutas absolutas del anfitrión ni navegar fuera con ...

$ cd /home/usuario/proyectos/regresion-api
$ docker build -t regresion-api:0.1.0 .
[+] Building 12.4s (10/10) FINISHED
 => transferring context: 482.31kB                              0.1s
 => [internal] load build definition from Dockerfile             0.0s
 => [1/5] FROM docker.io/library/python:3.11.9-slim-bookworm     2.1s
 => [2/5] WORKDIR /app                                            0.0s
 => [3/5] COPY requirements.txt .                                 0.0s
 => [4/5] RUN pip install --no-cache-dir -r requirements.txt    8.7s
 => [5/5] COPY app/ ./app/                                        0.1s
 => exporting to image                                            1.4s

La línea transferring context indica que se enviaron 482 KB al daemon. En proyectos descuidados ese número puede crecer hasta varios gigabytes.

7.2 El archivo .dockerignore

El mecanismo principal para controlar qué se envía al daemon es el archivo .dockerignore, situado en la raíz del contexto. Su sintaxis es muy similar a la de .gitignore. Un .dockerignore razonable para una API estadística incluye: 

# .dockerignore

# Control de versiones
.git
.gitignore
.gitattributes

# Entornos virtuales locales (no se reutilizan dentro de la imagen)
.venv

# Cachés de Python
__pycache__
*.pyc
*.pyo
.pytest_cache
.mypy_cache
.ruff_cache

# Notebooks de exploración (suelen contener datos crudos voluminosos)
notebooks/
*.ipynb_checkpoints

# Datos crudos y artefactos pesados
data/raw/

# Configuración local sensible

# Documentación e IDE
README.md

.idea/
.vscode/
*.swp

# El propio Dockerfile no se necesita dentro de la imagen
Dockerfile
.dockerignore

7.3 ¿Por qué importa tanto este archivo?

  1. Velocidad. Cada byte sobrante se transfiere y se sube por la red a registros remotos.
  2. Seguridad. Sin .dockerignore, un archivo .env con credenciales puede acabar dentro de la imagen y publicarse al registro. La regla práctica es: todo lo que no debería copiarse, debe ignorarse explícitamente.
  3. Caché. Cuando la instrucción COPY . . incluye archivos volátiles (logs, cachés de tests), su hash cambia constantemente y la caché se invalida en cada construcción, alargando los tiempos.
Riesgo de fuga de credenciales Un .env con la contraseña de la base de datos copiado a una imagen queda registrado en una capa permanente. Aunque luego se elimine con un RUN rm, la capa anterior sigue conservando el archivo. La única protección efectiva es no copiarlo nunca: para eso sirven .dockerignore y, en pipelines más maduros, los secrets inyectados como variables de entorno en tiempo de ejecución (Semana III, python-dotenv).

7.4 Verificación práctica

Para inspeccionar exactamente qué archivos llegarían al daemon antes de construir la imagen, puede prepararse un contexto de prueba:

$ tar --exclude-from=.dockerignore -cvf - . | tar -tvf -

Esta orden imita el filtrado de .dockerignore y lista cada entrada que se enviaría. Es una herramienta valiosa para auditar contextos sospechosamente grandes.

8. Multi-stage builds

Una primera versión de un Dockerfile suele mezclar dos preocupaciones distintas: construir el software (compilar, instalar herramientas de desarrollo, ejecutar pruebas) y ejecutarlo (servir peticiones HTTP). El resultado contiene compiladores, cabeceras y artefactos intermedios que en producción son superfluos y, peor aún, agrandan la superficie de ataque.

Los multi-stage builds, disponibles desde Docker 17.05, resuelven el problema dividiendo el Dockerfile en etapas. Cada etapa empieza con una nueva instrucción FROM y puede copiar selectivamente artefactos de las anteriores con COPY --from=....

8.1 Esquema general

# Etapa 1: builder — todo lo que sólo hace falta durante la construcción
FROM python:3.11.9-slim-bookworm AS builder
# ... instalar compiladores, descargar dependencias, compilar wheels ...

# Etapa 2: runtime — la imagen final que se entrega a producción
FROM python:3.11.9-slim-bookworm AS runtime
COPY --from=builder /opt/venv /opt/venv
# ... copiar el código y arrancar la aplicación ...

La imagen final, identificada por la etapa con la última instrucción FROM (o por una etapa nombrada con --target), contiene sólo lo que se copió explícitamente. Las herramientas de la etapa builder no aparecen en el resultado.

8.2 Ventajas concretas

  1. Reducción de tamaño. Un Dockerfile mono-etapa que necesita compilar puede pesar 800 MB; el mismo proyecto en multi-stage suele quedarse entre 180 y 250 MB.
  2. Separación de dependencias. Las dependencias de construcción (compiladores, cabeceras) viven sólo en el builder; las de ejecución (la API y sus paquetes Python) viven en runtime.
  3. Superficie de ataque más pequeña. Sin compiladores ni gestores de paquetes activos en producción, un atacante que logre ejecutar código tiene menos herramientas para escalar privilegios.
  4. Reutilización de etapas. Una misma etapa builder puede alimentar varias imágenes finales (API, worker, job batch) sin duplicar la instalación de dependencias.
  5. Construcción paralela. Etapas independientes pueden construirse en paralelo cuando se utiliza el motor BuildKit.

8.3 Patrón recomendado para Python

El patrón más común instala las dependencias en un entorno virtual dentro del builder y copia ese entorno virtual completo a la etapa de runtime. Así se evita reinstalar paquetes en la imagen final.

# syntax=docker/dockerfile:1.7

# ============================================================
# Etapa 1 — builder
# ============================================================
FROM python:3.11.9-slim-bookworm AS builder

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

# build-essential sólo se necesita para compilar wheels que no
# lleguen precompiladas; se descarta junto con esta etapa.
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*

# Entorno virtual aislado en /opt/venv (será portable a la etapa runtime)
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

WORKDIR /build
COPY requirements.txt .
RUN pip install --upgrade pip \
 && pip install -r requirements.txt

# ============================================================
# Etapa 2 — runtime
# ============================================================
FROM python:3.11.9-slim-bookworm AS runtime

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"

# Usuario no privilegiado para ejecutar la aplicación.
RUN groupadd --system --gid 1001 appgroup \
 && useradd  --system --uid 1001 --gid appgroup --create-home appuser

WORKDIR /app

# Sólo se trae el entorno virtual: ni compiladores ni cachés de apt.
COPY --from=builder /opt/venv /opt/venv

# Código de la aplicación con propietario no-root.
COPY --chown=appuser:appgroup app/ ./app/

USER appuser

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

8.5 Construcción dirigida a una etapa específica

Las etapas son útiles también durante el desarrollo: permiten construir hasta un punto intermedio para depurar.

$ docker build --target builder -t regresion-api:builder .
$ docker run --rm -it regresion-api:builder bash

Este patrón abre una shell dentro del builder e inspecciona el entorno virtual instalado, las versiones resueltas por pip y el tamaño exacto de cada dependencia, sin modificar la imagen de producción.

Conexión con la pirámide de testing (Semana X) Una etapa intermedia tester resulta natural en una API estadística: instala el código, ejecuta pytest y, sólo si pasa, deja que el motor produzca la imagen final. Si las pruebas fallan, la construcción aborta y la imagen jamás se publica al registro.

9.2 Modelo entrenado fuera de línea

Para mantener el ejemplo autocontenido, el modelo se reduce a una regresión lineal univariada con coeficientes precalculados. En un proyecto real este archivo lo produciría un script de entrenamiento separado (idealmente versionado).

# app/modelo.json — coeficientes de y = 2.3 * x + 1.7
{
    "version": "0.1.0",
    "intercepto": 1.7,
    "pendiente": 2.3,
    "x_min": -10.0,
    "x_max": 10.0
}

9.3 Carga del modelo (app/modelo.py)

# app/modelo.py
from __future__ import annotations

import json
from dataclasses import dataclass
from functools import lru_cache
from pathlib import Path

RUTA_MODELO = Path(__file__).parent / "modelo.json"


@dataclass(frozen=True)
class ModeloRegresion:
    """Regresión lineal simple con coeficientes inmutables."""
    version: str
    intercepto: float
    pendiente: float
    x_min: float
    x_max: float

    def predecir(self, x: float) -> float:
        return self.intercepto + self.pendiente * x


@lru_cache(maxsize=1)
def cargar_modelo() -> ModeloRegresion:
    """Carga el modelo desde disco una sola vez por proceso."""
    with RUTA_MODELO.open("r", encoding="utf-8") as f:
        datos = json.load(f)
    return ModeloRegresion(**datos)

La función cargar_modelo, decorada con @lru_cache, se integra con el patrón de inyección de dependencias visto en la Semana III: actúa como una provider reutilizable, costosa la primera vez y barata después.

9.4 Esquemas Pydantic (app/schemas.py)

# app/schemas.py
from pydantic import BaseModel, Field, field_validator


class EntradaPrediccion(BaseModel):
    x: float = Field(..., description="Variable explicativa")

    @field_validator("x")
    @classmethod
    def validar_rango(cls, valor: float) -> float:
        if not -1000.0 <= valor <= 1000.0:
            raise ValueError("x debe pertenecer a [-1000, 1000]")
        return valor


class SalidaPrediccion(BaseModel):
    y_hat: float = Field(..., description="Predicción del modelo")
    extrapolado: bool = Field(
        ...,
        description="True si x cae fuera del rango observado en entrenamiento",
    )
    version_modelo: str = Field(
        ...,
        description="Versión semántica del modelo servido",
    )

La validación con @field_validator y la respuesta automática HTTP 422 frente a cargas útiles inválidas son herencia directa de las semanas previas de Pydantic y FastAPI. La pieza nueva es que el contenedor las preserva exactamente igual al desplegarse.

Dos cotas, dos propósitos Conviene distinguir las dos cotas que aparecen sobre x:
  • El rango de validación de Pydantic ([-1000, 1000]) protege a la API de entradas absurdas o mal formadas; al violarlo, la API devuelve 422 Unprocessable Entity.
  • El rango del modelo ([x_min, x_max] = [-10, 10]) describe el dominio en el que se entrenó la regresión. Una x = 50 es perfectamente válida como tipo numérico, pero implica una extrapolación; la API responde 200 con extrapolado: true para que el cliente quede advertido.
Confundir ambas cotas es un error frecuente: la primera es responsabilidad de FastAPI/Pydantic; la segunda, del estadístico que entrenó el modelo.

9.5 Aplicación FastAPI (app/main.py)

# app/main.py
from fastapi import FastAPI, Depends

from app.modelo import ModeloRegresion, cargar_modelo
from app.schemas import EntradaPrediccion, SalidaPrediccion

app = FastAPI(
    title="regresion-api",
    version="0.1.0",
    description="API mínima que sirve un modelo de regresión lineal simple.",
)


@app.get("/health", status_code=200)
def health() -> dict[str, str]:
    """Sondeo de vida útil para orquestadores."""
    return {"status": "ok"}


@app.post("/predicciones", response_model=SalidaPrediccion)
def predecir(
    entrada: EntradaPrediccion,
    modelo: ModeloRegresion = Depends(cargar_modelo),
) -> SalidaPrediccion:
    y_hat = modelo.predecir(entrada.x)
    return SalidaPrediccion(
        y_hat=y_hat,
        extrapolado=not (modelo.x_min <= entrada.x <= modelo.x_max),
        version_modelo=modelo.version,
    )

9.11 Recapitulación de decisiones

Decisión Justificación didáctica
Imagen base python:3.11.9-slim-bookworm Coincide con el intérprete del curso, es ligera y compatible con las wheels del ecosistema científico.
Multi-stage con builder y runtime separados Reduce el tamaño y elimina compiladores de la imagen final.
Entorno virtual en /opt/venv Hace portable el conjunto completo de dependencias mediante un solo COPY --from=builder.
Usuario appuser con UID 1001 Cumple el principio de menor privilegio: el proceso de Uvicorn no puede escribir en el sistema de archivos del contenedor fuera de /home/appuser y de los archivos de los que appuser es propietario en /app (los copiados con --chown=appuser:appgroup).
HEALTHCHECK declarado Permite que orquestadores reinicien el contenedor si la API deja de responder.
Forma exec en CMD Asegura que SIGTERM llegue directamente a Uvicorn y que el cierre sea limpio.

10. Autoevaluación

Las preguntas siguientes ponen a prueba la comprensión conceptual y la capacidad de redactar Dockerfiles correctos. Se recomienda intentarlas antes de leer las soluciones comentadas.

10.1 Preguntas conceptuales

Ejercicio 10.1 — Diferencia clave Explíquese, en máximo cuatro líneas, por qué dos contenedores que ejecutan Python 3.11.9 y NumPy 1.26.4 sobre el mismo computador comparten el kernel del anfitrión, mientras que dos máquinas virtuales con la misma configuración no.
Solución comentada 10.1 Cada máquina virtual incluye un sistema operativo huésped completo —incluido su propio kernel— que se ejecuta sobre un hipervisor. Dos VMs en paralelo cargan dos kernels distintos en memoria. Un contenedor, en cambio, sólo aísla el espacio de usuario mediante namespaces y cgroups del kernel del anfitrión; todos los contenedores en una misma máquina comparten ese único kernel y, por eso, arrancan en milisegundos y consumen mucha menos memoria.
Ejercicio 10.2 — Lectura de etiquetas Indíquese qué significa cada componente de la etiqueta python:3.11.9-slim-bookworm y por qué la elección de 3.11.9 es preferible a 3.11 en una API estadística.
Solución comentada 10.2 python es el repositorio oficial; 3.11.9 es la versión exacta del intérprete; slim indica una variante reducida de Debian; bookworm es el nombre en clave de Debian 12. Fijar 3.11.9 evita que la etiqueta flotante 3.11 apunte automáticamente a un parche posterior, garantizando que las decisiones numéricas de la API sean reproducibles en el tiempo.
Ejercicio 10.3 — Caché de capas El siguiente fragmento se reconstruye lentamente cada vez que cambia un archivo de la carpeta app/. Identifíquese el problema y propóngase una corrección: 
FROM python:3.11.9-slim-bookworm
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
CMD ["uvicorn", "app.main:app"]
Solución comentada 10.3 El problema es que COPY . . incluye el código fuente; cualquier cambio en app/ invalida la capa siguiente y obliga a reinstalar todas las dependencias. La corrección consiste en separar la copia de requirements.txt de la del código: 
FROM python:3.11.9-slim-bookworm
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app/ ./app/
CMD ["uvicorn", "app.main:app"]
Mientras requirements.txt no cambie, la capa de instalación se reutiliza y la reconstrucción tarda segundos en lugar de minutos.
Ejercicio 10.4 — Contexto de construcción Indíquense tres archivos o carpetas que nunca deberían incluirse en una imagen de producción y descríbase qué problema concreto causa cada uno si llega a colarse.
Solución comentada 10.4 Tres ejemplos típicos:
  • .env: contiene credenciales (claves de API, contraseñas de bases de datos). Si llega a la imagen, queda registrado en una capa permanente y puede filtrarse cuando la imagen se publica al registro.
  • .git/: incluye toda la historia del proyecto y sus posibles ramas, archivos eliminados que aún viven en commits, y datos de identidad de los autores. Aumenta el tamaño y la superficie de información expuesta.
  • data/raw/: archivos crudos de varios gigabytes vuelven la imagen pesadísima, ralentizan los despliegues y pueden contener información personal sin anonimizar.
Ejercicio 10.5 — Multi-stage en propias palabras Resúmase, en máximo seis líneas, qué problema resuelve un multi-stage build y cuáles son los dos artefactos que se descartan por completo al pasar a la etapa de runtime en el ejemplo del curso.
Solución comentada 10.5 Un multi-stage build separa las dependencias necesarias para construir el software de las necesarias para ejecutarlo. Sólo la última etapa forma la imagen entregada; todas las anteriores se descartan. En el ejemplo del curso, la imagen final no contiene build-essential ni la caché de paquetes Debian (/var/lib/apt/lists/), reduciendo el tamaño y la superficie de ataque.
Ejercicio 10.6 — Usuario no privilegiado Justifíquese por qué la instrucción USER appuser es esencial en una imagen de producción, incluso aunque las pruebas funcionen igual con USER root.
Solución comentada 10.6 Si una vulnerabilidad permite a un atacante ejecutar código arbitrario dentro del contenedor y el proceso corre como root, ese código actúa como root: puede modificar todos los archivos del contenedor, instalar paquetes, montar puntos de montaje del anfitrión —si están expuestos— y, en escenarios con fugas de aislamiento, escalar privilegios al sistema anfitrión. Un usuario no privilegiado convierte ese mismo escenario en un compromiso mucho más limitado: el atacante hereda los permisos restringidos de appuser, lo que contiene el daño y facilita la respuesta a incidentes.

10.2 Redacción de Dockerfiles

Ejercicio 10.7 — Mini-API determinista Redáctese un Dockerfile mono-etapa, basado en python:3.11.9-slim-bookworm, que empaquete una mini-API FastAPI con un único endpoint GET /version que devuelva {"version": "0.1.0"}. Súmense estos requisitos:
  1. El proceso debe correr como un usuario no privilegiado.
  2. La caché debe permitir que un cambio en el código no reinstale las dependencias.
  3. El puerto expuesto es 8000.
Solución comentada 10.7 
# Dockerfile mono-etapa, didáctico
FROM python:3.11.9-slim-bookworm

    PYTHONUNBUFFERED=1

# Usuario no privilegiado.

Ejercicio 10.8 — Versión multi-stage Reescríbase el Dockerfile del ejercicio anterior empleando dos etapas (builder y runtime). El builder debe instalar las dependencias en un entorno virtual; la etapa final debe contener únicamente el entorno virtual y el código.
Solución comentada 10.8 
# syntax=docker/dockerfile:1.7

# --- builder ---
FROM python:3.11.9-slim-bookworm AS builder
ENV PIP_NO_CACHE_DIR=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /build
COPY requirements.txt .
RUN pip install --upgrade pip && pip install -r requirements.txt

# --- runtime ---
FROM python:3.11.9-slim-bookworm AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"
RUN groupadd --system --gid 1001 appgroup \
 && useradd  --system --uid 1001 --gid appgroup --create-home appuser
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY --chown=appuser:appgroup app/ ./app/
USER appuser
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
La imagen final se reduce porque no contiene los archivos auxiliares de pip ni los caches intermedios; sólo el entorno virtual y el código. El patrón es idéntico al del ejemplo integrador y resulta directamente transferible a otras APIs estadísticas.

11. Conclusión, buenas prácticas de seguridad y recursos

11.1 Resumen ejecutivo

  1. Un contenedor extiende la idea del entorno virtual al sistema operativo completo: aísla paquetes, intérprete, bibliotecas del sistema y procesos.
  2. Las máquinas virtuales virtualizan el hardware y cargan un kernel completo; los contenedores comparten el kernel del anfitrión y son órdenes de magnitud más livianos.
  3. El Dockerfile describe, instrucción a instrucción, cómo se reconstruye la imagen. Cada instrucción produce una capa cacheable.
  4. La imagen base python:3.11.9-slim-bookworm ofrece un balance razonable entre tamaño, compatibilidad con el ecosistema científico de Python y vigencia de soporte.
  5. El contexto de construcción es lo que el cliente envía al daemon. Un .dockerignore bien diseñado mantiene el contexto pequeño, rápido y sin secretos.
  6. Los multi-stage builds separan construcción de ejecución: la imagen final no contiene compiladores ni cachés, lo que reduce el tamaño y la superficie de ataque.

11.2 Buenas prácticas de seguridad

Lista mínima de seguridad
  • No ejecutar como root. Crear un usuario del sistema con useradd y aplicar USER antes del CMD final.
  • No copiar secretos a la imagen. Usar .dockerignore para excluir .env, claves privadas y certificados; inyectar credenciales como variables de entorno en tiempo de ejecución.
  • Fijar versiones. Tanto la imagen base (3.11.9-slim-bookworm) como las dependencias en requirements.txt con ==; idealmente, fijar el digest @sha256:... de la imagen base.
  • Mantener el contexto pequeño y limpio. Cada archivo que no participe en la construcción es una potencial fuga de información y un ralentizador del flujo de trabajo.
  • Reducir la superficie de ataque. Multi-stage para descartar compiladores; una sola responsabilidad por imagen; sin curl ni git en producción.
  • Escanear vulnerabilidades. Herramientas como docker scout, trivy o grype inspeccionan las capas y reportan CVEs conocidas.
  • Actualizar regularmente la imagen base. Reconstruir y republicar cuando aparezcan nuevos parches de seguridad de Debian o de CPython.
  • Privilegios mínimos en tiempo de ejecución. Lanzar con docker run --read-only o --cap-drop=ALL cuando la aplicación lo permita.
